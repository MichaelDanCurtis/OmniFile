# Decision log

Owner decisions, newest last. Each entry says what was decided and the context that made it the right call. Research evidence: `docs/research/2026-09-26-research-findings.md`.

## 2026-09-26 — Research phase (in the Prizmanyx conversation)

| # | Decision | Context |
|---|---|---|
| 1 | **Build, don't buy.** | No product combines plain Azure blobs, the Archive tier, an in-protocol NFS "offline/wait" signal, per-user notification and a self-service recall portal. Spectra StorCycle and Komprise come closest. Gateways (Nasuni, CTERA, Panzura, NetApp tiering, Isilon CloudPools) stop at Hot/Cool/Cold. |
| 2 | **Separate product, separate repo, named OmniFile Gateway.** It is a leave-behind product that Prizmanyx uses through an API. | A permanent sync agent sits outside Prizmanyx's migration scope ("continuous replication" is excluded there), and it runs code on client servers. |
| 3 | **Linux only** for the edge filer. | fanotify pre-content events (Linux ≥ 6.14) and NFS-Ganesha make a Linux filer realistic. Appliance NAS (Isilon/NetApp) cannot host our code. |
| 4 | **Rust** (edge daemon), **C** (Ganesha FSAL), **Python** (Azure service). | Rust suits the high-throughput uploader and fanotify handling. Ganesha FSALs are C. Python matches Prizmanyx, so API models can be shared. |
| 5 | **Archive is core.** Tier timing is configurable: Hot → Cool → Cold → Archive days, *or* Smart tier plus a respected archive date. | Smart tier needs ZRS and Archive forbids ZRS, so Smart + archive = two storage accounts and a server-side copy on the archive date. |
| 6 | **NFSv3, NFSv4.x and SMB are all supported**; NFSv4 is preferred. Batch clusters may wait. | Per-share recall policy: wait / fail fast / wait if quick. |
| 7 | **AD integration is mandatory; all target clients have on-prem AD.** | Removes the cloud-only-Entra problem (no supported NFS/SMB authentication with Entra ID alone). |
| 8 | **Kerberos is configurable per share**, and the UI shows a throughput-cost note when it is enabled. | Microsoft measured krb5 ≈ −53% IOPS and krb5p ≈ −77% on NFS. |
| 9 | **Teams is the primary notification channel** (proactive bot, Adaptive Cards with buttons); email is the fallback. | AD SID → Entra user via Graph makes per-user cards possible. |
| 10 | **Must work over Azure Private Endpoints.** | All data and control traffic is private. |
| 11 | **One public endpoint is acceptable** — the Teams callback relay only. | Teams must reach the bot's messaging endpoint from the internet; this cannot be made private. |
| 12 | **Policy UI: very easy, very detailed.** | Four plain questions (which files / when they move / what users see / who is told), with a live timeline, live cost and live rule checks. Everything else sits under "More settings". |
| 13 | **Provider-agnostic, like Azure Data Box Gateway for any provider.** Each dataset binds to a storage backend (Azure Blob and Amazon S3 first). Where the data sits is between the gateway and the provider. | The owner's framing (2026-09-26): feel and act like Data Box Gateway, without being dedicated to Azure. Consequences: logical tiers mapped per backend; the "Azure service" becomes the OmniFile service with pluggable backends; the migration namespace is a dataset whose backend changes. |
| 14 | **Migrations run in any direction** (S3 → Azure, Azure → S3, …). While a dataset is migrating, **every new write goes to the destination**. | The owner's rule (2026-09-26). For Prizmanyx engagements the destination is mostly Azure, but the model is symmetric. |
| 15 | **OmniFile always holds permission to request Glacier restores** (`s3:RestoreObject`), and a completed or scheduled restore can **automatically trigger migration** of the restored objects. | Restores are part of the product, not an exception. One restore serves the user and the migration. *Kept for every source by decision 74 (2026-11-11).* |
| 16 | **Egress on user reads during a migration is accepted.** Egress waivers are an administrative matter outside this project. | Reads are served from wherever the bytes are; the cache reduces egress but is not required to avoid it. |
| 17 | **Control plane runs in Azure** (container app + Azure Database for PostgreSQL, VNet-injected). *Revised the same day:* an earlier draft made it portable to AWS ECS for S3-only clients; decision 18 removed that case. | Azure is the long-term home of every dataset OmniFile serves. The control plane still avoids depending on Event Grid push, because that breaks private networking. *Amended by decision 69 (2026-11-11): Azure is one host among three, not the only one.* |
| 18 | **S3-only clients are out of scope; they can use AWS Storage Gateway (S3 File Gateway).** OmniFile serves datasets whose home is Azure, and presents S3 data only while it migrates, in either direction. | The owner (2026-09-26): AWS already offers the Data-Box-Gateway equivalent for S3. The S3 backend exists for migrations: source for S3 → Azure, destination for Azure → S3. *Reversed by decision 68 (2026-11-11): any of the three clouds can be a dataset's home.* |
