# Local renames, deletes and owner changes reach the catalog

**Status: built (2026-10-16); who made each change and hard links added 2026-10-21 (ports of line B, below).** Tests: `edge/crates/omnifile-edge/tests/nsync_linux.rs` (renames, moves, swaps, new folders, chowns and deletes from other processes, against a fake service that a replay checks never sees a rename onto a taken name), `omnifile-detect/tests/ns_linux.rs` (the watcher), and step 10 of `tests/e2e/m5_exit_test.sh` (over NFS and from a shell, against the real service: a renamed or moved file keeps its catalog id, deleted files and folders are tombstoned and never come back, and every op is acknowledged). Found by the M7 edge review (`docs/design/threat-model.md`, T8). The edge sends the service a `create` for every new local file and folder, and a commit for every write, but never a user's rename, move, delete or `chown`. `ChangeKind::Rename`, `Unlink` and `Setattr` exist in the control types, and `POST …/changes` accepts them (`control-api.md` §4.1), but nothing sends them. So the catalog, the portal, the partner API, rewind trees and Teams cards kept old names and deleted files. A re-snapshot after a digest mismatch would even bring a deleted file back as a placeholder. `edge-metadata.md` §5.4 and §6 have always said the edge is the authority for these changes until acknowledged; this note says how it is done.

## What is detected, and how

The edge watches the namespace, not the protocols. NFS (Ganesha's `FSAL_VFS`), SMB (smbd) and a local shell all change the same xfs tree, so one watcher sees them all; the FSAL's `NS_HINT` isn't needed.

- **Events mark directories, nothing more.** A fanotify notification group in directory-FID mode (`FAN_REPORT_DIR_FID`), marked on the data volume's filesystem, reports `FAN_CREATE`, `FAN_DELETE`, `FAN_MOVED_FROM`, `FAN_MOVED_TO` and `FAN_ATTRIB` (`FAN_ONDIR` too). Each event names the directory that changed, as a file handle. The daemon opens it by handle (`open_by_handle_at`, `CAP_DAC_READ_SEARCH`) and marks that directory dirty. Events caused by the daemon itself (its pid) are skipped. The queue is the kernel's default, bounded one, so under a flood (`tar x`, `chown -R`) the kernel drops events and says so, and the daemon sweeps. Each burst is looked up once per directory.
- **A dirty directory is reconciled against the replica**, after a short quiet period, so a burst of events is one pass. The pass compares what is on disk with what the replica says is there, by inode and generation:
  - **Identity is the inode number and its generation,** both read from the entry's file handle (`name_to_handle_at`), so nothing is opened as root. xfs often gives a freed inode number to the next file: `rm a; cp x a` is a new file and a delete, not the same file.
  - **The same name, the same inode:** compare the owner. A changed `uid` or `gid` is a `setattr`. A changed mode is left to the ACL scan, which reports mode and ACL together (`acl.rs`), and the path is queued for it. A share root's group is the edge's own (Owners), never sent.
  - **A name the replica doesn't have,** whose inode (and generation) is a replica node: that node was renamed or moved here, and it's a `rename` to this directory and name. Unless its recorded place still holds the same inode: then it's a second hard link (`cp -al`, `rsync --link-dest`), and the catalog keeps its one name.
  - **A name the replica doesn't have, whose inode is unknown:** a new object. A new folder is created as today (`commit.rs`, `ensure_dir`). A new file is the write detector's, which sees its close; one whose close it never saw is handed to the commit pipeline once quiet (below, "Files no close was seen for").
  - **A replica child whose name is gone,** and which no entry here claims: the daemon opens its inode by handle (`(ino, generation)` as xfs's 64-bit handle; checked on xfs: a wrong generation is `ESTALE`).
    - **Gone (`ESTALE`), or open but with no links left:** deleted. It and, for a folder, what the replica has below it become `unlink` ops, deepest first, because the catalog has no recursive delete. Below it means less what this pass moves here (`mv old/* . && rmdir old`): those are renamed first, and the folder's unlink follows. Everything else below it that was on disk is looked up by handle, and if any of it is alive somewhere else, its move hasn't been seen yet: the delete waits for a later pass rather than tombstone a live file. It waits with a back-off (5 s doubling, six times, about five minutes); after that, what is gone is deleted, and what is still alive stays in the catalog with every folder above it, recorded as a conflict.
    - **Alive somewhere else:** moved. Its new directory is marked dirty, and the pass there finds it as a rename.
- **Swapped names** (`a` ↔ `b`, in one folder or across two, before the quiet period ends): a node that moved onto a name the catalog still gives another node that moved too would find it taken. That holder is first renamed to a temporary name no node there has (`.omnifile-mv-<lid>-<n>`) in the catalog, but only if its new place is a folder the catalog has, then the renames follow in order, so the service never answers `conflict`. A holder that didn't move (a catalog file the edge couldn't place) keeps its name, and the rename is refused as below.
- **Nothing is trusted from the event itself:** not its name, not its order. A lost or reordered event costs only a later pass, and the daemon's own changes find the replica already agreeing.
- **A sweep** reconciles every directory: once at start (events while the daemon was down are not kept) and every `[namespace] sweep_s` (a day by default). It runs at low priority and paces itself.

## Files no close was seen for (WP9, 2026-11-03)

WP3's chaos soak (M7) lost a file: written over NFSv4.1, fsync and close returned 0, and the daemon was SIGKILLed 0.9 s later, inside the 3 s commit quiet period. The detector had read the close and was waiting out the quiet period; that wait was in the daemon's memory and died with it. The sweep left new files to the detector, so the file was never uploaded, stubbed or put in the catalog. It was 1 of 239 writes in 30 minutes. A file written while the daemon was down was lost the same way, and so was one whose commit stopped after its `create` (while it was cloned or hashed): the replica knew it, with no version, and nothing came back to it.

Two layers fix it:

- **Every pass, the sweep at start included, hands such files to the commit pipeline** as a close no one saw (`CloseWrite::swept_gen`). A file qualifies if it is a regular file with one name and either no replica node, or a node the edge registered and never committed a version of (`local_dirty`, no content version). The pass only reads the directory; a file whose ctime is newer than the commit quiet period plus 2 s is looked at again when that time is up (the first look comes right after it, so a file closed just before a restart is committed then), and one open for write (a read lease can't be taken) is looked at again with a backoff (5 s doubling, eight times). After that the detector, which is running, sees its close, or the next sweep finds it. To look, the pass opens the entry by an `O_PATH` handle, checks that it is the same regular inode, and only then reopens it read-only, so a FIFO or device swapped in is never opened. A file it handed is not handed again for 30 minutes unless its commit is done.
- **The commit checks it all again** in the single commit task, so no other commit of the file can run between the check and the commit: the name still holds that inode (and generation); it carries no `trusted.omnifile` marker; the replica still doesn't know it, or knows it only as never committed, and the upload outbox holds no upload of it; its last write (mtime) is older than the quiet period; and nobody has it open for write. A file not ready is retried on the commit pipeline's backoff (2 s doubling, ten times). So a file is never committed while a writer has it open, and never twice: a second event for a file already registered and committed, or held in the outbox, is ignored.
- **The edge's own files are never committed this way.** Everything the edge makes in a share is marked: placeholders and stubs carry `trusted.omnifile`, recall notes carry their own `trusted.*` mark (a user's file that is only named `*.RECALLING.txt` is committed). Commit clones and rewind trees are under `.omni/`, which no pass walks and the commit refuses. Hard links keep their path: a new file with two names waits for one name's commit and is then split (below); once it has one name it is a new file like any other.
- **The detector's group is kept in the systemd fd store** (`FDNAME=omnifile-detect`, `FAN_UNLIMITED_QUEUE`, `edge/crates/omnifile-edge/src/fdstore.rs`), as the smb-guard's are. A close that lands while the daemon restarts or is down is queued there and read by the next instance, including the overwrite of a file that is already committed, which the sweep can't tell from an unchanged one. The unit has `NotifyAccess=main` so the push is accepted without the guard's `Type=notify` drop-in.

- **A durable log of pending closes** (`edge/crates/omnifile-edge/src/pending.rs`, `<replica dir>/pending-closes`). This covers an overwrite of a file that is already committed whose close the detector had read when the daemon died: in its quiet period, or queued behind other commits. The sweep can't find that one, and the catalog would go on serving the old version while the new bytes had no copy off the box.
  - The detector records each file it starts waiting on (`+ token ino generation`) before it acts on the event, and makes the records durable (`fdatasync`) once per batch of events.
  - The commit pipeline writes `- token` once the commit has an outcome: committed, held in the upload outbox, or nothing to do. A commit that fails stays pending, so the next start tries it again.
  - At start the daemon opens each pending file by its xfs handle, wherever it is now. It hands them to the new detector, which waits out a quiet period and reports them as if the close had just been seen; the commit then decides as for any close.
  - A file seen again while pending gets a new token in memory only, so a commit done for the older close leaves it pending.
  - The window left is between reading an event and appending its record: microseconds, not the quiet period.
  - **Replayed files are found by the replica's path first** (WP9 review). An inode opened by handle when its dentry isn't cached, as after a reboot, is disconnected, and `/proc/self/fd` can't name it. So the daemon opens the replica's path for the node and checks that it holds that `(ino, generation)`.
    - Failing that, it opens by handle, and uses the result only if it is connected below the data root.
    - A file that is gone (`ESTALE`, or no links left) is done.
    - Anything else is looked for again with a backoff (5 s doubling to 5 min, about an hour). For example, a file renamed while the daemon was down is found once the namespace sweep has moved its node.
    - A file still not found is left pending, with a warning, for the next start.
    - The detector reports every file it was given a token for, or tells the log it won't (deleted while quiet, moved out of the landing tree). None is skipped silently.
  - **The detector never waits on the commit pipeline** (WP9 review). It queues what it reports in memory and keeps reading and logging while the commit pipeline is busy; without that, closes would sit only in the kernel queue, which a reboot loses. Every queued file is in the log already.
    - A file reported again before its last report was handed over replaces it, so the queue holds at most one report per file.
    - At shutdown the hand-over to a full commit queue gives up at once. The detector then reads its group to the end and records what it finds.
  - **No second upload of a held write.**
    - When a commit is left to the upload outbox, its `-` record is made durable at once.
    - A detector close, or a replayed one, for a file whose upload the outbox still holds is not committed yet (WP9 re-review). It is deferred and stays pending in the log, and is looked at again once the outbox lets go: then it is either unchanged (nothing to do) or one commit.
    - The outbox's own re-check of the live file may commit the file first. A crash in between loses nothing, since the close is still pending.
    - An outbox op whose finish fails is kept, with its clone, and tried again with a doubling backoff (`[commit] outbox_finish_backoff_s`, 10 s). After `outbox_finish_attempts` failures (8: waits of 10 s doubling, about 21 minutes in all) it is forgotten and its file committed again from the live copy. That is safe because the file's close is still pending in the log.

  Why a log, not a comparison of each committed file's size, mtime, ctime and generation with the replica:
  - ctime moves on every rename, chmod, chown and ACL edit, so comparing it would upload unchanged files again as new versions.
  - Size and mtime alone miss a same-size overwrite that keeps its mtime (`cp -p`).
  - Hashing every file at start costs too much at 10^8 files.
  - The log has no false positives, and it also covers closes waiting in the commit queue behind a big upload.
- **A hard-link split or removal cut short** leaves `.omnifile-split-<pid>-<ino>` or `.omnifile-unlink-<pid>-<ino>`.
  - Such names are never committed, renamed or deleted in the catalog.
  - A pass removes one left by an earlier run where no bytes go with it: an extra link (`nlink >= 2`), or a split's copy the replica doesn't know.
  - The last link of a catalogued file is kept, with a warning.
- **Orphaned commit clones are removed at start** (`Core::remove_orphan_clones`): a clone in `.omni/commit` that no outbox upload names, left by a commit that stopped before its upload was journalled. The file it was taken from is committed again from the live copy.

Tests: `edge/crates/omnifile-edge/tests/lost_commit_linux.rs` (a close 1 s before a SIGKILL of the daemon process; files written while it was stopped, in a new folder too, each committed once, and not again after another restart; a file held open for write across the restart; a commit cut short after its create; the edge's own files; a close queued in the stored group while systemd restarts the daemon; an overwrite closed 1 s before a SIGKILL) and `omnifile-detect/tests/fanotify.rs` (a close queued while no detector reads the group).

## What the edge records and sends

- **The replica follows the disk at once.** A rename moves the node's catalog name and its on-disk name together, so the materialiser never moves the file back. A delete marks the node and its subtree deleted, so nothing puts them back.
- **Ops are queued in the replica's outbox** (`rename`, `unlink`, `setattr`) in the same transaction, naming nodes by their local id, never by path. A sender delivers them in order, in batches, with `op_id` = edge id and counter (idempotent at the service). An op waits while any node it names has no catalog id yet, for example a folder whose `create` hasn't been acknowledged. Ops resolve ids when they are sent, so a file renamed before its create was acknowledged gets its rename after it.
- **A create for something already gone** (a temporary file or folder removed before its create was acknowledged) is sent once more with its op id: if the service had made it and only the answer was lost, the node gets its catalog id and its unlink follows; otherwise it is dropped. A create whose folder will never be in the catalog is refused. Neither holds the queue.
- **A create refused while another node's rename or unlink frees that very name** (`rm a; cp x a`) is tried again later; what depends on it waits with it, and the ops behind it still go.
- **New folders:** each folder created in the catalog is reconciled at once, so `mkdir -p a/b/c` puts every level in, not only `a`.
- **Results:**
  - `applied` or `duplicate`: acknowledged. The node takes the returned `entity_version`, and the op's echo in the feed is skipped (its origin is this edge and op).
  - `conflict` (a name taken by another file, a folder moved under itself) or `rejected`: the op is marked `conflict` and a conflict row records it. The edge keeps the user's tree as it is (`edge-metadata.md` §7) and alerts. The service's answer wins in the catalog.
  - A network or service failure: the op stays queued and is sent again.
- **Feed events for a node with an op in flight are held** (a conflict row, as for a file with uncommitted writes). An edge's dataset is changed by that edge and the portal only, so this is rare. When the op is acknowledged after such a hold, the node's row is fetched again (a snapshot page of that one file), and its version isn't raised, so the fetched row, the next event or the daily digest brings what was held.
- **No `expected_entity_version` is sent.** For these changes the edge is the authority until acknowledged (`edge-metadata.md` §6); a portal change to the same file in the same seconds loses to the user's.

## Who did it (`actor`)

Ported from line B (PR #10: d981ee9, 81fa187) onto this design (2026-10-21). Every `rename`, `unlink`, `setattr` (owner) and folder `create` the edge sends names who made it, as `actor` (`control-api.md` §4.1): `{via, uid, sid, sec, proof, client_addr}`, or `{via: unknown}`. The version the op writes records it (`file_version.actor_*`, migration 0030), so a tombstone says who deleted the file, and the cutover report's `deleted_by` (`portal-api.md` §5.18) gives that user's `identity_id` and the service's proof.

The pass still decides *what* changed from the disk alone; *who* comes from hints (`edge/crates/omnifile-edge/src/actor.rs`), kept ten minutes and looked up when a pass queues an op, by the object's `(ino, generation)` first and then by `(directory, name)`:

- **NFS: `FSAL_OMNI`'s `NS_HINT`** (`fsal-socket.md` §5.4): mkdir, unlink, rmdir, rename and chown, each with the caller's uid, flavour and address. Ganesha makes every NFS change as one process, so only the FSAL can tell callers apart. The SID comes from winbind (`uid_to_sid`) when the op is queued. `sec=sys` is `claimed`, Kerberos `proven`; the service has the last word (decision 28).
- **SMB and local processes: the namespace watcher.** With `FAN_REPORT_NAME` and `FAN_REPORT_TARGET_FID` (Linux 5.17) each event also names its entry and carries the entry's own handle and the pid that made it. The daemon resolves the pid at once, while the process is there: the smbd session's user (`omnifile_identity::Resolver`, as for SMB recalls) or a local process's uid. A process gone before it is read (a short `mv`) is `unknown`.
- **Ganesha is known by its pid and binary, never its name** (line B review N2): a pid whose `/proc/<pid>/exe` is `[fsal] required_exe` (or, with no binary configured, a connected FSAL's peer pid) gets no watcher hint, so an NFS change is never put on Ganesha's own root uid.
- **Races with the hint.** A pass waits (up to 5 s) while the watcher is still resolving a batch's pids, and a new folder with no hint whose inode is under 3 s old is looked at once more a second later. A new folder is found by its own inode too, and a folder moved into place counts as made by whoever moved it: smbd makes folders under a temporary name (`.::TMPNAME:D:…`) and renames them (seen on the dev VM's Samba).
- **The daemon's own changes are never put on a person:** its pid is skipped, and they find the replica agreeing, so they send nothing.
- **`unknown`**: no hint fits. A change made while the daemon was down (the sweep at start finds it), one whose events were lost, an unresolved session, an older FSAL. Ops queued before this change carry no actor at all; the service records nothing for them.

## Safety rules (line B's review round, 81fa187)

All four were already this design's or are now: **(ino, generation) identity**; **tombstone only when the handle is stale** (`ESTALE`, or no links left: `Whereabouts::Gone`); **a node alive elsewhere is moved, never deleted**: its new directory is marked and that pass renames it, and a folder whose descendant is alive elsewhere waits (B parks such a node under a holding name; here the delete waits instead, with the same effect); and **renames before creates**: a pass that queued renames or deletes sends them before it creates its new folders, so `mv X Y; mkdir X` made while the daemon was down renames the catalog's `X` to `Y` first and then creates the new `X` (before, the create reached the service first, was refused as a taken name, and was only retried a minute later). A false delete matters: it reaches the cutover report, and a partner may then delete the real S3 object.

## Hard links (decision 42)

- **NFS:** `FSAL_OMNI` refuses `LINK` with `NFS3ERR_NOTSUPP` / `NFS4ERR_NOTSUPP`; nothing is linked.
- **SMB and local processes** bypass the FSAL, so the pass splits them. A name the replica doesn't hold whose inode is a known node still at its recorded place is a second name: the daemon gives it its own inode, a reflink copy (`FICLONE`, else a byte copy) with the same owner, mode, ACL and times, swapped in atomically (`RENAME_EXCHANGE`; a name a user replaced meanwhile is swapped back untouched), and hands it to the commit pipeline, which commits it as a separate file. Audited `namespace.hardlink_split`.
- A second name for a **placeholder whose bytes are not all local** can't be copied without a recall, and it can't stay either: it would share the managed inode outside the catalog, and survive a delete or rename of the catalogued name. So it is **removed**: moved aside to a temporary name, checked by handle to be that inode's other name (same inode and generation, still two links, not the catalogued name), then unlinked; audited `namespace.hardlink_removed`. The catalogued name, its marker and its bytes are never touched. If the check fails (the name was replaced meanwhile), what is there is put back and the folder is looked at again. (Codex review of #25: leaving it in place was a live, untracked alias.)
- Hints are used once (Codex review of #25): a hint matched to an op is consumed, and one noted before the change being attributed (the inode's ctime) is never used, so an op whose own hint was lost is `unknown`, not an earlier user's.
- A **new file given two names before either was committed** waits (5 s doubling, six times) for its first name's commit, then the other name is split; after the waits it is split anyway.
- No Samba VFS module of ours is involved (the GPL `vfs_omnifile_prevver` of decision 36 is for Previous Versions only): splitting after the fact covers SMB and local processes alike. Two names never share one catalog file.

## Not covered (yet)

- **Symlinks.** A new symlink isn't created in the catalog; rare on data shares. A hard link in a seeded or migrating source becomes separate files (decision 42).
- **A rename across shares** is a copy and a delete to the user's tools, which the edge then sees as such.
