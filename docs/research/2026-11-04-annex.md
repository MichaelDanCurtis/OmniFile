# Annex research: NAS change feeds, copiers and cloud-tiering formats

Raw findings behind `docs/design/annex.md`.

**Owner decision (2026-11-04, decision 51):** v1 treats ONTAP and PowerScale as generic NFS/SMB servers, with scans plus reconciliation. It uses no FPolicy, no partner programme, no ONTAP audit logs and no PowerScale changelists or audit events. The vendor findings below are kept for a possible later addition (design phase A5). Read on 2026-11-03 unless a line says otherwise. Page dates are the vendor's own (git comment dates in NetApp's sources, `updated_at` on Microsoft Learn, revision dates in Dell papers).

How the pages were read:

NetApp publishes the same pages as AsciiDoc in the public `NetAppDocs/ontap` repository, so those sources were read raw from `raw.githubusercontent.com/NetAppDocs/ontap/main/...`. - **[F]** marks a finding read in a vendor document. **[S]** marks a search-result summary or a community post that was not read in full. Treat [S] items as leads, not facts.

## 1. NetApp ONTAP

### 1.1 FPolicy

Pages:
- How FPolicy works with external servers: https://docs.netapp.com/us-en/ontap/nas-audit/fpolicy-external-fpolicy-servers-concept.html (last edit 2025-06-17)
- Node-to-server communication: https://docs.netapp.com/us-en/ontap/nas-audit/node-fpolicy-server-communication-process-concept.html (2025-06-17)
- External engine planning: https://docs.netapp.com/us-en/ontap/nas-audit/plan-fpolicy-external-engine-config-concept.html
- Event planning: https://docs.netapp.com/us-en/ontap/nas-audit/plan-fpolicy-event-config-concept.html (page date 2025-01-28)
- Policy planning: https://docs.netapp.com/us-en/ontap/nas-audit/plan-fpolicy-policy-config-concept.html
- Persistent stores: https://docs.netapp.com/us-en/ontap/nas-audit/persistent-stores.html (2025-06-17)
- Requirements and best practices: https://docs.netapp.com/us-en/ontap/nas-audit/requirements-best-practices-fpolicy-concept.html
- Configuration types: https://docs.netapp.com/us-en/ontap/nas-audit/fpolicy-config-types-concept.html

Findings:
- [F] FPolicy is a notification framework for "partner solutions". ONTAP connects **out** to an external FPolicy server over TCP, from every node that has a data LIF in the SVM, so a server sees several control channels per SVM. A keep-alive detects broken sessions (default 2 minutes).
- [F] Engine type: `synchronous` (the default) holds the client's request until the server answers allow or deny; `asynchronous` sends the notification and continues.
- [F] Mandatory screening (`-is-mandatory`, default `true`): when no server answers in time, `true` denies the client's operation and `false` allows it.
- [F] Engine format `xml`, or `protobuf` from ONTAP 9.15.1.
- [F] SSL: `no-auth`, `server-auth` or `mutual-auth`, with certificate CN, serial and CA.
- [F] Tunables include `max-server-reqs` (1–10,000, default 500 outstanding requests), cancel and abort timeouts, a status-request interval and a server-progress timeout that disconnects a slow server.
- [F] Protocols: SMB (`cifs`), `nfsv3`, `nfsv4`. NFSv4.1 operations from ONTAP 9.15.1.
- [F] Operations: close, create, create-dir, delete, delete_dir, getattr, link, lookup, open, read, write, rename, rename_dir, setattr, symlink.
- [F] Filters include `close-with-modification`, `close-without-modification`, `first-write`, `write-with-size-change`, `open-with-delete-intent`, `exclude-directory`, and setattr filters for owner, group, mode, mtime and DACL/SACL changes (DACL and SACL on SMB and NFSv4 only).
- [F] From ONTAP 9.13.1, `-monitor-fileop-failure` also reports operations denied by permissions.
- [F] A synchronous server may get a "privileged data access" channel: SMB only, through `ONTAP_ADMIN$`, under a Windows account saved in the configuration. Super-user status bypasses permission checks, breaks existing locks, and generates no FPolicy notifications.
- [F] **Persistent store:** from ONTAP 9.14.1, an SVM can keep FPolicy events in a persistent store volume, **for asynchronous non-mandatory policies only**. From 9.15.1 the volume is created automatically.
  - There is one store per SVM, shared by every partner's policy.
  - If the store fills, FPolicy drops new notifications, with EMS messages.
  - The store survives reboots and takeover/giveback; unprocessed events resume, with live events first.
  - "The partner application you use needs to support this feature."
- [F] NetApp recommends a low-latency private network between the cluster and the FPolicy server, dedicated resources for a virtual server, and partner sizing before enabling. FPolicy adds latency to SMB and NFS access in proportion to the server's response time.
- [S] **The wire protocol is not in ONTAP's public documentation.**
  - Community posts show an XML handshake (`NEGO_REQ` / `NEGO_RESP`, a `HandshakeResp` body, protocol version 3.0) framed with a 4-byte length.
  - A 2017-era community thread says FPolicy development material is restricted to approved partners: https://community.netapp.com/t5/Software-Development-Kit-SDK-and-API-Discussions/How-to-develop-an-external-FPolicy-Server/m-p/126681 (sign-in required, not read).
  - No public protobuf schema was found.

### 1.2 ONTAP native auditing (no partner needed)

Pages:
- Auditing process: https://docs.netapp.com/us-en/ontap/nas-audit/auditing-process-concept.html (2023-12-15)
- Log formats: https://docs.netapp.com/us-en/ontap/nas-audit/supported-audit-event-log-formats-concept.html
- NFS events audited: https://docs.netapp.com/us-en/ontap/nas-audit/file-directory-access-events-audited-reference.html
- Auditing UNIX-security files: https://docs.netapp.com/us-en/ontap/nas-audit/configure-auditing-unix-security-files-directories-task.html (2025-01-15)
- Planning (rotation): https://docs.netapp.com/us-en/ontap/nas-audit/plan-auditing-config-concept.html

Findings:
- [F] Records go first to binary staging files on each node, then a scheduled task consolidates and converts them to `EVTX` (the default) or `XML` files in a log directory inside the SVM's namespace.
- [F] Rotation is by size (default 100 MB), by schedule, or both.
- [F] **Auditing is guaranteed by default:** a client operation doesn't complete until its record is in the staging volume. If the record can't be committed, client operations are denied.
  - This is safe for us as a reader, but a full staging volume blocks the customer's users.
- [F] NFS events: READ, OPEN, CLOSE, READDIR, WRITE, SETATTR, CREATE, LINK, OPENATTR, REMOVE, GETATTR, VERIFY, NVERIFY, RENAME. To catch NFS renames reliably, put audit ACEs on directories.
- [F] Auditing needs audit ACLs: SACLs on NTFS-style files, and audit ACEs inside NFSv4 ACLs on UNIX-style files. On UNIX security style, NFSv4 discretionary and audit entries share one ACL, so editing it must not drop the existing entries.

### 1.4 FabricPool (ONTAP cloud tiering)

Pages:
- Tiering policies: https://docs.netapp.com/us-en/ontap/fabricpool/tiering-policies-concept.html
- Requirements: https://docs.netapp.com/us-en/ontap/fabricpool/requirements-concept.html (2026-06-08)
- Azure as cloud tier: https://docs.netapp.com/us-en/ontap/fabricpool/setup-azure-blob-storage-cloud-tier-task.html

Findings:
- [F] A daily scan finds cold **4 KB blocks**. Blocks from one volume are **concatenated into 4 MB objects** and moved to the cloud tier. ACLs, directory structure and metadata never leave the local tier.
- [F] On Azure, FabricPool supports only the Hot and Cool account tiers. It supports neither blob-level tiering nor the Archive tier. S3 Glacier Flexible Retrieval and Deep Archive are not supported.
- [F] With `auto`, random reads of cold blocks make them hot and write them back; sequential reads leave them in the cloud. With `all`, reads leave them cold. Non-NDMP backup reads over NFS or SMB "become hot" and can pull data back.

## 2. Dell PowerScale (OneFS)

### 2.1 Protocol auditing, CEE and syslog

Source: "File System Auditing with Dell EMC PowerScale and Dell EMC Common Event Enabler", H12428, revision July 2021 (covers OneFS 9.1): https://www.delltechnologies.com/asset/en-us/products/storage/industry-market/h12428-wp-best-practice-guide-isilon-file-system-auditing.pdf

Findings:
- [F] SMB, NFS and HDFS events are audited per access zone. Events are logged on the node that served the client, in binary files under `/ifs/.ifsvar/audit/logs`, which roll over at 1 GB and are compressed. Audit logs are not deleted unless purging is enabled (OneFS 9.1+, which deletes only events already forwarded).
- [F] The CEE forwarder sends each event by **HTTP PUT** to `http://FQDN:port/cee` (default port 12228). From OneFS 8.0.1, each node keeps 20 HTTP connections to up to 5 CEE servers.
- [F] Syslog forwarding of protocol events has existed since OneFS 7.1.1 (`--protocol-syslog-servers`).
- [F] **The forwarder keeps its position:** `isi audit progress view` shows the last event sent to CEE and to syslog, and the oldest unsent one. A forwarder enabled late sends everything since auditing began. `--cee-log-time` and `--syslog-log-time` move the start point. A consumer that is down loses nothing while the logs are kept.
- [F] From OneFS 8.2.0, events are granular and map 1:1 to CEE events: `create_file`, `create_directory`, `open_file_write`, `open_file_read`, `close_file_modified`, `close_file_unmodified`, `delete_file`, `delete_directory`, `rename_file`, `rename_directory`, `write_file`, `read_file`, `set_security_file`, `set_security_directory`, logon, logoff, tree_connect.
- [F] Requirements: OneFS 7.1+, an account with `ISI_PRIV_AUDIT`, CEE 6.6.0+.
- [F] CEE runs on Windows, configured in the registry. The PUT payload is XML (the paper shows a picture of it, not a schema).
- [S] OneFS 9.x syslog forwarding has TLS and certificate settings (search summary of Dell InfoHub "OneFS Protocol Auditing", page now redirected; not read).

### 2.2 Snapshot changelists (public API)

Sources:
- Dell's OneFS Python SDK (generated from the OneFS Platform API), v9_10_0 docs: https://github.com/Isilon/isilon_sdk_python/blob/HEAD/isilon_sdk/isilon_sdk/v9_10_0/docs/SnapshotChangelistsApi.md and `.../ChangelistEntry.md`. SDK versions 9.5 to 9.12 are present; the repository was last pushed 2026-04-29.
- [S] Dell "Data Protection with PowerScale SnapshotIQ: changelist job and snapshots": https://infohub.delltechnologies.com/en-au/l/data-protection-with-dell-powerscale-snapshotiq/changelist-job-and-snapshots
- [S] Commvault's use (needs OneFS 8.2.0+): https://documentation.commvault.com/2024/essential/faster_incremental_backups_of_dell_emc_isilon_powerscale_with_changelist.html
- [S] Permission anecdote (`isi_changelist_mod`, OneFS 8.2.2): https://www.dell.com/community/en/conversations/isilon/privilege-for-isichangelistmod/647f9410f4ccf8a8de646a63

Findings:
- [F] The `ChangelistCreate` job takes `older_snapid` and `newer_snapid` (and `retain_repstate`).
- [F] Results are read with `GET /platform/10/snapshot/changelists/{id}/entries`, paged with `limit` and `resume`.
- [F] Each entry has `path`, `lin`, `parent_lin`, `size`, `physical_size`, `uid`, `gid`, `file_type`, `change_types`, `atime`, `btime`, `ctime`, `mtime`, `user_flags` and optional changed byte regions (`diff_regions`).
- [S] SyncIQ and FSAnalyze use the same mechanism. Snapshots need the SnapshotIQ licence.

### 2.3 CloudPools (PowerScale cloud tiering)

Source: "PowerScale: CloudPools and Microsoft Azure", H17746.7, May 2023 (OneFS 9.4): https://www.dell.com/en-us/infohub/articles/powerscale-cloudpools-and-microsoft-azure-2 (first 100,000 characters read)

Findings:
- [F] An archived file leaves an **8 KB SmartLink (stub) file** on the cluster, holding a local cache and a map to its cloud objects.
- [F] File data is split into **2 MB chunks** (1 MB before OneFS 8.2.0), stored as cloud data objects (CDOs), plus cloud metadata objects (CMOs). Chunks may be zlib-compressed and AES-256-encrypted with keys kept by the cluster.
- [F] SmartLink files are "the sole means to access file data stored in Microsoft Azure". Only the Hot access tier is supported.

## 3. Generic NFS and SMB servers

- [F] SMB2 CHANGE_NOTIFY: a client asks to be told about changes in a directory, or with `SMB2_WATCH_TREE` its whole subtree. The completion filter covers names, size, last write, creation, attributes and security. MS-SMB2 §2.2.35 (`updated_at` 2026-01-14): https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/598f395a-e7a2-4cc8-afb3-ccb30dd2df7c
  - Overflow (STATUS_NOTIFY_ENUM_DIR, "rescan the directory") is from general knowledge, not read on this page.
- NFS has no change notification that Linux clients implement. NFSv4.1 directory delegations with notifications are in RFC 8881 but not in the Linux client. General knowledge, not re-read.
- Scan cost data point, from Storage Mover's own tests (§4):
  - an SMB source of 117 million 1 KB files took **21–23 hours just to scan**;
  - an NFS source of about 50 million items took 5 h 28 min end to end (about 2,860 items/s), with a 4-core agent.

## 4. Azure Storage Mover

Pages:
- Overview, supported pairs: https://learn.microsoft.com/en-us/azure/storage-mover/service-overview (ms.date 2025-10-17, updated 2026-05-05)
- Agent deployment: https://learn.microsoft.com/en-us/azure/storage-mover/agent-deploy (ms.date 2025-05-29)
- Agent registration, Private Link: https://learn.microsoft.com/en-us/azure/storage-mover/agent-register (updated 2026-02-13)
- Performance targets: https://learn.microsoft.com/en-us/azure/storage-mover/performance-targets (updated 2026-03-25)
- [S] Endpoint metadata for NFS → Blob: https://learn.microsoft.com/en-us/azure/storage-mover/endpoint-manage

Findings:
- [F] Supported pairs:
  - SMB 2.x/3.x → Azure file share, and → Blob container. Blob targets go through the ADLS Gen2 API set; FNS and HNS containers are supported.
  - Agentless SMB, which needs private connectivity and credentials in Key Vault.
  - NFS 3/4 → NFS Azure file share.
  - S3 → Blob.
  - The overview's table lists the NFS row twice as "Azure file share (NFS 4.1)". The same page's text and the performance page describe **NFS → Blob container** (folders become empty blobs carrying metadata), so NFS → Blob is still supported. The table looks like a doc error.
- [F] SMB sources keep timestamps, ACLs and attributes at Azure Files fidelity.
- [S] NFS → Blob keeps permissions and timestamps only as custom blob metadata (4 KiB cap), in Storage Mover's own names, not OmniFile's `file_owner` / `file_group` / `file_permissions`.
- [F] The agent is a VM image for **Hyper-V (Generation 1) or VMware only**. It needs 8–16 GiB RAM and 4–8 vCPU by item count (16 GiB / 8 vCPU for 100 million items) and at least 20 GiB of disk. Its documented network requirement is "**unrestricted internet connectivity**" (outbound 443 to the listed endpoints).
- [F] Private Link: migration data can go from the agent to the target account over Private Link. Control messages, progress telemetry and copy logs can't, and use the Storage Mover resource's public endpoint. Registration needs a Private Link Scope id when private networking is used.
- [F] Tested at 500 million namespace items. Runs are copy passes of a whole source path (convergent n-pass); only changed files and metadata move in later passes.
- From `migration-engine.md` §4 (read 2026-09-26): a job takes one source and one target subpath, Additive or Mirror, and no object list.

## 5. AWS DataSync (for a later S3 destination)

- NFS location: https://docs.aws.amazon.com/datasync/latest/userguide/create-nfs-location.html
  - [F] Needs an agent.
  - [F] A source export can be `ro,no_root_squash` for the agent, or `all_squash` with a known uid/gid.
  - [F] NFS 3, 4.0 and 4.1 (4.2 in Enhanced mode); the export must be reachable without Kerberos.
  - [F] NFSv4 ACLs aren't copied.
- Metadata copied: https://docs.aws.amazon.com/datasync/latest/userguide/metadata-copied.html
  - [F] NFS → S3 keeps mtime, atime (best effort), uid, gid and POSIX mode as S3 user metadata, File Gateway compatible.
  - [F] SMB → S3 keeps **no** Windows ACLs and applies default POSIX metadata (0644/0755, 65534).
