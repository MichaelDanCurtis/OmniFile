# WP21: tiering a blob with more than one reference

Branch `claude/tiering-shared-blobs`. No migration and no new privilege: the worker could already update these columns on `catalog.location`, and read `catalog.audit_log`.

## The bug

`api.data.commit_dedupe` makes a second file's location point at a blob that already has one. `worker.tiering._in_place` moved the blob with Set Blob Tier and updated only the mover's row.

## What the review said, checked

The review read the code and did not run it. These results come from running it at origin/main, on Postgres 17 and sim.

| Claim | Result |
|---|---|
| In-place layouts (`single_account`, WORM): B's row says `hot` while the blob is Archive | True. Reproduced. |
| B's reads fail and no recall is offered | True until the change feed catches up. `online_location` returned a location, so the edge would get a read credential, and sim refused the read (`NotRestored`). |
| It fails closed, with no data loss | True. |
| `two_account` is safe | True for Archive only. See below. |

Three things the review did not have:

- **The failure ends when the feed applies the record.** `changefeed_sync._locations` already matches every row of the blob. After one sync at origin/main, B's row said `archive` and a recall was needed. So the wrong row lasts for the feed's lag, or for as long as the feed is down. This was run on sim. The real change feed's fields are still unverified (`backends/azure/changefeed.py`).
- **`two_account` is wrong below Archive.** Archive is a copy, the shared original stays, and `delete_blob` answers `shared` and retires only A's row. That test passes at origin/main. But hot, cool and cold are in place on that layout too, so B's row was wrong after those moves. Reads still work, so nothing fails, but the tier and the minimum-duration clock were untrue.
- **The stale row could change the blob.** At origin/main, B's `hot` row made B's schedule move a blob that A had archived: Set Blob Tier to Cool, out of Archive, with the early-deletion fee. A's row kept saying `archive`.

## The fix (`worker/tiering.py`)

- **Every committed row of the blob is updated:** tier, native class, tier clock, and the one-way Smart flag. The match is the change feed's: backend, container, key and exactly this version id. Pending and deleting rows are left alone.
- **Rows in another dataset are treated the same.** Dedupe stays inside one dataset today, so none exist yet.
- **What the other file's owner sees:**
  - the file's `remote_tier` changes, through the existing trigger, and its edge gets the normal feed event;
  - the portal shows Archive and offers a recall;
  - the audit log has a `tier.move` row with `how: shared_blob` under that file's own dataset, naming no other file;
  - no Teams message is sent until someone reads the file, as with any archived file;
  - `archive_at` stays that file's own date, so it can be later than the day the blob was archived.
- **A class change that mints a version touches only the mover.** S3's is a CopyObject. The version B names keeps its class, so B's row was already true.
- **Movers of one blob take turns,** with a transaction-scoped advisory lock. Without it, worker 1 could set Cold, worker 2 set Cool and commit first, and worker 1 then write Cold over rows whose blob is Cool. A mover that finds the lock busy defers its message for 30 seconds rather than waiting, so its consumer's batch isn't held up.
- **With the lock held, a mover reads its row again.** If the blob is already at its target, it does nothing, and the tier clock keeps the real time. If the blob is now Archive, the move is refused and audited as `why: archived`. This applies the engine's existing rule ("Leaving Archive is a rehydrate, never a policy step") to a move queued before the blob archived. It decides nothing new.
- **Other references are not woken.** Their own schedule and pins come round when they do. Waking them would turn a single disagreement into a loop.

## The billing loop, and the guard

The first version of this PR understated the loop. Its review was right, and each finding was checked by running it.

**It needs one pin, not two.** Copy a file so it dedupes, pin the copy hot, then overwrite or delete the original. `sweep_versions` pushes the old version colder on every sweep and the pin pushes the blob back. It works with folder pins too. Run on sim, one sweep a minute:

| Case | Moves at origin/main | Moves with the row fix, no guard | Moves with the guard |
|---|---|---|---|
| 1 pin, 60 sweeps, `azure_worm` | 2 | 61 (30 fees) | 2 (0 fees; 1 on this blob, 1 on the new version's own blob) |
| 1 pin, 60 sweeps, `two_account` | 2 | 61 (30 fees) | 2 (0 fees; same) |
| 2 folder pins over 3 duplicate pairs, 20 sweeps | not run | 60 (30 fees) | 3 (0 fees) |
| 2 pins, 180 sweeps, feed every minute | 180 (90 fees) | 180 (90 fees) | 1 (0 fees) |
| 2 pins, 180 sweeps, feed every 3 minutes | 60 (30 fees) | 180 (90 fees) | 1 (0 fees) |
| 2 pins, 180 sweeps, feed every 5 minutes | 36 (18 fees) | 180 (90 fees) | 1 (0 fees) |
| 2 pins, 180 sweeps, feed every 15 minutes | 12 (6 fees) | 180 (90 fees) | 1 (0 fees) |
| 2 pins, 180 sweeps, feed down | 1, then stops | 180 (90 fees) | 1 (0 fees) |
| 2 pins, 5 days, a sweep every 10 minutes | not run | 720 (360 fees) | 9 (4 fees) |

So the row fix alone made the loop about lag-in-minutes times faster, and unbounded with the feed down. My "up to a few times faster" and "it needs two active pins" were wrong.

**Cost.** From `policy/prices/azure_blob.json` (LRS, marked `verify: true`), a 184 GB file leaving Cold costs $1.99 of early deletion and $5.52 of retrieval: about $7.51 a cycle, and $5,405 a day at 720 cycles. This reproduces the review's figure. Neither of us checked it against a real bill. With the guard it is about one cycle a day, so about $7.51 a day per looping blob until the owner decides.

**The guard (`_held_until`).** Before Set Blob Tier: a warmer move is held if the blob has another committed row and any of its rows changed tier in the last 24 hours (`SHARED_BLOB_WARMER_HOLD`). It uses the newest clock of all the blob's rows, because `commit_dedupe` leaves a new reference's clock empty.

**It picks no file, but it isn't neutral, and it doesn't honour a pin against a standing colder wish.** The guard limits the rate and doesn't look at which file asks. But only warmer moves wait, so the colder wish takes the blob back on the next sweep:
- Against a standing colder wish (a colder pin, or an old version `sweep_versions` keeps pushing), a hot pin isn't honoured in any useful sense. Over 3 days of ten-minute sweeps the blob was Hot on 2 of 432; over 5 days, on 4 of 720.
- Each cycle still bills about $7.51 per 184 GB at the repo's prices.
- The harm is cost, not latency: a Cold blob is online, so reads work.
- "At most a day late" holds only against a one-off move, such as one file's schedule step.

**What it doesn't touch, each tested:**
- a colder move, so an archive date is never held;
- a same-rank move: Smart to explicit Hot on day 0;
- a recall or rehydrate: those never come through `_in_place`, and the scheduler's filter leaves a pin on an archived file alone, so its recall starts at once;
- a blob with one committed row, even with a row on its way out: it moves back in the same tick, as before.

**A held move comes back by itself.** The message is acknowledged, not retried, and `next_action_at` is set to when the hold ends. At that time the scheduler decides afresh, so a pin released meanwhile moves nothing. Two more things were needed:
- `policy/scheduler.py`: the pinned candidates would otherwise queue a move on every sweep, whatever `next_action_at` says. They now skip a warmer pin on a shared blob that changed in the last day, once its hold has been reported.
- The wake is earlier if the file's archive date comes first, because colder moves aren't held.

**How it is reported.** The first time a blob is held, and at most once a day per blob, there is one each of:
- an audit row, `tier.move.refused` with `why: held_back_shared_blob`, `to`, `until`, `at` and the file's own `location_id`, under the file's own dataset. No other file is named;
- a counter, `omnifile.tier.held_back`, with `dataset_id` and `file_id`, which fires a new Azure Monitor rule, `tier-held-back` (`deploy/azure/modules/app-metrics.bicep`);
- a warning in the worker's log.

None of this needed a schema change. A new `reconcile_drift` kind would have needed one (its CHECK), so that was not used. A blob held every day shows up as one row a day: that is what a loop looks like.

**What the portal and API show for a held pin:**
- `Entry.move_hold`, new in `GET /v1/files`, on the list and the file: `{to, until}`, or null. `web/entries.py` computes it with the guard's own rule from the catalog: an active pin (the file's, or a folder's above it) warmer than the file's tier, another committed row on the blob, a tier change under a day old, and an active tiering policy on the dataset, since nothing moves without one. On the archive date it uses the file's exact archive time, as the engine does: before it, a pin without `override_archive` still wants its tier and the hold shows; after it, the date wins and it doesn't. It says nothing about the other rows but that there are some. No migration.
- While it is set, `next_action` and `next_action_at` are null. The stored label is `archive` (`next_action`'s CHECK has none for this), which read as "Moves to Archive on" tomorrow, and again each day.
- The file page: "Its move to Hot is held until 7 Nov: another file shares its storage, and that storage changed tier in the last day." The list: "Move to Hot held until 7 Nov".
- Activity, the live panel: "Tier move refused to hot" for the file. Settings, Alerts: a row, `tier-held-back`, firing with a count for the last day.
- Still open: the partner API's file shape (`routes_partner.py`) still gives the raw `next_action`, so it reads `archive` during a hold. It has no `move_hold`. Not changed: that API is a contract of its own.
- Reporting is per blob, so a second file held on the same blob the same day gets no audit row of its own, though its page shows the hold. In another dataset that would hide the alert from that dataset's owner. No such row exists today.

**Three limits left as they are:**
- `tier_held_back` fires inside the handler's transaction, not after it. The consumer has no after-commit hook and adding one isn't small. If the transaction then aborts, the audit row rolls back and the message comes back, so the alert can fire twice. It can't be missed.
- A deleted file leaves its location row committed, so another file on that blob stays held for up to a day after the deleted one was the only other reference.
- A hold can delay archiving by hours within the same date: the wake is that date's midnight, and if the file's exact archive time is later that day, the next look is the end of the hold.

## Product decision for the owner: which file's wish wins

Today there is one active policy per dataset and references stay inside a dataset, so files disagree through their dates and their pins:

| Case | What happens on an in-place layout |
|---|---|
| Same policy, A older than B | A's schedule takes the blob colder for B too, early. On `two_account`, this applies below Archive only. |
| A's archive date, B pinned hot | A wins, and B is archived against its pin. No fight, because the engine never moves a blob out of Archive. A stubbed B gets one recall for the pin. A resident B keeps its bytes on the edge. |
| A's schedule says Cold, B pinned hot | B's pin brings the blob back a day later, once. A isn't woken, so it stays Hot until A's next step. |
| A's old version, B pinned hot | A loop, limited by the guard to about one cycle a day. The blob is cold nearly all the time. |
| A pinned cold, B pinned hot | The same. |

**Recommendation: a file whose plan differs from the blob's other references gets its own copy first.** The server-side copy and read-back already exist for Archive (`_copy`, `verify`). Every file's schedule, pin and archive date then stay honest, the loop is gone rather than limited, and the cost is one more blob. If that is too much for now, the small stopgap is to refuse a pin that opposes an active pin on the same blob, in the portal, though that doesn't reach the one-pin case. Not built: both change who wins.

## The review's other findings

- **`FOR SHARE OF l` was wrong, as the review said.** A mover waiting on A's share lock wakes inside a READ COMMITTED statement whose snapshot can't see B's new row. **Fixed, because it was small:** `find_duplicate` takes the blob's advisory lock shared, without waiting, and reads the row again. If a move is running, the file uploads its own copy, which costs only that upload. If a dedupe is in flight, the mover goes back to the queue and sees the new row next time. PR #70's `Batch.adopt_placed` copies a location without this lock, so once #70 merges it has the same short window, and the feed corrects it.
- **Portal: confirmed and fixed.** A file archived by its sibling showed "Archived since" its own, possibly future, `archive_at`. `FileJourney.tsx` and `EntryBits.tsx` now use `tier_changed_at`, and say just "Archived" when there is no clock. The list used to fall through to "Archives <date>" when `archive_at` was empty; an archived file now always says Archived.
- **Lock order: my first fix was wrong, as the re-review found.** The feed takes a blob's rows, then their files through the update's trigger, and so do `delete_blob`, `_plan` and `_commit_copy`. My files-first order deadlocked with the feed, and `test_the_feed_and_a_mover_on_one_blob_cannot_deadlock` reproduces `DeadlockDetected` on that order. The mover now takes the blob's rows in `location_id` order, then its files in `file_id` order, then updates.
  - **What prevents two movers deadlocking:** on one blob, the blob's lock makes them take turns. On different blobs they hold different rows and can meet only on files, which they all take in one order before any trigger fires, even when two files share both blobs with their rows in opposite orders (`test_a_blobs_files_are_locked_in_file_order`).
  - **What can still deadlock:** a feed page keeps its file locks until the page commits, so a page that has written file A and then wants a row a mover holds, while that mover wants file A, is a cycle. It needs a file with versions on both blobs, in one page, at that moment. Postgres aborts one and the queue or the page retries it; a repeated Set Blob Tier is a no-op on Azure. Not provoked in a test.
- **A slow holder lost its message, and my first fix for it was worse.** The review's run reproduced with the old code: the second consumer read the message, the holder lost it, blob Cold, row hot, message requeued. I fixed that by locking the holder's queue row across the call, and the next review found that this was a regression: `FOR UPDATE` assigns a transaction id, and the edge feed's horizon is the oldest open id, so every edge's events stayed unread until the call ended. Reproduced: 1 id held during the call, and an event committed then wasn't readable. The lock is gone. What holds now:
  - **No transaction id across a provider call.** Everything `_in_place` does before `set_class` is a read, or the blob's advisory lock, which takes no id. `test_an_edge_reads_a_feed_event_committed_during_a_provider_call` checks that no session in the database holds an id during the call, and that an edge can read the event then. A write added before the call fails it too. The real horizon is cluster-wide, so another session on a shared server could fail this test, or hide the event for the wrong reason. The test works out the horizon from its own database's sessions, and keeps a session open in another database holding an id throughout, to show that can't move the result. The transaction stays open across the call, but it has no id and, between statements in READ COMMITTED, no snapshot.
  - **A visibility timeout with a reason, and my first choice cost too much.** I first set 4 h 15 min for every message. The re-review showed that a crash, or a deadlock, then hid the message that long, and the sweep skips a file while its message exists, so a pin's recall waited too. Now:
    - By default it is 5 minutes (`MOVE_VISIBILITY_SECONDS`), with a call bound of 4 minutes (`MOVE_CALL_TIMEOUT`), so a live holder's message isn't read again. Batch size is 1, or messages would use up their timeout waiting behind a slow call.
    - A copy can really run long. Every archive copy (`_copy`) does this, at any size, because Azure's Copy Blob into the archive account has no time promise at any size and `_wait_copy` waits up to 6 hours for it. An S3 class change does it above 1 GiB. Before the call it raises `queue.Extend`: the consumer commits a longer timeout (6 h 15 min) with `set_vt`, in its own transaction, then runs the handler again, bound 6 h 5 min. No transaction is left open and no id is held across the call (tested for both).
    - Why any size: a small copy past the 4-minute bound would fail, and the retry would start a copy over one still pending, which is assumed to get 409. That would be one dead letter per sweep while it stayed pending (RA-53 checks the assumption).
    - **The worst wait for a user's pin** when a worker dies: about 6 minutes (5 for the message, up to 1 for the next sweep). If it dies during that file's own archive copy, up to 6 h 15 min, for that file alone.
    - Heartbeating would have shortened that last case. It needs a second connection, which a handler doesn't have.
  - **If a holder outlives it anyway,** the second consumer finds the blob's lock held and defers the message with `set_vt`, promptly, with nothing deleted, and the holder's acknowledgement still works. `test_a_holder_outlasting_its_visibility_timeout_keeps_its_message` runs the review's scenario and ends with blob Cold, row cold, queue empty and one provider call. With `Retry` in place of `Defer` it fails. The stale batch's `Defer` no longer blocks behind the holder, since nothing locks that row.
  - **Another move of a busy blob** is deferred the same way, keeping its id and read count.
  - **At the bound:** after `max_reads` (20 looks, about 10 minutes), it isn't dead-lettered, because the holder is alive and nothing failed. The message is acknowledged and the file is looked at again in an hour (`BLOB_BUSY_HANDED_BACK`). The one bad case: a holder's own message reaching that bound. It needs a holder alive more than 15 minutes (or 6 h 25 min on a long copy), past its call's bound, so it would have to be stuck on a database lock. It would then lose the message and roll back, leaving blob and row apart until the hand-back's look an hour later runs the move again. The feed corrects it sooner on Azure.
  - **Provider timeouts.** The repo sets none of its own, but each SDK has defaults, read from the installed packages and not tried on a real network: Azure, 20 s to connect and 60 s to read, with retries; botocore, 60 s each, with `max_attempts` 5. Those bound one stalled request, not a whole call: an S3 copy of 184 GB is 368 such requests in a row. So `_in_place`, `_copy` and `_archive_copy` now wrap the call in `asyncio.wait_for`: 4 minutes, or 6 h 5 min for a copy. Past it, the move fails like any other: rolled back, the lock freed, backed off, then dead-lettered, which the `dead-letters` alert reports. An S3 object too big for 6 hours can't be moved this way. v1 doesn't tier in S3; if that changes, the path is a bound scaled to the object's size.
  - **A deadlock victim.** `DeadlockDetected` is an `OperationalError`, and those go up to the run loop, leaving the message hidden for its whole visibility timeout. Reproduced at 15,300 s under my first timeout. My first fix sent every `OperationalError` on a live connection to `_fail`, and the next review showed that was too wide: on `restores`, five of them dead-letter the message, the recall stays `requested`, a later sweep doesn't send it again and `api/recalls.py` joins without sending, so the user's recall sits for ever. Now:
    - Only a conflict between transactions (`DeadlockDetected`, `SerializationFailure`, `LockNotAvailable`) is treated specially. Everything else, `QueryCanceled` included, goes up, as on main.
    - A conflict backs off and isn't counted. `_back_off` sends the message again with a fresh read count and a delay that grows up to `backoff_max` (15 minutes), and leaves its failure count alone. So a conflict can never dead-letter a recall. A message that always conflicts retries for ever and shows in the queue-age alert.
    - The move's retry finds the row behind the blob, calls the provider again (a no-op on Azure) and records it, so they agree (`test_a_deadlock_victim_retries_soon_and_ends_in_agreement`).
  - **The same mistake elsewhere, not from this PR and not changed (L).** These take a row lock and then call a provider in one transaction, so they hold the feed's horizon for that call: `handle_restore` (`worker/recalls.py`, `RECALL_SQL`, then `head` and `restore`) and `handle_restore_budgeted`; `retention/worm_sync.delete_blob` (then `delete`); `changefeed_sync._sync_page` (the cursor, then `read_changes`). Read from the code, not run. Most are single quick calls, but none has a bound of its own.
- **Tests that can hang: confirmed, fixed.** `pytest-timeout` 2.4.0 (MIT) is in the dev group and the lockfile, with a row in `LICENSES.md`. The default is 300 s, on the test body only (`timeout_func_only`). The slowest test is `test_portal_api_contract`, at about 65 s idle and 69 s under load. Fixtures aren't covered, on purpose: with the host at a load of 55, Docker's disk stalled a `DROP DATABASE` in a session fixture past 300 s, and the timeout charged it to an unrelated test (`test_partitions`). So a hung fixture still hangs. The tests in this file also set `lock_timeout` on their connections. A test can only check that the default is set.

## Left open

- L: `commit_dedupe` doesn't copy `tier_changed_at` or `explicit_tier_set`. A new reference has no minimum-duration clock until the next move, so the portal's early-deletion warning is skipped for it. The guard already reads the blob's newest clock instead. The Smart flag does no harm: the one-way check also refuses anything not already `smart`.
- L: `_archive_copy` updates only its own row. Two references archived at once can share one copy, and the other's `secondary` row says `hot` until its own phase runs. That row isn't read, and its phase either finishes or drops the copy, so no primary row is ever untrue. Named, not changed.
- L: a B recall in `downloading` when A archives the blob holds a credential that now fails. Its fill fails and fails the recall (#52), and the next read gets a real recall. Read from the code, not tested.
