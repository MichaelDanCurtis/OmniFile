# WP27: no transaction id across a provider call in the migration engine

Branch `claude/migration-engine-feed`. No migration. No new privilege. No product decision needed. The constants are mine, and each is one line: `CALL_SECONDS`, `STAGE_SECONDS`, `UNSTAGE_PER_STEP`, `READ_SECONDS`, `READ_BYTES_PER_S`, `LEASE_BUSY_S`.

## The bug, run before fixing it

At origin/main (2bb29b5), `test_a_feed_event_during_a_staging_copy_can_be_read_at_once` ran the real `migrate` handler through the real consumer, with a provider that committed a change to a file during `copy_object` and then read the feed as an edge does:

```
AssertionError: [('copy_object', False)]
Seen(call='copy_object', ids=1, tables=frozenset({'file', 'location'}))
```

So the event could not be read during the call, and the worker held an id and read locks on `file` and `location`. It is the same test now, and it passes.

## The fix

A step is still one transaction of writes. What changed is when the calls happen. Each provider call goes through `migrate/calls.py`'s `provider`, which is `queue.outside` with a bound and `hide_for`:

1. The pass that asks rolls back (the handler's savepoint). The consumer commits nothing of it, and makes the call with no transaction open.
2. The step runs again from the top with the result in hand: `FOR UPDATE OF m`, fresh reads.
3. The last pass makes no call and does all the step's writes in one transaction.

So atomicity stays as it was: nothing is committed half way. The calls come first and the writes last, and everything the step decides on, except a call's own answer, is read after the last call. There are two exceptions, each its own commit: the listing, which was never safe as one transaction, and the answer to a call a retry would make again or pay for again (a Batch job, a staging copy, a staging run). The pass after such a call records it and ends the step. The review of 0507f31 found the first version lost those, below.

Tests and CLIs that pass no message run in place, in their own transaction, as before. That is why the existing tests pass without a change to what they assert.

## Each site: what the transaction protected, and what does now

| Site | What the transaction protected | What protects it now |
|---|---|---|
| `_start_run`: `running_run`, `ensure_job`, `start_run` | A second holder waited on the row and saw the run. A provider error left no state. | The prefix's **lease**. `start_run` looks for the job's running run before it touches the job, and follows it, so a crash after the start doesn't scan the prefix twice. The start time is when it was asked for, not the last pass's clock. A prefix cancelled during the call stays cancelled, and the run finishes, as section 9.1 says. |
| `_advance`: `run_status` | The status and what it decided commit together. | Re-read row; the tag names the run. Writes are in the last pass. |
| `_discover`: `list` | All pages and the state change in one transaction, which on 10^8 blobs is hours and outlives the 15-minute timeout. | A page a message, with the cursor in the next message, tied to the state and the run's start. `_record` skips what is on record. A crash goes back one page. |
| `_discover_keys`: `head` | Same as a step. | One call for all the keys. The list comes from `staging_run`, which the lease keeps still. |
| `plan_checksums`, `plan_wave`: CreateJob | "Job first, no row if it fails": kept. | The call returns what it asked for. The next pass records that and commits, whatever the catalog or the prefix's state says by then. The request token now includes a digest of the objects (below). A user's restore during the call: `ON CONFLICT DO NOTHING` on the open restore, as before. |
| `checksum_progress`, `wave_progress`: status, report | The job row's lock. | Lease, and the row is locked again on each pass. The tag names the job. |
| `stage`: `copy_object`, up to 10 | `staging_object`'s rows written with the copies. | The call returns what it copied. The next pass records each and commits, even if the file was deleted during the call: otherwise nothing would ever delete it. Bound of 6 h per step. |
| `staging_progress`: `run_status`, start | The `staging_run` row's lock. | Lease, and the same `start_run` as above. |
| `unstage`: `delete` | Row and delete together. | The call returns what it removed, and only those are marked. 100 per step within 230 s. The cutover waits on a query of what is left, below. The filter stays: only OmniFile's staging keys, never a source bucket. |
| `verify_copy`: bad copy's `delete` | The location's row lock. It did not stop another copy of the same key committing. | **The blob's advisory lock**, session level, the same lock `retention.delete_blob` takes. `_shared` is checked under it, and another copy of that key can't be marked verified or gone until the message ends. So this closes a small race main has too. |

### The cases you asked me to look at hardest

- **Cutover and verification.** `_count`, `_journal`, `_unstamped` and `_flip` are catalog queries in the last pass, so they run after every call the step makes. A file overwritten during a call goes back to `verifying` and isn't flipped: `test_a_file_overwritten_during_a_call_is_not_cut_over_on_its_old_copy`. `_flip` still requires a committed, verified copy of the current version, so nothing flips without its full CRC64 read (decision 24).
- **Decision 40.** No path writes to a source. `test_a_whole_migration_holds_no_id_across_any_call` checks the fake's log for writes to the source bucket across the whole run: none. A staging bucket registered as a source during a copy is left alone: `test_a_staging_bucket_that_becomes_a_source_during_a_copy_is_left_alone`. `S3Backend._writable` is still the last guard.
- **Held and WORM.** A hold placed during a call counts before the flip, and the prefix waits for its stamp: `test_a_hold_placed_during_a_call_waits_for_its_stamp`.
- **A recall joining a staged copy.** A second recall during the copy gets no second copy, one `staging_object`, and the file cuts over through that copy: `test_a_recall_joining_during_the_staging_copy_shares_it`.
- **A step run twice.**
  - **Two holders.** The lease is a session advisory lock, taken at the top of each pass. It survives the commit before each call, costs no id, and a crash frees it with the connection. A second holder raises `Defer`: its message stays, and shows again in 5 minutes. The consumer lets go of session locks at the end of every message, however it ended. Tested with a lapsed timeout and with a second message, 2 cases.
  - **Lapsed timeout.** Each call hides the message for its bound plus a minute, at least 15 minutes. `migrate` now reads one message at a time, since a second one read with an hours-long copy would lapse behind it.
  - **Storage Mover job started twice.** `running_run` (ARM's `latestJobRunName` and `latestJobRunStatus`, unverified on real Azure, on RA-14) finds it, for the prefix's job and the staging job. If the lost run has already ended, a new Additive run starts, which copies nothing new. An adopted run's real start is earlier than the recorded one: the journal gate is then stricter, and `_record`'s time check looser, with the CRC check as the guard.
  - **Batch job started twice.** The name is the request token. A crash with the catalog unchanged finds the same job, with no second `RestoreObject`.
  - **The catalog changed before the retry.** On main the token stayed the same over a different manifest. I expect S3 refuses that with `IdempotencyException` (unverified, on RW-18), which would retry for ever. The token now names the objects, so this is a second job.
  - **So a billable restore can be asked for twice in one case:** the worker or the database is lost in the moment between CreateJob's answer and the commit that follows it, and the catalog changes before the retry. A later call's error no longer does it, since the job is committed before any other call. S3 should refuse the overlap or extend it, with no second retrieval charge. That is from AWS's documentation as I recall it, not from a run, and it is on RW-18.

### Bounds

| Call | Bound | Past it |
|---|---|---|
| Status, list, CreateJob, deletes, heads | 240 s | A provider error: `Retry(60)` with `last_error`, as any other |
| A checksum report | 15 min | The same |
| A step's staging copies | 6 h in all | The object being copied is given up (`failed`, and deleted if it got there), and the prefix's next run copies it. One not reached goes in the next step. `S3Backend._copy` aborts the multipart upload when cancelled. |
| A copy's read-back | 1 h, or the file at 25 MiB/s if longer | A provider error |

## The review of 0507f31

Nothing blocking. Five findings and an ordering point, each reproduced first, with a test that failed before its fix (17 tests failed at 1c56a9a). No migration. Each constant is one line.

**1. A cutover stopped waiting after one failed delete.** It compared the count removed with the limit, so one failure, or running out of time, sent it to `cut_over` with the rest never tried. Reproduced: `cut_over`, b and c untried.

- `staging.drain_staging` decides on a query of what is left. The least tried go first, so a failing key can't starve the others. It uses `staging_object.attempts`, past any runs' attempts, so it survives a crash or a second message, and needs no column.
- Out of time counts as a try on the row being deleted, or a hung delete would hold the step on it.
- After 5 tries each, 5 minutes apart once only failures are left, the prefix cuts over. The row stays `failed` with its error, and `last_error` names the bucket.
- **The alert:** a new gauge and rule, `staging-left`, severity 3, which ends a week after the cutover, since nothing retries after one and an alert that can't clear stops being read. The console's health says attention for that prefix only. No attention item, since that means a new kind in the API and the portal: named here in case you want one.
- A running staging run is now closed only when the prefix really cuts over. The wait can end in a file changing and a return to `verifying`.

**2. A call's result was lost when a later call failed.** Reproduced: 2 jobs after a 503 and a new object, and 3 copies over 3 retries. `engine._put_on_record` is the next pass of the step: it records and commits, and nothing else runs in it.

**3. A cancel during a call dropped its result.** Reproduced: a job at S3 with 0 rows, a copy with no `staging_object`. `_put_on_record` runs before anything looks at the state, so this is the same fix, and it covers a staging run too. A window closing during a call: the same for a job. For a prefix's own run, the verifying branch skips the gate and the schedule once the run was started. A cancel during that start still stands, as section 9.1 of the design note says.

**A related bug this exposed, fixed:** `checksum_job_object` stops an object being asked about again, across migrations, so a job still `running` under a cancelled prefix (nobody reads its report) would leave those copies unverifiable under a later migration. Main has this for a cancel while a job runs. Recording during a cancel would have added a path into it. `plan_checksums` now ignores such a job.

**The same class, left, as on main:** a wave `running` under a cancelled prefix has nobody to run `wave_progress`. Restores that complete get their events. One whose task failed stays open for good, and blocks later waves for that object and any recall that joins it. Not small, since a cancelled prefix has no step. **Recommendation:** a sweep that closes open wave restores past `WAVE_WINDOW` for cancelled prefixes.

**4. `migrate_verify` read a batch of 10.** Now 1.

**5. A read-back past its bound retried silently for ever.** Now each error goes on the prefix's `last_error`, tries are counted in the message, a minute apart at first and an hour at most, and after 12 (about 6 hours through an outage, plus each read's own time; this said 7, which was wrong) it dead-letters, which fires the `dead-letters` alert. A copy that recovers clears only its own error. **The cost:** a provider outage over about 6 hours now dead-letters its copies, where main retried for ever, and someone must `resend` them. That is what `VERIFY_ERRORS` is for, and it is one constant. **Since then:** `wp27b.md` holds the last try through an outage, for up to 3 days, so that cost is gone.

**RA-14.** `start_run` now does the GET before the PUT, and a 404 means no run. Only a 404: another refusal is an error, so it can't pass for "no run" and start a second. On RA-14 as unverified.

**Two bugs of my own, found while fixing these:**

- A staging run ending and the next one starting in one pass: the pass that asked rolled back the end, so the record found the old run still open (`UniqueViolation`). A run's end now commits first, and the next starts in the next step.
- A shortcut for the started run at the top of the step skipped the rest of the pass, so `wave_progress`'s write was lost and a wave stayed `running`. The through-the-consumer run of `test_a_restore_wave_brings_archived_objects_in` caught it. The check is now where the run is decided.

## Teams and Graph: not fixed, and why

The 6 entries stay in `KNOWN`. It isn't small:

- `_send_card` mints a card's intents before the send and records them after it, per recipient, with writes between recipients. A rerun from the top would mint new tokens, so the card sent and the rows recorded must be carried through the call. That is the double-send protection the allow-list names.
- There are three entry points: `handle_recall`, `handle_identity_resolve`, and the `sweep_due` and `sync_group_directory` sweeps. Sweeps have no message, so `outside` doesn't apply to them.
- `resolve_identity` holds `FOR UPDATE SKIP LOCKED` as its own guard against a second resolver.

The stall is real: a reviewer's estimate is seconds, worst case tens of minutes. **My recommendation:** its own work package, one send per message, recording the send's result in a transaction after it. Until then a provider that hangs on a Teams send can delay ACL events for all edges. I didn't measure that.

## Left

- **`_count` still holds an id for its length.** `FOR UPDATE OF m` assigns the id, and `_count` runs under it once a minute per prefix. It isn't a provider call, so the guard doesn't see it. At 10^8 rows it could stall the feed for as long as the query takes. Not measured. A pass that makes calls runs it more than once.
- **One worker's `migrate` consumer is busy during a long copy.** Other prefixes' steps wait for another replica. Main was the same.
- `migrate`'s dead letters have no re-send (wp23, "Other queues").
- `Retry(60)` on a provider error has no limit in the engine, as on main.
- A version left in the staging bucket by a copy retried after a crash, if that bucket is versioned: only the last version is on record. Small, and main is the same.
