# WP11: the portal's Settings area and API clients

Branch `claude/portal-settings`. The owner's requests of 2026-11-04: an admin place for storage endpoints, Storage Mover and S3 credentials; "API" instead of a product name; every API recommendation with an owner who has access; API key setup in the admin settings; and, later that day, OmniFile-issued API keys beside Entra app identities.

## What's built

**Settings connect and check; they store no secret.** Azure is reached with managed identities and RBAC, AWS with web-identity federation (decision 43), Teams with the bot's managed identity. ArchiveAdmin, signed in, never an app. Every change is audited. The contract is `portal-api.md` §5.20 and §5.21, and the YAML.

- **Storage** (`settings/storage.py`). Lists backends with what uses them. Add and edit go through the admin CLI's own functions (`admin/backends.py`: `azure_row`, `s3_row`, `register`), merged from #37, so the page and the CLI refuse the same things. `register` gained an audit actor (`Actor`), so portal changes are audited as the person. There is no public option, and migration 0035's `backend_guard` refuses turning private networking off, or changing a kind, from any writer. `web` may now INSERT and UPDATE `catalog.backend` (`config`, `private_network`), with re-auth. Live checks: each account's blob name resolves to private addresses only (decision 22), the service identities hold Storage Blob Data Contributor or Owner, public network access is off, versioning and the change feed are on, and the live account is ZRS with Smart while the archive account isn't ZRS. For S3: the account is in the AWS settings, the S3 and STS interface endpoints resolve privately, and the last role test passed.
- **AWS** (`settings/aws.py`): the exact trust policy for a pasted role ARN (the account's OIDC provider for `https://sts.windows.net/<tenant>/`, `aud` the deployment's `api://` audience, `sub` the service identities). Test queues an `AssumeRoleWithWebIdentity` in the worker, which holds the trusted identity, and records only the role and expiry.
- **Identity** (`settings/identity.py`): tenant, client id, audiences, app roles and the groups holding them, admin consent and its link, and a "who am I" with checks. From Graph when `web` may read the app's role assignments; otherwise from who held each role at sign-ins.
- **Teams and email** (`settings/notify.py`): health from the catalog's notifications; the app package from `deploy/teams/build.sh` when `OMNIFILE_TEAMS_APP_PACKAGE` names it, else the build steps; test card and test email through the worker's notify path (`settings/worker_jobs.py`, queue `settings_test`), to the asker only.
- **Storage Mover** (`settings/mover.py`): the Storage Mover, agents and projects, read-only GETs through ARM at the engine's API version.
- **Prices and alerts**: the price-table routes, and the alert rules of `observability.md` §1 with the catalog's view where it has one (`settings/alerts.py`).
- **API clients** (`apiclients/`, migration 0035):
  - A token is accepted only from an application registered and enabled here (`403 client_not_registered`, `403 client_disabled`), with its roles cut to the client's scopes. The check is in `web/auth.py`, calling `apiclients/registry.py`.
  - Every client has an owner. Audit rows of its calls carry `details.api_client`. A proposal records the client and owner (`Proposal.api_client`), and is refused with `403 owner_lacks_access` unless the owner held ArchiveAdmin or DataSteward at a sign-in in the last 30 days, or owns a share of the dataset. Sign-in now records `identity.app_roles` for this.
  - Disable takes effect on the next call and needs no re-auth; enable, scopes and owner changes need re-auth. Revoke is for good.
  - **OmniFile API keys** (`apiclients/keys.py`): `ofk1.<16-hex id>.<32 random bytes>`, shown once, only the SHA-256 kept and compared in constant time, never in the idempotency store. 90 days by default, at most 365. Rotation keeps the old key for an overlap (7 days by default). Revoke is immediate. Accepted only as `Authorization: Bearer`; a key in a query string is refused; log lines are redacted (`RedactKeys` on the root handler; uvicorn now logs through it, `log_config=None`). The audit names only the key id; refusals are audited with the reason. Rate limits are per key. Last use (time and address) is shown per key. Entra stays the recommended path, and the page says so.
- **"API" naming**: the Proposals page shows "From: API · <client> · owner <name>"; `portal-api.md`'s user-facing text says API client.
- **Portal**: `portal/src/features/settings/**` (eight pages, the API client detail page with keys), mocks in `portal/src/mocks/settings.ts`, nav and routes.
- **Docs**: `portal-api.md` §2.2, §2.2.1, §5.20, §5.21, §7 and §10; `threat-model.md` T3 (registered clients, the new key credential, Settings).

## Deployment (`deploy/azure`)

- **Role:** a custom, read-only "OmniFile Settings Reader" (`modules/roles.bicep`), assigned to `web` on the resource group (`webSettingsReader` in `main.bicep`). Its actions: `storageAccounts/read` (SKU, public access, network rules), `storageAccounts/blobServices/read` (versioning, change feed), `roleAssignments/read` and `roleDefinitions/read` (whether the service identities hold their data roles), and `storageMovers/read`, `agents/read`, `projects/read`. No dataActions, so `web` still reads no blob, and no `listKeys`. Built-in Reader was not used: it reads every resource type in the group.
- **Environment** for `web`: `OMNIFILE_SETTINGS_PROBES=1`, the subscription and resource group, `OMNIFILE_SERVICE_PRINCIPAL_IDS` (worker, api, verifier), `OMNIFILE_AWS_WEB_IDENTITY_SUBJECTS` (worker and api, the two given AWS settings), the AWS settings, the Teams ids, the sender and the Storage Mover config, all the same values the worker gets. The Teams intent key is not passed. `OMNIFILE_TEAMS_APP_PACKAGE` isn't set: the zip is built on an admin workstation, and the page shows how.
- The storage RBAC check now accepts the deployment's custom data roles (OmniFile Blob Worker for the worker, OmniFile SAS Minter for api, Storage Blob Data Reader for the verifier), and reads role definitions at the account's scope, where the reader role reaches them.
- Tests (`service/tests/test_deploy_env.py`): `test_web_gets_what_its_settings_pages_read` and `test_web_reads_the_control_plane_only_and_no_data`. Both fail on main's Bicep. `deploy/azure/check.sh`: 29 ok, exit 0.

## The security review of #43 (at c24f019)

Four should-fix findings and one minor, each now with a test in `service/tests/apiclients/test_review43.py` that fails on c24f019:

1. **Self-approval through a minted key.** An ArchiveAdmin could own a client, mint a key, propose with it and approve alone. A proposal now records its client, owner and `key_id`. Its owner, the client's registrant and the key's maker get `403 self_approval`, and the catalog's `proposal_client_guard` refuses it too (SQLSTATE OF010).
2. **Approval checked nothing again.** Approval now refuses a disabled or revoked client (`client_disabled`) and an owner who can no longer see the dataset (`owner_lacks_access`). Revoking a client marks its pending proposals stale (`stale_reason: client_revoked`).
3. **Refused keys were unthrottled, one audit row each.** A per-address gate (`registry.KeyRefusals`: 20, then one a second) answers `429` before any catalog work. Refusal audits are aggregated, one row per address, reason and key per minute, with a `count`; unknown and malformed keys count as one key.
4. **`web` could write any backend row.** `web` has no INSERT or UPDATE on `catalog.backend` now. Settings, Storage writes through the owner-run `catalog.backend_register`: a person, always private, by name, audited. `backend_guard` holds these rules for every writer:
   - an app's session never writes a public row;
   - private networking never turns off, and a kind never changes;
   - under data, the locating keys never move (layout, accounts, container, account, region of S3, smart, worm), and buckets are never dropped.

   Two fixtures from #35 repointed a seeded backend under a dataset, and now set the trigger aside for that setup step. Threat model T6 records it.
5. **A percent-encoded key reached the access log.** uvicorn's access lines lose their query string, and any line holding a key decoded is written decoded with the key redacted.

## The re-review of #43 (at 071b190)

One should-fix and two minors, each with a test in `service/tests/apiclients/test_review43b.py` that fails on 071b190:

1. **Under data, any key could change through the portal** (`versioning: false`, `recall_container`). `backend_guard` now refuses any added, changed or removed key on a backend in use, except an allow-list: S3 buckets added (never dropped), an inventory rule, a display name, an Azure row's region. The CLI's `_change_under_data` uses the same list (`UNDER_DATA_MAY_CHANGE`, `UNDER_DATA_ADDITIVE`), and a test checks the SQL and Python lists agree. `admin/backends.py`'s docstring says so.
2. **`SET ROLE NONE` evaded the app check.** The guard also refuses a public row from a non-superuser login that may `SET ROLE` to an app's group role (`pg_has_role(session_user, …, 'SET')`).
3. **A valid key got 429 after junk from its address.** The key is parsed and looked up first, and only refusals count: from a throttled address a refused key gets 429 with no audit row, and a valid key gets in.
