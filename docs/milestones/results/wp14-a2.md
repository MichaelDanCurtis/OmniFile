## What writes to the filer, and how each path is gated

A2 adds exactly four write operations on a NAS. All of them live in one edge module, `annex/remover.rs`. No other code gets a writable handle. A2 replaces nothing on the NAS: overwrites arrive only with A3's placements.

| # | Operation | How it is done |
|---|---|---|
| W1 | Hide: rename `<name>` to `.omnifile-removing-<id>-<name>` in the same folder | `renameat2(dirfd, name, dirfd, hidden, RENAME_NOREPLACE)`, where `dirfd` is opened beneath the root with `openat2` (RESOLVE_BENEATH, NO_SYMLINKS, NO_XDEV) |
| W2 | Delete the hidden name after the grace period | `unlinkat(dirfd, hidden)`, only once `fstatat(dirfd, hidden)` shows the ticket's inode, size, mtime and nlink = 1 |
| W3 | Cancel: rename the hidden name back | `renameat2(..., RENAME_NOREPLACE)`. If the name has been taken in the meantime, the file stays hidden, a problem is raised for the Owners, and nothing is deleted |
| W4 | Write the pointer `<name>.omnifile.txt` after W2 | `openat(dirfd, …, O_CREAT \| O_EXCL \| O_NOFOLLOW)`, fixed text: where the file went and a portal link. It never overwrites; if the name exists, no pointer is written |

**Every one of the gates below must hold before W1 or W2. Each gate is checked again right before W2.**

1. **Mount.**
   - The scanner and the copier keep using the read-only mount, which is checked as in A1.
   - A second, read-write mount, with an account in `OmniFile-Annex-Remove`, exists only while removals are live: an active rule set with a removing rule, approved by an ArchiveAdmin, out of dry run, and not paused anywhere.
   - When that stops being true, the unit unmounts it. So a Copy annex, a dry-run annex or a paused annex has no writable path at all.
2. **A ticket from the service for each file.** The edge never decides a removal alone. The service issues a ticket (file, version, the expected size/mtime/ctime/file id, an expiry of minutes) only when all of these hold:
   - the annex and global switches allow it;
   - `dry_run_until` has passed;
   - the running rule set's removing rule was approved by an ArchiveAdmin, and that rule matches the file;
   - the file's current version is the one copied;
   - **the current version had an in-Azure read** (`azure_read_crc`) within the last 24 hours. A copy verified only by `upload_block_crc`, or read longer ago, is queued for a read, and the answer is "not yet";
   - no legal hold stands on the file or a folder above it (no WORM gate: WORM is a share's, and an annex's dataset has no share);
   - the rate and window allow it.

   Tickets are journalled in the catalog (`annex_removal`), so issuing one is audited and rate-limited in one place.
3. **The edge's own checks, before W1 and again before W2:**
   - a forced `statx` matches the ticket;
   - nlink = 1 (hard links are never removed, decision 42);
   - no alternate data streams, queried by ioctl. If the query fails, the file is not removed: fail closed;
   - the filer isn't flagged SnapLock/WORM, and an `EPERM` on W1 cancels the removal with reason `worm`;
   - the annex still has its ticket and isn't paused (the poll interval drops to seconds while removals run).
4. **In use.**
   - Over SMB, W1's rename is refused (sharing violation) while anyone holds the file open without `FILE_SHARE_DELETE`. That counts as "in use, try later".
   - Files opened with `FILE_SHARE_DELETE`, and every NFS file, are covered by the grace period: after W1, a change to the hidden file, or a rename back by a user, cancels the removal.
   - Open question 1 below asks whether this is enough.
5. **Two steps, journalled.**
   - `annex.db.removal` records each step before it is taken: `ticketed → hiding → hidden(at) → deleting → deleted → pointer → done`, or `cancelling → cancelled(why)`.
   - On a restart, the remover resumes from the journal. It finds a hidden name by inode, never deletes anything not at `hidden` with its grace passed and re-checked, and never deletes twice.
   - The service acknowledges every step (`removal_scheduled`, `renamed_for_removal`, `removed`, `removal_cancelled`, `skipped_in_use`), and each acknowledgement writes an audit row naming the file, version, CRC and rule.
6. **Dry run.**
   - Any rule set that adds or widens a removal gets `dry_run_until = approval + 7 days`.
   - During that time the service issues `would_remove` tickets. The edge runs gates 3 and 4 except the rename, without the read-write mount, and records `would_remove`.
   - The portal shows the would-remove list against the proposal's dry-run report.
7. **Pause.**
   - The per-annex switch and the global Settings switch both stop ticket issue at once.
   - The edge then takes no new W1 and no W2. Files already hidden stay hidden, and their grace restarts on resume.
   - "Pause and restore" runs W3 on all of them.
8. **Throttle:** 1,000 removals an hour per annex by default, plus an optional window. The service enforces it when issuing tickets, and the edge caps it locally too.

**Tests (A2.2 exit, on omnifile-acl with the A1 Samba and NFS servers).** Each of these must be refused or handled:
- a file changed between verification and W1, or during the grace period;
- a file open over SMB;
- a rename back during the grace period;
- a hard link;
- an alternate data stream;
- a paused annex, and a dry-run annex (no read-write mount exists);
- an expired ticket;
- a copy without a recent in-Azure read;
- a daemon killed before and after each of W1 to W4, which resumes and never deletes twice or unverified;
- a pointer that is never overwritten;
- and the NAS tree digest showing exactly the expected changes and nothing else.

## Decided (decision 59, 2026-11-04)

The owner answered both questions:

1. **The SMB in-use check:** the rename's own sharing check (W1 is refused while someone holds the file open without `FILE_SHARE_DELETE`), plus the 15-minute grace period. The edge gets no SMB client of its own.
2. **The end of the dry run:** removals never start by themselves. After the dry run, an ArchiveAdmin reviews what it would have removed and confirms, with a sign-in in the last few minutes (`require_recent_auth`). The confirmation is audited. The person who proposed the rule set, and anyone answerable for the app it came from, can't confirm it. So gate 6 above gains a step: a ticket is issued only after that confirmation.

## #57 review fixes

Each has a test that fails without it.

**Edge (the evaluator A2.2 relies on):**
- **Blocking: the glob matcher was exponential in `**`.** It is now memoised (pattern × path), and runs of `**` collapse. `rules::parse` enforces the limits itself: 200 rules, unique ids, 100 values per list, 512-character globs, 32 segments, at most 4 `**`, no `.`/`..`.
- **Blocking: the real run could remove more than the preview showed.** One function, `RuleSet::removal`, decides removals for both. It re-decides the arrival under the running rule set and never reads the rule id saved at arrival. A `changed` report no longer overwrites that id. `changed` rules can't remove, on either side.
- **Three-valued matching.** A condition that can't be read now is unknown. An unknown at or before the deciding rule leaves the file undecided: it isn't copied by a guess, isn't removed, and is counted apart (`undecided`, `removals.undecided`).
- **Blocking I/O off the async loop.** Previews and the age pass run on `spawn_blocking`, each with its own `annex.db` connection (`AnnexDb::reopen`). Previews have a 2-minute budget. The unit marks a run `running` before it starts and drops runs the service has replaced.
- **atime.** A preview reads no file. The copier sniffs the content type from its hash pass and caches it. The editor and `annex.md` §4.5 say that a real arrival's sniff moves atime.
- **Minors.**
  - Age rules refuse `policy`, `tag` and `keep_copy`.
  - Age-based removals wait while the edge's clock is more than 10 minutes from the service's `served_at` (in `GET annexes`). The check uses a monotonic clock since that response, so a jump between polls is caught too.

**Service and portal:**
- **Blocking: an Owner could widen removals.**
  - Every rule set that removes anything is an ArchiveAdmin's to approve.
  - A removing set that adds or widens a removal, or changes any `arrived`, `changed` or `age` rule, starts a fresh 7-day dry run.
  - Both are computed again in `decide()` against the running set.
- **Globs:** `**/**` is refused, and so are more than 4 `**` and more than 32 segments.
- **Counts leaked names.** Previews are ArchiveAdmins' and apps' only: an annex's folders carry the Owners' ACL, not the NAS's, so no folder check can stand in. Anyone else gets `403 role_required`, and `report_hidden` on a report. Capturing the NAS folder ACLs is what would reopen previews to Owners (`annex.md` §4.5). The approval card's diff also counts a reorder within a trigger.
- **The approval UI.** A proposal shows its rules (the flow), what it changes against the running set (`running_body`), and asks for a fresh dry run when it opens.
- **Unversioned approve.** `POST /v1/annexes/{id}/ruleset/approve` is gone; the Annex page points at the versioned approval. Every proposal moves the annex's ETag.
- **Unreachable rules** are found by subset (lists) and range (sizes, ages).
- **`policy` and `tag` are refused** until something applies them (A3).
- **Dry runs:** `running` with `taken_at`. A run not taken in 10 minutes, or not answered in 15, fails. A newer draft replaces the same person's older ones. Proposals' runs count toward the throttle of 20.
- **Found by the exit test:** taking a run and answering it shared one idempotency key, so the answer was replayed as "running". Each step now has its own key (`dry_run_key`, with a unit test; the exit test's dry-run checks failed without it).
- **Lanes, after merging main (#55 took 0039 and 0040, so this migration is now 0041):**

  - edge: Linux 252 passed with clippy clean; macOS workspace 504 passed;

  - The scans and the reconciliation don't take a hidden or removed file for a user's delete.

## #61 review fixes

Each has a test that fails without it. The exit test has a step where one can (R4b).

**Edge:**
- **Blocking: W2 could delete unverified bytes.** Right after W1, a forced `statx` journals the ctime its rename left, and W2's two gates compare it. A POSIX client can't set a ctime, so a same-size rewrite with its mtime put back is seen, and so is a reused inode. Over SMB, where a client can set the ChangeTime, the hidden file is read again before W2 and its CRC-64/NVME compared with the verified copy's (`expect.crc64`). Tests: `w2_sees_a_same_size_rewrite_with_its_mtime_put_back`, and exit step R4b on both NAS.
- **Files left hidden:**
  - The journal write is fatal before every write (`no_write_follows_a_journal_that_cant_be_written`).
  - A transient error retries with backoff; past 8 tries a hidden file goes back (W3), and a W3 that can't be done becomes `stuck`. A stuck file is reported (an owner problem, an `ALERT` log line) and tried again hourly. A taken name is `stuck` at once (`w3_tries_again_after_a_transient_error_and_raises_when_it_cant`, `w3_never_takes_a_name_back_from_someone_else`).
  - A folder renamed during the grace: the file is found by its hidden name and inode, and put back there (`a_folder_renamed_in_the_grace_is_followed_by_inode`).
  - Removals stopped for a reason other than a pause or the window: the read-write mount stays, or comes back, until every hidden file is put back (`when_removals_stop_hidden_files_go_back_and_a_pause_only_holds_them`).
- **W1 on NFS:** a plain `renameat` once the unique hidden name is checked absent. The original name is never unlinked (`w1_without_rename_flags_never_replaces_or_unlinks_the_original`).
- **W3** is `linkat` to the name, refused atomically on the server if the name exists, then `unlinkat` of the hidden name. Where a link is refused, it makes an empty placeholder at the name with `O_EXCL` (refused if the name exists) and renames the hidden name over it, so only its own placeholder is ever replaced. The exit test found the link refused over SMB: the Samba server's protected hard links refuse a link to another user's file. A crash between either pair of calls is finished on restart (`a_w3_cut_between_its_link_and_unlink_is_finished`, `w3_without_hard_links_goes_through_a_placeholder_and_never_replaces`). This also answers the cifs `RENAME_NOREPLACE` question: cifs checks the target in its own cache only and sends `ReplaceIfExists`, so W3 never renames onto a name it didn't just create.
- **Resume in `deleting`:** the original name's inode is checked before anything counts as deleted, and the silent `_ => false` loop is gone (`a_restart_in_deleting_with_the_file_renamed_back_never_counts_it_deleted`). An `ENOENT` on W2 is "deleted" only after the same check.
- **Tickets are matched by file id** (`tickets_are_matched_to_files_by_id_not_by_position`). Candidates carry the rule set version they were decided under, and a candidate from another version is decided again.
- **Minor:**
  - An empty stream answer fails closed.
  - No write while the read-only mount isn't `ST_RDONLY`, or shares a superblock with the read-write one (`no_write_while_the_mounts_arent_apart`).
  - The pointer escapes control characters in the path (`a_pointer_never_says_more_than_the_path`).
  - The sharing-violation claim above is corrected.

**Service:**
- **Blocking: reusing a removed file's name purged the only copy.** A new file where a removed one was is now a new version of the same catalog file (annex.md section 3.7). `_gone()` and the deleted-file retention never touch a `removed` or `removing` row (`test_a_new_file_where_a_removed_one_was_is_a_new_version`).
- **Tickets are bound to their rule set version:** a hide or delete under another running version is refused with `rule_set_changed`, and a candidate decided under another version gets "not yet" (`test_a_ticket_of_an_older_rule_set_is_never_deleted`).
- **Membership first:** the open-removal lookup is by annex and file (`test_another_annex_never_gets_a_ticket_for_this_annexs_file`).
- **The edge's cancel is recorded,** also after the service's own, and `stuck` is a state with a `removal_stuck` event and an alert (`test_the_edges_cancel_and_a_file_left_hidden_are_recorded`).
- **The grace is kept by the service:** a delete asked within `hidden_at + grace_minutes` is held (`grace`), and a pause or the window restart it (`test_the_service_keeps_the_grace_itself`).
- **Every gate on every ask:** a delete asked again in `deleting` is checked like the first.
- **Every step is audited,** holds included, with the verified CRC (`test_every_step_is_audited_with_the_verified_crc`).
- **The catalog's path, never the edge's** (`path_mismatch`; `test_the_catalogs_path_not_the_edges`).
- **The confirmation shows what the dry run would remove:** files, bytes and up to 20 sample paths. The button waits for them (portal test).
- **Minor:**
  - `removals.enabled` honours the ArchiveAdmin approval.
  - The WORM gate is dropped on purpose: WORM is a share's, and an annex's dataset has no share. The plan and the code say so.
  - The removals list is paged with a cursor.
  - A CRC mismatch on the read before a removal raises an `ALERT` and a `copy_mismatch` problem (`test_a_copy_that_reads_back_wrong_before_a_removal_is_raised`).
