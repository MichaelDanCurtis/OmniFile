## What is built

**Connect Azure** (Settings, Azure; design section 1).
- The ArchiveAdmin signs in to ARM with a delegated token: auth code + PKCE, through `web` as a confidential client (it already is one for sign-in), on a second redirect URI, `/auth/azure/callback`.
- The token lives for one request. The callback checks the cookie, the state, the nonce, and that the ID token's `oid` is the admin who started it. Then it does the operation and drops the token. No refresh token is asked for, and the PKCE verifier is deleted when the code is taken. A test checks no token is in the catalog.
- **List:** tenants, subscriptions and resource groups. Only the deployment's tenant can be chosen; the others say why.
- **Choose:** the subscription, the resource groups, and optionally a resource group for Storage Mover. This gives the plan: every role, its scope, the identity that gets it, and every action in it. Nothing is made yet.
- **Grant:** a second sign-in (`max_age=600`). The service checks the admin's rights on every scope, and makes nothing if any is missing. Then it PUTs custom roles and assignments. The ids follow from the scope (uuid5), so a rerun updates the same ones.
  - The roles: a read-only "OmniFile Discovery Reader" for `web` on each group, and an "OmniFile Mover Deployer" for the worker on the Storage Mover group.
  - They have no data actions, keys, deletes or authorization writes.
  - Each grant is audited and listed with Remove, which takes its own sign-in.
  - A grant that fails half-way keeps what it made, so that can be removed.
- **Discover:** `web`'s own identity reads storage accounts, VNets, private endpoints and storage movers, and marks which accounts are reachable privately.
- **Confirm:** audited. Only private accounts can be ticked (decision 22).

**Identity tab.** It now starts with plain-language steps: what Entra ID is for, what AD is for, and a done/to-do checklist. Everything it showed before is still below.

**Connect AWS** (Settings, AWS; section 2).
- **The template:** `deploy/aws/cloudformation/omnifile-connect.yaml`, with a byte-identical packaged copy. It makes:
  - the OIDC provider;
  - the service role, whose trust policy a test checks equals the one the page shows;
  - an explicit deny of every write on the sources (decision 40);
  - the Batch role, the ops bucket, the queue and the rule;
  - optionally, the interface endpoints.
- **Launch in AWS** is a quick-create link with the tenant, audience and identities filled in. The link needs the template in S3 (`awsConnectTemplateUrl`). Without it, the page offers the template for upload.
- **Fetch:** the worker assumes the new role with its web identity and only reads: buckets, versioning, EventBridge and the queue. The endpoints pass the operator settings' own rules first.
- **Fallback:** the stack's outputs pasted by hand, in four formats.
- **Confirm:** records the entry, checked by `AwsDeployment.from_mapping`. It shows the whole `OMNIFILE_AWS_ACCOUNTS` value to set as `awsAccounts`.
- The S3 backend still reads only operator settings (the M5 review's B1). That is why confirming doesn't write the account where the backend would use it (design 2.3).

**Storage Mover** (section 3).
- Deploy Storage Mover is offered once the worker holds its Mover Deployer grant. The worker then PUTs the mover and its project.
- The page shows:
  - the agent's download and registration steps;
  - the values to type at registration;
  - the agents live, read every 15 s, before `OMNIFILE_STORAGE_MOVER` is set;
  - the `storageMoverConfig` value.
- Decision 20 is unchanged.

**Scan source** (New migration; section 4). The scan uses the seed's own readers (listing or S3 Inventory). It reads one batch per queue message, shows progress, and is capped at 2,000,000 objects and 300 s by default.
- The result: prefixes, the storage-class mix, a Bulk restore estimate, objects over 10 GiB counted apart, and suggested waves.
  - The estimate uses waves of 100,000, AWS's stated hours, the shared 1,000 requests a second, and the S3 price table if one is set.
  - No time is promised for objects over 10 GiB.
- "Use this prefix" fills the wizard.
- A test over the in-memory S3 shows the scan sent only LIST calls.

**Contract and deployment.**
- `portal-api.md` §5.20, §7 (`dependency_failed`) and §10.
- `portal-api.yaml`: 15 operations and 15 schemas.
- Migration `0044_cloud_connect.sql`, with five tables and the `cloud_task` queue. `azure_connect_op` is `web`'s alone (`privileges.py`).
- `register.sh`: the second redirect URI, and ARM's `user_impersonation`, not admin-consented. Its golden transcripts are updated.
- `main.bicep`: `web` added to `OMNIFILE_SERVICE_PRINCIPAL_IDS` (the Storage checks skip it), and `awsConnectTemplateUrl`.

## Review of #64 (fixed on this branch)

The review found no escalation: the OAuth flow, the roles and the AWS trust are sound. It found these, each fixed with a test that fails without the fix. Each fix was undone in turn and its test seen to fail (`mutate.py` in the scratchpad, 7 mutants); the old template fails the template test too.

1. **Grants made with no audit row.** `grant_with` and `remove_with` caught only `ArmError`. A lost answer (a transport `ProbeError`) escaped after a role and an assignment were made in Azure, leaving them unrecorded and unremovable.
   - Both now catch it. Once an item's role definition exists, the item is recorded and audited (`uncertain: true`) and can be removed; removal treats a 404 as gone.
   - A removal keeps what it removed before the error.
   - Test: `test_a_lost_answer_mid_grant_still_records_and_audits_what_was_made`.
2. **The deny on source writes was a hand-picked list scoped to bucket ARNs,** so a write through an access point slipped past.
   - The service and Batch roles now deny `s3:Put*`, `s3:Delete*`, `s3:Replicate*`, `s3:Bypass*`, `s3:AbortMultipartUpload` and `s3:ObjectOwnerOverrideToBucketOwner`, with `NotResource` the ops bucket and its objects.
   - `s3:RestoreObject` is allowed explicitly (decision 40: OmniFile may always request restores).
   - The test checks the wildcard set, the `NotResource`, and that no allowed source action matches a denied pattern.
3. **Connect AWS couldn't finish without private networking.** An account defaults to private, so a public deployment's entry was refused for lacking endpoints. The entry and the fetch's candidate now carry the deployment's `private_network`. Test: `test_connect_aws_finishes_without_private_networking`.
4. **Discovery's "private" was too loose** (decision 22). It now needs all three:
   - `publicNetworkAccess` Disabled, or Deny with no IP or VNet rule;
   - an approved blob private endpoint (no status is not approved);
   - a `privatelink.blob` zone linked to the service's VNet. `main.bicep` now sets `OMNIFILE_SERVICE_VNET_ID`, and the Settings Reader may read DNS zones and their links.

   Test: `test_private_means_closed_approved_and_resolved_privately`. The portal shows a DNS column and the reason (`privateWhy.ts`, with its test).
5. **Minors:**
   - every ARN names its partition (`AWS::Partition`, or a three-way choice where CloudFormation can't substitute);
   - `ServiceSubjects` and `SourceBuckets` have per-value `AllowedPattern`s;
   - the interface endpoints have least-privilege policies;
   - the security group has no wide default: the portal fills in the service VNet's range (`OMNIFILE_SERVICE_VNET_CIDR`), and a template rule requires it;
   - the ops bucket is TLS-only;
   - the Batch role's trust has `aws:SourceAccount`.

   `cfn-lint` 1.34.2 is clean (run with `uvx`, not a project dependency).
