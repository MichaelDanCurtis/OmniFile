## What it does

With `overwrite_keep_version`, a file coming back to its own name in its original folder may replace the file there, when that file is exactly the annex's current, verified copy. Before A3.4 it always took a `-restored` name.

- **Where (decision 82):** only the file's own name in its original folder, on its own filer. Anywhere else a `-restored` name, and the placement's outcome says `overwrite_refused_not_origin`.
- **What (decision 83):** an older version may replace a file still on the NAS. `POST /v1/placements` now takes an older `version_id` for the origin of a present file when the rule says overwrite (the version already there is still `file_present`).
- **How (decision 84):** hide, wait the annex's grace period (the name is empty), place, delete. The rule builder says so.
- **Control (decision 85):** no new switch. A rule set's `replaces_on_nas` lists the rules that can do it, and the approval page marks them "Replaces files on the NAS".

## Changed from the plan

The plan's failure handling couldn't hold at R4: by then the new file has the name, so "put the old file back with W3, the new file takes a `-restored` name" would need a rename or unlink of the placed file, a new kind of NAS write. The coordinator decided (2026-11-11):

1. **`replace_delete_go` is asked at the end of R2,** with the W2 edge gates, before R3, and again before R4's delete. A refusal or a failed gate at R2 puts the old file back under its own name, and the new file takes a `-restored` name.
2. **A gate failing definitely at R4** (the hidden file changed, a second link, a definite refusal such as a legal hold set in that window): the old file goes back with W3, no-replace, under the first free `<name>-replaced-<UTC time>` (then `...Z-2`, up to 9 tries), the placement finishes (`replaced_old_kept`), and a Problem names both files. Nothing is deleted. Not `-restored`, which means a version someone asked for.
3. **The service unreachable, or an answer that isn't definite:** wait and retry by the existing rule; after the bound the placement is `stuck`, its reason naming the hidden file, asking hourly.
4. **W3 itself refused:** `stuck`, every byte kept.

The scanner treats a `-replaced-` file as an ordinary new file to copy.

One more, by the same principle, which the coordinator didn't rule on: **at R2, if a user made a file at the name in the grace,** the old file can't go back under its own name either, so it is kept aside the same way, and the new file takes a `-restored` name. The plan said it stays hidden and the placement is `stuck`.

## Built

- **Service** (`annex/replace.py`, `api/annex_placements.py`):
  - the replace gate, at the ticket and at each question: the target is the file's own place; the annex's file is present, its current version the copied one with its copied attributes; verified, read back in Azure within 24 hours (a read is queued, and the ticket waits up to 30 minutes, then goes without a replace: `overwrite_refused_azure_read_pending`); no legal hold; no open removal; no other placement replacing it. A file already holding the placed bytes is `same`, read back by the edge as `same_content`;
  - the ticket's `replace` (the file's expected attributes, its CRC and hidden name), and its names: an older version takes its own name only with a replace offered, or when the name is free and the rule says overwrite;
  - `replace_go` and `replace_delete_go` (phases `place` and `delete`), each checking every gate again, answering `hold` (paused, the grace, a read under way) or a definite refusal. A placement gate failing at `place` ends the placement, as at `go`; at `delete` it only refuses the replace, since the new file has its name;
  - the reports `replace_hidden`, `replace_put_back`, `replace_aside` (with a `replace_kept_aside` Problem) and `replaced`, recorded once, also after the placement ended; every question and report audited with the replaced version's id and CRC;
  - `done`: an older version under the file's own name becomes a new head version referencing the placed version's blob (no copy), the replaced one kept; a `restored_name` after a refused replace is stored as `overwrite_refused_<why>`;
  - a `left` for a hidden file is `rejected: placement_in_progress`; the loop breaker counts a replace as a return to the origin;
  - the web side: `file_present` relaxed for an older version with overwrite; `return-targets` says `replace_older`; a placement's `replace`; a rule set's `replaces_on_nas`;
  - migration 0060 and the `api` app's grants for its columns.
- **Edge** (`annex/placer/replace.rs`, part of the placer): R1 to R5 as above, reusing the remover's W1, W2 and W3 (now `pub(super)`) and the placer's P4. Each step journalled in `placement_replace` before it is taken; a restart finds the hidden file by name and inode. P7 (cleanup) first puts back any old file a placement hid, so a placement that ends any other way (a `go` refused after a restart, a cancel, an abandon) never leaves it hidden. The scanner and reconciliation skip `.omnifile-replacing-*` and don't report the departure of a file hidden for a replace. Debug crash points `place_replace_start`, `_hiding`, `_w1_taken`, `_hidden`, `_grace_passed`, `_deleting`, `_old_deleted`, `_putting_back`, `_putting_aside`, `_w3`.
- **Portal:** the rule builder's note when overwrite is chosen for a NAS; the approval page's "Replaces files on the NAS"; a placement's line "Replaced; the old content is version N" (or what happened instead).
- **Exit test:** stage `replace` (RP0 to RP7) on both test NAS.
- **Docs:** decisions 82 to 85, `AGENTS.md`'s Annex line, `annex.md` §4.6, `control-api.md` §4.8 and `portal-api.md`, both YAMLs.

## Not proven, and left

- **Real NAS:** ONTAP, PowerScale and Windows servers aren't tested. Whether their restore right includes deleting a user's file for the hide, and how an SMB open without `FILE_SHARE_DELETE` answers the rename (`EBUSY` is taken as "in use", as decision 59 has it for removals; the lab's Linux cifs client can't hold such an open), are real-site checks. Unit-tested only: the alternate-data-stream refusal over SMB (the exit test's Samba has none) and W3's placeholder path where a NAS refuses links.
- **A retired annex** stops its unit, so a file hidden for a replace at that moment stays hidden until its owners put it back; the service's retire event names the placement but not the hidden file.
- **An edge that loses `annex.db`** mid-replace doesn't know about a file it hid; the catalog keeps the hidden name (`replace_hidden_name`) for an owner to find.
- **The in-Azure read is queued at the first ticket ask,** not at the request: the web app has no grant to queue a verify, and giving it one wasn't worth it. A placement waiting for its recall from Archive is asked after the recall, so its replace may wait up to 30 more minutes for the read.
- **The portal** shows the replace on the placement ("Replaced; the old content is version N", or what happened instead). The file's own version history doesn't label the new head as a replace yet; its `edge_op_id` (`placement-<id>-replace`) says so.
- **The migration number:** 0060. It was 0059 until #96 merged first with its own 0059; renumbered when main was merged in.
