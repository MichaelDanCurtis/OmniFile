# WP16: a small deployment size, and what each resource costs

Branch `claude/deploy-small-profile`. Compile-only: nothing was deployed, and no what-if ran against a
subscription.

## What changed

- `deploy/azure/main.bicep` has a `deploymentSize` parameter, `small` or `standard` (the default). A
  `sizes` table sets, per size: the PostgreSQL server and storage, each app's CPU, memory and replicas,
  the verifier job's size, the log workspace's retention and daily cap, and how often the alerts run.
  `standard` is exactly the sizing before the parameter existed.
- The sized parameters (`postgresSkuName`, `postgresSkuTier`, `postgresStorageSizeGB`, `apiMinReplicas`,
  `apiMaxReplicas`, `workerMaxReplicas`, `logRetentionDays`, and the new `logDailyCapGb`) have no default
  now. Left out, they take the size's value; set, they override it.
- Two refusals at deployment, with a message that says what to change: `small` with a dedicated
  verifier profile, and high availability on any Burstable server (Burstable has none).
- `modules/monitoring.bicep` takes a daily cap (`workspaceCapping`, set only when there is one).
  `modules/app-metrics.bicep` takes the alerts' frequency (5 or 15 minutes; the window stays 15).
- `deploy/azure/small.bicepparam` and `standard.bicepparam` start each size; `small` sets `westus3`.
  `main.example.bicepparam` names `deploymentSize = 'standard'`. `test.bicepparam` is now `small` and
  drops the values the size gives (it had B2ms; it now gets B1ms).
- The guide: `OMNI_DEPLOYMENT_SIZE` in `omnifile.env` (`standard` or `small`; empty is standard) picks
  the size. `check-env.sh` checks it, `customer.bicepparam` passes it, and the sized test values are
  `null` for a client, so the size's own apply. Section 5 says what each size costs and gives up. The
  guide's lint now allows a null where main.bicep's parameter is nullable, and builds the parameters
  for a small site too. On that build it fails if any sized parameter is set, or if the size isn't
  small. Two new lint tests: a client literal overriding small, and a fixed size.
- `tests/real/harness/guidevalues.py` `TEST_VALUES` gets `OMNI_DEPLOYMENT_SIZE=small` (one line; the
  harness refuses an example name it has no value for). The golden transcripts are rewritten
  (`REAL_UPDATE_GOLDEN=1`).
- The service: `OMNIFILE_PG_POOL_MAX` (`catalog/connect.py` `pool_max`, 1 to 100) caps one replica's
  catalog connections. api, web and enrol size their `Catalog` pool by it (default 10, as before). The
  worker, when it is set, takes every connection from one shared pool of that size (`worker/pool.py`,
  `PooledConnect`; a connection's `close()` gives it back). Its queue consumers then hand theirs back
  after each batch. Unset, the worker is as before: a connection per queue, kept, and one per running
  sweep. main.bicep sets it at small only (api 4, web 4, enrol 2, worker 6).
- Review of #59, fixed:
  - **Blocking.** `Lease` only forwarded reads, so `conn.row_factory = dict_row` in
    `handle_recall_batch` stayed on the lease and every partner recall batch was dead-lettered with
    a TypeError when the pool was on. `Lease` now forwards writes too, and the pool resets a
    connection's row factory and autocommit when it comes back. `handle_recall_batch` now reads dict
    rows through `conn.cursor(row_factory=dict_row)` (`DictRows`) and never changes the shared
    connection. `tests/web/test_recall_batches.py` runs the worker's step both direct and through
    `PooledConnect`; both fail without the fix. `tests/pooled.py`
    (`OMNIFILE_TEST_WORKER_POOL=6`) runs the worker, retention, notify and recall-batch suites on
    the pool: 158 passed.
  - **Should-fix.** The worker's budget is split into lanes (`PooledConnect.lane`). Two of its 6
    are reserved for `restores`, `edge_instructions` and `notify`, which try the reserved pair
    first. Of the other 4, at most 2 go to the long holders: `verify`, `migrate`,
    `migrate_verify`, `snapshot_export`, `seed` and `reconcile`. With six long handlers holding
    their connection for 1.5 s, at most two hold one at once, and a priority and an ordinary queue
    are served at once. Without the lanes, all six hold one and the priority queue waits
    (`tests/worker/test_pool_lanes.py`).
  - **Minor.** On a B1ms, main.bicep fails the deployment when the apps could open more than 25
    connections, leaving a margin of 5 under 30. The count is the replicas times the pools, the
    worker's 37 without a budget, 2 per verifier execution (10 at once with the Event trigger,
    1 at small), and the short ones. This refuses standard on a B1ms, and small with raised
    replicas. `test-sizes.py` checks small's 25 and the refusals.
  - **Minor.** The workspace always gets its daily cap, `-1` for none, so small's 0.5 GB can't
    stay on after a move to standard.
- `deploy/azure/test-sizes.py`, run by `check.sh`: the compiled table, standard pinned to the old
  values, small's Consumption sizes and warm replicas, the guide's client values; and, with uv, the
  template evaluated with the service's ARM evaluator (`service/tests/test_deploy_env.py`): what each
  module is given at each size, an override winning, and both refusals. A mutation (standard api min
  2 to 1, small relay min 1 to 0) fails four of its checks.
- `docs/guide/lint/test_guide_lint.py`: its "client default differs" case used
  `postgresStorageSizeGB`, which has no default now; it uses `keyVaultSoftDeleteDays` instead.
- `deploy/azure/README.md` (parameters, the cost table) and the guide's section 5 (a sizing note).

| api | 1 vCPU / 2 GiB, 2 to 10 | 0.5 / 1 GiB, 1 to 2 |
| worker | 1 / 2 GiB, 1 to 4 | 0.5 / 1 GiB, 1 to 1 |

What no size changes: storage and the vault reached only through private endpoints, with public access
off and no fallback; the relay's environment as the only public one; one managed identity and one
database role per app; the three allow-lists required; api's TCP ingress with its own TLS (T5); the
HSM-backed CA key (premium vault).

How the figures are worked out:

- Container Apps: api and the worker are priced at the active rate all month (they poll the catalog
  and hold edge connections), the warm web, enrol and relay replicas at the idle rate, and small's
  scale-to-zero apps by an assumed use (web 2 hours a day, enrol 5 hours a month). The verifier runs
  2,920 times a month (every 15 minutes) for about 30 s each with an empty queue. If api and the
  worker were idle all month, small's apps would cost about $30 instead of $82.
- Log Analytics volumes are estimates: about 0.5 GB a day at standard, 0.2 at small. The first 5 GB
  a month are free per billing account, so another workspace may already use them.
- Container Apps is about 29% cheaper per vCPU-second in westus3 than in westus2 ($0.000024 against
  $0.000034, meter `2711ef08`); memory $0.000003 against $0.000004.

## What was checked

**PostgreSQL on Burstable.** Microsoft's pages (fetched 2026-11-04): Burstable has no zone-redundant or
same-zone high availability, no read replicas and no built-in PgBouncer ("Limits",
"Reliability in Azure Database for PostgreSQL"). Nothing there or in "Extensions considerations" limits
`pg_cron`, `pgcrypto`, `pg_trgm`, `btree_gist`, `pg_stat_statements` or `shared_preload_libraries` by
tier, and the Entra authentication page has no tier limit. PGMQ is plain SQL from our migrations, so the
tier doesn't matter to it. The template already sets everything else the same way at both sizes. So
B1ms runs the catalog as built, with two limits:

- **Connections.** B1ms allows 50, of which 15 are reserved: 35 for users ("Limits"). Before the
  pool setting, api, web and enrol each pooled up to 10 per replica, and the worker kept one per queue
  (13 queue jobs plus restores and edge instructions) and opened one per running sweep (22 of them):
  about 15 to 37 for the worker alone. With `OMNIFILE_PG_POOL_MAX`, small's sum at every app's
  maximum replicas is:

  | | replicas | pool | connections |
  |---|---|---|---|
  | api | 2 | 4 | 8 |
  | web | 1 | 4 | 4 |
  | enrol | 1 | 2 | 2 |
  | worker (every queue and sweep) | 1 | 6 | 6 |
  | verifier job (a lock and its queue) | 1 | | 2 |
  | short ones: api's start-up read per replica, web's Settings storage run | | | 3 |
  | **total** | | | **25** |

  That is at most 30, leaving 10 of B1ms's 35 for an administrator and the migrations.
  `test-sizes.py` checks the sum from the compiled table, and the env each app gets.
  `tests/worker/test_pool.py` shows the worker's budget holds. Six consumers share a pool of two:
  every message is handled, and Postgres never sees more than two of their connections. Without the
  pool, the same consumers hold six. When a deployment replaces an app's revision, its old and new
  replicas overlap for a moment. A connection refused then is retried: consumers and sweeps retry, and
  api and web answer 503. B2s (414 connections, $49.64 a month) is the next step:
  `postgresSkuName = 'Standard_B2s'`.
- **CPU.** A B1ms gets about a fifth of one vCore at baseline and bursts on credits. A long migration
  or a re-snapshot will be slow.

The server goes read-only when less than 5 GiB is free ("Storage"), so 32 GB holds about 27 GB of
catalog; storage autogrow is on at both sizes.

**Container Apps charges.** Both "Dedicated Plan Management" (`109e832e`) and "Environment Private
Endpoint" (`1563b6cf`) are $0.10 an hour in westus3, as are "Environment Management Hour" (`dc8f611b`)
and "Environment Planned Maintenance Hour" (`a2fd15f8`). Microsoft's billing page: the plan
management fee applies only when a dedicated workload profile is in the environment, and private
endpoints and planned maintenance on the environment bring the same charge on either plan. The
template uses workload-profile environments with the Consumption profile only, puts no private endpoint
on either environment (the internal one is VNet-injected with an internal load balancer) and sets no
planned maintenance. So neither size pays it, and small refuses a dedicated verifier profile. The
networking page says a workload-profile environment in your own VNet also bills one standard load
balancer, one egress public IP, and for an external environment one ingress public IP: $47.45 a month
for the two environments, at both sizes. The API also lists a free variant of the load-balancer
meter; which one these use shows only on a real bill (VERIFY).

**The relay stays at one warm replica.** Teams expects the bot to answer a card's `Action.Execute`
within seconds, and a scale-from-zero start (image, Python, the relay's first fetch of the Bot
Framework signing keys) is not measured and could take longer. Scale to zero would save about $5.91 a
month at 0.25 vCPU. It stays at min 1 until a real tenant shows a cold start answers in time
(`real-tenant-checks.md`).

**web and enrol scale to zero at small.** No background task runs in either (their lifespans only open
the catalog and the signer). api asks enrol for its server certificate in a loop with backoff
(`first_certificate`, up to 30 s between tries) and its startup probe allows about 5 minutes; the
worker retries the CRL upload; an edge or a browser retries. The cost is a cold start on the first call
after an idle spell. Two side effects: per-replica rate limits start over, and before phase 2's
`web-cursor-key` a new web replica makes its own cursor key.

**Private endpoints.** Three, at both sizes: the live account, the archive account and the vault.
PostgreSQL uses VNet integration, not an endpoint. The Azure Monitor private link scope is off. Each
WORM share adds one. None can go: storage and the vault have public access off.

**Key Vault.** Premium is needed for an HSM-backed key: on standard the key would be software. The CA
key is EC P-384, an "advanced" key type, so $5 a month, not the $1 of an RSA 2048 HSM key (the README
said $1). The signing keys of decisions 47 and 48 are OmniFile's own, in OmniFile's vault, not in a
client deployment. Decision 50's edge CA is this key. A standard vault with a software key would save
$5 and lose the HSM; both sizes keep premium.

**Others.** No container registry, NAT gateway, public IP, Front Door or Application Gateway is in the
Bicep; the public IPs and load balancers above are the environments' own.

## What can't go smaller without breaking a constraint or changing the design

- **The second environment** ($25.55 a month of load balancer and IPs, plus the relay's replica): the
  relay needs a public ingress, and an internal environment has none. Putting the relay somewhere
  else is the design decision in `deploy/azure/README.md`.
- **Two non-WORM storage accounts and their two endpoints** ($14.60): Smart tier needs ZRS, and
  Archive is refused on ZRS.
- **The vault's endpoint and the HSM key** ($12.30): no public fallback, and the CA key in an HSM.
- **api's and the worker's warm replicas** (about $79 at the active rate): the edges call api all the
  time, and a starting api first asks enrol for its server certificate, so a cold start would hold
  every edge for a minute or more; the worker polls the queues and runs the timed sweeps.
- **The relay's warm replica** ($5.91): see above.
- **PostgreSQL below B1ms**: B1ms is the smallest Flexible Server.
