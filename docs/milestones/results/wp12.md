# WP12: the New migration wizard

Branch `claude/portal-migration-wizard`. The owner asked how to start a new migration. Until now the Migrations page only listed them, and starting one took `POST /v1/sources` and then `POST /v1/migrations` through the API.

## What is built

**Portal** (`portal/src/features/migrations/`):
- The Migrations page has a **New migration** button for ArchiveAdmin. Its table now reads `/v1/migrations`, so it shows the switch-over mode and the excluded count, and each prefix links to its migration. A source with no migration has a **Start migration** link.
- **The wizard** (`/migrations/new`) asks five questions, each with its settings under More settings:
  1. **Source.** A list of kinds. For an S3 bucket, the admin picks a backend an ArchiveAdmin configured, then a bucket, with an optional prefix. The inventory (automatic, S3 Inventory, S3 Metadata tables, listing) is under More settings. Annex (an existing NFS or SMB share, WP10) is listed as coming soon. Adding it means adding a kind and its questions, with no redesign.
  2. **Destination.** An existing dataset, or a new one made through `POST /v1/datasets`, and the Azure storage it lives on. The folder in the dataset, and a new dataset's layout and key prefix, are under More settings.
  3. **Access.** The Owners, Writers and Readers AD groups. All three are required, because S3 objects carry no ACLs (`access-control.md`).
  4. **How.** The copier (Azure Storage Mover by default, or an external copier through the API) and the switch-over (automatic or manual). Two notes explain that nothing switches until every file is verified (decision 24) and that new writes go to Azure while the dataset migrates (decision 14). The mode is under More settings, where hand-off shows as not offered yet.
  5. **Review.** What will happen, and notes on what AWS bills: restores, the temporary restored copy, and data transfer out. There are no figures, because the service has no S3 price table. Before the source is registered the API has no counts to give. Once seeding starts, the next screen shows the source's counts.
- **Start** calls `POST /v1/datasets` if a new dataset was chosen, then `POST /v1/sources`. It puts `?source=<id>` in the URL, polls the source until it is `seeded`, and then calls `POST /v1/migrations`, which refuses a source that is still seeding. Each call gets its own Idempotency-Key from the client. If the migration call fails, the source is kept, and the page offers Try again. A dataset the wizard made is reused when the source is refused, so it is never made twice. The wizard can be resumed from the Migrations page, and the how-choices are kept per source in localStorage.
- **The migration page** (`/migrations/:id`) shows the lifecycle (pending, copying, verifying, verified, cut over; a failed or cancelled migration is marked where it stopped). It shows the file counts (total, verified, failed, excluded), the copier and its last run, the details, and the cutover report. Its actions:
  - **Cut over**, for a manual migration once it is verified;
  - **Cancel**, after a confirmation;
  - **Retry**, for a failed migration;
  - **Exclude objects**: keys and a reason. The API requires a recent sign-in for this, and the page shows "Sign in again" when it is needed.
- **Naming.** User-facing text says "API" for an external copier, never a product name. `MigrationsPage.tsx:101` is fixed, and the tests check that no page text says Prizmanyx.

**Service** (two routes, minimal):
- `GET /v1/source-backends` (`routes_sources.py`; ArchiveAdmin, session only) lists each S3 backend with its region, `private_network`, `buckets` and `metadata_tables`. Buckets leave out OmniFile's operations buckets; `null` means the backend takes any bucket. It never returns endpoints, roles or credentials. `GET /v1/backends` has no bucket list, and the wizard needs one. Registering the route took one line in `web/app.py`, which is outside the owned globs.
- `GET /v1/migrations/{id}/tombstones` now also answers a signed-in ArchiveAdmin. That admin sees only the rows naming files they could read: the file and every folder above it, as in a listing, because roles never grant read (§3.2). `source_deletes_pending` still counts every row. Before this, a session got `403`, so the portal could show only the count.
- The YAML, contract §5.10, §5.18 and §10, and the generated `schema.gen.ts` and `examples.gen.ts` are updated.

**Mocks** (`portal/src/mocks/migrations.ts`). The mock has source backends, sources and migrations. A source or migration made in the mock moves one step each time it is read, so `dev:mock` shows progress and the tests stay deterministic. The first mock dataset is now `migrating`, which matches its sources.

  - the app that started the migration;

## The migrations console (follow-up package, branch `claude/portal-migration-console`)

The owner (2026-11-04) asked for a console that shows each migration's status and the agents doing the work, lets an admin fix problems from there, and plans staged migrations on a schedule. The contract is §5.22 of `portal-api.md`, with migration 0037.

- **Overview.** The Migrations page is now the console. It has one row per migration:
  - phase;
  - files and bytes verified, out of the total;
  - failed and excluded counts;
  - the last hour's throughput;
  - an ETA and its basis;
  - a health badge and the next wave.

  The ETA is null, with the reason, when nothing was verified in the last hour, or while objects are still in an S3 archive class without a finished restore.
- **Drill-down.** A row expands to the Storage Mover job, its last run and the agents; the edge, from its heartbeat; restore waves, with counts and the first expiry; checksum jobs; and verification. `web` reads only the catalog. The worker lists the Storage Mover agents through ARM every 5 minutes into `catalog.mover_agent`. A cloud-to-cloud S3 job runs without an agent, and the page says so. A new Agents view shows every agent and every job under way, with where it runs.
- **Needs attention.** Each problem has its fix in place, and every fix is audited:
  - copies that failed their check: **Copy again** (`rerun_requested_at`: the engine starts a new Additive run at its next step), or **Exclude**, which opens the existing re-auth dialog;
  - a failed run: Copy again;
  - restored copies about to expire: **Restore again** (`restore_requested_at`: the next restore wave renews copies that expire within 24 h);
  - a stopped migration: Retry;
  - an access or private-endpoint error: a link to Settings;
  - an agent offline: the Agents view;
  - a source still being catalogued: wait.
- **Plans.** Tables `migration_plan`, `migration_wave` and `migration_wave_prefix`.
  - A plan's waves come from a source, split by size or by file count (`GET /v1/migration-plans/split`).
  - Each wave has a start, a daily window in UTC, blackouts, an optional "after wave N is verified", a cutover mode and a copier.
  - An ArchiveAdmin's plan is approved at once. An API client's is a proposal, with a named owner in the source's Owners or Writers group, which another ArchiveAdmin approves.
- **Scheduler.** It runs every minute in the worker (`migrate/plans.py`). It starts a wave on time, inside its window, outside its blackouts, after its dependency, and once its sources are catalogued.
  - The engine holds the wave's migrations at `verified`. The scheduler asks for each cutover only for verified migrations, inside the window. The engine counts again and flips nothing unverified (decision 24).
  - A wave starts in one transaction, so a crash leaves it whole.
  - Bandwidth and egress caps are advisory, and the page says so. Starts, windows, blackouts and dependencies are enforced.
- **Schedule view.** A Gantt chart of the waves: planned start handles, actual runs, verified and cutover marks, blackouts, and now.
  - A handle moves by pointer drag, or by keyboard: arrows move an hour, Shift a day, and Home and End go to the limits its dependencies set. Each move is held until Save.
  - A typed date and time is the other way to move a wave.
  - The server checks dependencies, windows and the plan's version again (`PATCH .../waves/{seq}`).
- **Starting while the source is still catalogued** (the L item above). When the source isn't catalogued yet, the wizard hands the start to the scheduler as a one-wave plan, so the migration starts even if the page is closed. If the plan can't be made, the page falls back to starting it itself.
- **Placeholders.** `0035_reserved_wp11.sql` and `0036_reserved_wp13.sql` hold the numbers of #43 and WP13, because migrations must run without gaps. Delete each one when merging the real file in.

Review of #45 (at 014cb2b): 6 should-fix and 3 minor findings, all fixed. Each has a test that fails without its fix; 13 of the new tests fail against the code before the fixes.
1. **Wave migrations belong to the plan.** They are now made with `requested_by` `system:plans`, and each carries `plan: {plan_id, seq}`. Their own cutover, cancel and retry routes answer 409, and the app that proposed the plan gets 404. The plan has new routes, `POST …/waves/{seq}/retry` and `…/cancel`, and the migration's page now links to its plan.
2. **A wave whose migrations were all cancelled** is now `cancelled`, not `verified`. A wave that waits for it is `blocked` (a new state) and never starts; the plan stays open and shows it.
3. **Waves of a cancelled plan that had started** are still followed, so an `auto` wave still cuts over inside its window. A `failed` wave goes back to `started` once none of its migrations is failed.
4. **Windows and blackouts** now gate the engine's new Storage Mover runs and new restore waves for a wave's migrations (`migrate/windows.py`). When a migration leaves `verified`, the sweep's cutover request is dropped. Migration 0037's comment, §5.22 and the page list exactly what is gated and what isn't.
5. **`split` and folder names.** A signed-in caller sees only folder names they can read; the rest are counted in `hidden` and left out of the waves. An app needs its client's owner to see the dataset.
6. **Console load.** The console now reads counters on the migration row and samples in `catalog.migration_progress`. The worker computes them every 5 minutes (`migrate/progress.py`), so a console read no longer scans objects. Throughput is the difference between two samples taken at least 10 minutes apart.
7. **Failure count.** A new `failing_now` gives the copies that failed their check and still have no verified copy. Copy again is refused while the migration is verified, and the toast text now mentions the wave window.
8. **Time zones.** Plan times are UTC everywhere: inputs, schedule text and `aria-valuetext`.
9. **Tests and paging.** The `or True` is gone, `renew_expiring` has a test, and the agents list follows ARM's `nextLink`, only on ARM, so the token never goes elsewhere.

### Re-review of #45

The re-review found 2 should-fix and 2 minor issues. All four are fixed, each with a test that fails without its fix.
1. **Finished migrations were recounted forever.** The count used `bump_version`, which moved `updated_at` past `progress_at`, so every sweep picked the row up again. The counters now live in their own table, `catalog.migration_count`, with the state they were counted at. A count never touches the migration's row. A cut-over or cancelled migration is counted once more after it finishes, then left. The test uses real database time.
2. **Blocked waves were a dead end.** PATCH now accepts a blocked wave: changing or dropping `after` puts it back to planned. Plan cancel includes blocked waves, and a wave after a blocked one is blocked too. The plan page has a "Don't wait for wave N" button on a blocked wave.
3. **External copiers in plans.** These are refused with a 422 `action_not_allowed` that says to use `POST /v1/migrations` instead. A plan can't receive an external copier's run reports yet.
4. **`failing_now` clears.** A new test shows the attention item goes away once the failed file has a verified copy.
