# WP26: a file whose plan differs gets its own copy (decision 66)

Branch `claude/shared-blob-own-copy`, #77. No migration, no new privilege and no new dependency. One new Azure Monitor rule, `tier-archive-late`.

## The rule: when two files want the same tier

A move of a shared blob asks every other file on it. The answer comes from the same engine that plans a file's own moves (`engine.same_tier_wanted`), reading each file's schedule, pin and archive date.

**They want the same tier when the other file's own plan has it in that tier now.** For a colder move, also when it has no pin in force and:

- **the tier is Cool or Cold, and its schedule gets there within 7 days.** It goes up to 7 days early;
- **the tier is Archive, and its archive date is today (UTC).** A file is never archived on a date before its own.

Everything else differs. In particular:

- A pin says what it wants now, however soon it ends.
- A warmer move has no window. The schedule never warms a file, so only a pin to that same tier agrees.
- A file that wants a tier colder than the mover's, right now, differs. Each then moves on its own from the warmer tier, with no retrieval.
- A file with no tiering policy, or a broken one, has no plan, so it never causes a copy.
- A superseded version, or a deleted file's last version, has the schedule from its commit, colder only, as `sweep_versions` moves it.

**Why these numbers.** The only cost of moving a file up to 7 days early to Cool or Cold is a dearer read on a file that is still online. The cost of a copy is a blob for good. Going early beats waiting, too: waiting would make the older file's dates untrue, and an archive date is always respected. Archive differs because it takes the file offline, so there the window is the file's own date, which is how the catalog stores it (`file.archive_at`). A move is never put off to agree with another file's plan. It can wait for a split of its blob that is already running: see "While a split runs".

**It doesn't need a product decision,** so I didn't stop. Both numbers are one constant or one line in `engine.py` if the owner wants them otherwise. The one thing to know: two copies of a file made a day apart on an in-place layout split on the older one's archive date. That costs one retrieval out of Cold and a second Archive blob, about $5.52 once and $0.18 a month per 184 GB at the repo's prices, so that neither file is archived early. A window of a few days there would save that and take a file offline early. I recommend leaving it as built.

## Which side copies

**The file that is moving copies. The files that stay keep the original.**

Staying costs nothing: the blob, its tier and its minimum-duration clock don't change. Leaving costs one read of the blob's tier. So **a split bills no early deletion while another file stays on the blob**, whichever way the wishes point, and a copy of Hot or Smart is free to read.

Two limits on that:

- **Everyone else leaves during the copy.** The swap's `delete_blob` then removes the old blob, which bills an early deletion if the blob is under its minimum. Moving it in place would have billed the same, so this costs the wasted copy, not the fee. A split that finds nobody left before its copy starts makes no copy and moves in place (`nobody_left`). One that finds out later still swaps.
- **A copy dropped after it reached its tier** bills its own early deletion. Only a version pruned during the split does that. The deadline leaves such a copy alone and lets it finish.

| Blob | What they want | Who leaves | Bills, per 184 GB, at the repo's prices |
|---|---|---|---|
| Hot | A wants Cold, B pinned Hot | A | Nothing to read. The cheapest case |
| Cold | B pinned Hot, A's schedule keeps Cold | B | $5.52 retrieval once. No early deletion, where moving the blob would add $1.99 |
| Cool | A wants Cold, B wants Hot | Whoever moves first | $1.84 retrieval once. The other then has the blob to itself and moves in place, which bills an early deletion only if the blob is under 30 days in Cool |
| Archive | Anything | Nobody | Never copied. See below |

After the split, each blob has its own monthly bill, so the extra blob is the lasting cost: the one the owner accepted.

**One blob per wish, not per file.** Before copying, a file looks for the same bytes already in the tier it wants (BLAKE3, size and CRC64-NVME, in the same container), and joins them as one more reference. So A and B wanting Cold against C's hot pin make one copy, with A and B on it. A retained version doesn't join: nothing of it may be retired, and a new reference couldn't be stamped true on a blob whose retention differs. So on a WORM share each file makes its own copy. A file that isn't retained may join a blob a retained one is on: the blob just stays longer.

**A blob in Archive is never copied.** That would be a rehydrate, which only a person starts. A warmer pin on a stub starts the recall it always did, the bytes come back to the edge, and the blob stays where it is. If the catalog is behind and the copy finds the blob in Archive (`NotRestored`), it stops: audited as `source_archived`, no rehydrate, and no fallback, because the fallback's Set Blob Tier would start one on Azure.

## How the split runs

It uses Archive's phases, in `worker/tiering.py`:

1. **`inplace`**, under the blob's lock: read the other files' wishes. They differ, so write a `pending` secondary row named `<prefix><file>/<version>.own-<time>` in the same container, and mark the message `own_copy`. The transaction commits, and the lock goes.
2. **`copy`** (`_copy`): a server-side copy, landing in Hot. No transaction is open during it.
3. **`verifying`** (`verify`): an in-Azure read of every byte, compared with the catalog's CRC64-NVME and size.
4. **`archive`** (`_archive_copy`, now any tier): Set Blob Tier on the copy. It leaves Hot, so no fee.
5. **`commit`** (`_commit_own_copy`), under the blob's lock: the copy becomes the primary and only this file's row changes. The old row goes `deleting`, and `delete_blob` answers `shared` while another row uses the blob.

**The original stays until the copy is verified.** Plain blobs only, and the copy's bytes are the file's. No provider call holds a transaction id: `tests/provider_guard.py` found one of mine while I was writing this (a fallback that audited and then called Set Blob Tier in the same transaction), and that path now commits first.

One more look before paying: a message can be old, so the mover's own plan is read again, and if it no longer wants the tier there is no copy and the scheduler decides afresh.

S3 doesn't split. Its class change is a CopyObject that makes a new version, so it is a copy already.

## While a split runs

A split's copy reads the blob with no lock open, so any other move of that blob sees `own_copy` on the split's message and waits.

- **A move to Archive waits only about 10 minutes** (`ConsumerConfig.max_reads` looks, 30 s apart). Then it takes its own copy from the readable blob, beside the other, through the same phases: landing in Hot, read back, Set Blob Tier to Archive, carrying retention and holds on WORM. The other file's copy goes on undisturbed, and the blob isn't archived under it. If the other file has left by the time its own copy would start, it just moves in place.
- **Any other move waits for the split to end.** Archive is the only date that is promised, so it is the only one worth a second copy. Past `max_reads` it is handed back and looks again an hour later. It writes one audit line, `tier.move.waiting`, `why: behind_another_files_copy`, at most once a day for the file, not one a look. Activity says "Move to Cold waiting".
- **A copy into Archive ends by 24 hours of reachable time (`OWN_COPY_DEADLINE`),** in any phase, throttled or stuck behind `verify` included: the move falls back, audited with `detail: deadline`. It counts in the window recalls use (migration 0040, `recall_timeout.WINDOW_GAP`): a gap in the edges' heartbeats over 3 minutes starts it again, and with no heartbeats it isn't counted at all. A copy already checked and in its tier is left to finish, unless its retention hasn't landed.
- **A copy for any other move carries on past 24 hours,** because no date is at stake and a pin must stay true. It writes one line, `why: own_copy_slow`.
- **If a file's own copy into Archive fails too, its fallback doesn't wait:** the blob goes to Archive for everyone, on the date. That leaves the others' pins false, which is what a date being "always respected" costs when the copies have failed. It is said out loud: see "If the copy can't be made".

**Why a copy within one account should work on WORM.** The repo's research quotes Microsoft: under retention, blobs "can be created and read, but not modified or deleted", and "you can change the access tier". Copying creates a blob and reads another, and Set Blob Tier is allowed. What the design doc ruled out on WORM is copy-and-*delete*, and this deletes nothing. No page we've read shows this exact case, so it isn't proven: RA-55 and RA-56. A refusal is a failed copy, which ends in the fallback.

**A backlog on `verify`** delays a file's own copy behind other files' read-backs. A copy into Archive falls back if the deadline passes first. If the read-back comes in time but past the date, the archive lands late, and says so. While it waits past its date, the overdue alert fires (below).

**Any archive after its date is reported,** by whichever route: in place, a two-account copy, an own copy or a join. It writes `tier.archive.late` in the file's own dataset, with `archive_at` and `late_by_hours`, counts `omnifile.tier.archive_late`, and fires the Azure Monitor rule `tier-archive-late`. Settings, Alerts has a row, and Activity says "Archived after its date". An archive is late from an hour after the end of its date. Not reported: a file an Owner's pin held past its date (`override_archive`, on the file or a folder above), or an old version, whose date `file.archive_at` doesn't describe.

**Overdue says so while it is.** `omnifile.tier.archive_overdue` counts files past the end of their date and not in Archive, and the rule `tier-archive-overdue` and a Settings row fire on it, so a stuck file is known before it lands. It costs the same at 10^8 files: it reads `file_archive_due` (migration 0049), the files whose next step is Archive, from the oldest due, for at most 10,000 rows (`policy/overdue.py`), since such a file stays due until its move lands. A dataset with no tiering policy now isn't counted. **The limit:** past 10,000 archive steps due at once, the count stops at what those rows hold, which is still above zero when one of them is overdue. (The re-check found the first version read `file_next_action`, every step, so 10,000 stale rows of another step, which nothing clears when the scheduler stops taking a file, hid an overdue file. `test_stale_rows_of_other_steps_dont_hide_an_overdue_file` is the reviewer's run.) It counts every few minutes, with the other gauges. An old version has no `file.archive_at`, so it isn't counted.

## Decision 34: restoring a version during a split

Traced in `worker/portal_jobs.py` and `web/routes_rewind.py`, and tested. A restore reads the version's primary, whichever row that is then, and copies it to `restores/<id>`: a blob of its own, which nothing else references. So it never joins a split.

- During the copy phases, the original is still the primary, so it reads that.
- After the swap, it reads the new blob. If that went to Archive, its existing recall path applies.
- If the swap's delete takes the old blob under its copy, the copy fails (`ObjectNotFound`), the message retries, and the retry reads the primary afresh. Nothing is lost.
- An overwrite makes a new current version. The old version's split carries on, because a superseded version is still live, and lands on its own blob.

## Decision 31: WORM

- **The new blob carries the version's retention and legal hold before it becomes the primary.** `stamp_worm` runs on that one row, with no transaction open, and the swap refuses while `worm_sync_needed` is set. A hold set during the copy is stamped first too.
- **Nothing is deleted.** The catalog's guard refuses `deleting` on a retained version, so the old row becomes a `secondary` instead, through the swap a migration's cutover uses (0027). Its blob stays until retention ends.
- **A daily sweep retires it then** (`replaced_secondaries`, `retire_replaced_secondaries`), through `delete_blob`, which keeps the bytes while another row uses them. Prune can't: it leaves a current version alone, so before this the row would have kept the blob `shared` and billed for as long as the file lived. The sweep takes a secondary in the same container as its version's verified primary, under another name, once no hold or retention covers it and no message is using it. That leaves archive copies (another container) and a migration's rows (another backend, or a source) alone. It reads the whole table, with no index on the role, so it runs daily and holds no id. A partial index would suit the next migration (L).
- **A copy whose message was lost goes too,** a day later, through the same sweep. The grace lets the next move pick it up first. So a split that dead-lettered and whose file's plan then changed isn't billed for ever.
- **A blob's retention is never shortened.** `stamp_worm` never stamps a retention that has ended: the flag clears, and nothing reaches the blob. On a shared blob, that date could have shortened another file's retention, or failed on every sweep against a locked one. A row with an earlier date than the blob carries leaves the blob's, and the retain-until tag stays with it. A hold cleared on one file stays while another file on the blob is held. `stamp_worm` is the only caller of Set Immutability Policy and Set Legal Hold.
- **A retained secondary has no plan.** It asks for no copy and holds nothing back in the worker, the scheduler or the API. It follows the blob, so its row stays true.
- **A copy of a retained version that fails its read-back stays too, unused,** because nothing of a retained version is deleted. The next attempt makes a new one and never reuses it.
- **Limit (L):** on a WORM share, a blob all of whose primaries have left stays in its last tier until retention ends, because nothing with a plan moves it. It can be Hot.

## If the copy can't be made

No write rights, a provider failure, three failed tries a minute apart, a bad copy (length or CRC), no CRC to check against, retention that won't stamp after 5 tries, or the deadline:

1. An audit row: `tier.move.refused`, `why: own_copy_failed`, with `detail`. The metric counts `failed`. The copy's row goes, or stays unused if the version is retained.
2. **Only an archive date that has come may move a blob over a file that differs,** because a date is always respected. That's the file's own date, on that UTC day or after, or an old version's date from the version sweep, which has no pins. The move runs again with `no_own_copy`, for everyone. **A pin to Archive doesn't force:** it's a person's choice about their own file, and they may not be able to read the others on that blob. So it waits like any other move until the file's own date comes, and then the date forces (`_archive_date_arrived`, `test_a_pin_to_archive_never_takes_another_file_offline`).
3. **Any other move, warmer or colder, or to Archive by a pin, changes nothing.** A schedule running late with an alert is better than a pin going false and a fee being billed. It writes `tier.move.refused`, `why: held_back_shared_blob`, once a day per blob, and tries the copy again a day later (`_wait_a_day`, `OWN_COPY_RETRY_AFTER`). The scheduler and the version sweep stay away until then. If a pin was released meanwhile, nothing moves.

Throttling isn't a failure and uses up no try. A source that's gone is a dead letter, as for Archive: the other file has lost its bytes too, and a person has to look.

**The alert keeps firing while it's stuck.** `omnifile.tier.own_copy_stuck` counts those reports in the last 25 hours, a little over the wait, so it doesn't lapse between retries. The rule `tier-held-back` and its Settings row read it and say in plain words what is wrong: a file needs its own copy of shared storage and can't get one; most often the worker lacks write rights on the storage account, and the audit row's `detail` says why; fix that, and each file tries again within a day. It clears itself a day after the copies work.

**Files that don't differ, and blobs with one file, move exactly as before,** in place, with no copy tried, whatever the copies are doing: `test_files_that_agree_move_with_copies_failing`, `test_a_single_reference_is_never_held`, `test_a_move_for_a_lone_blob_never_waits`.

**S3** doesn't change: its class change is a copy already, and the rows that name the old version keep it.

**What a forced Archive does.** The other files go offline before their own dates, and maybe against a pin, so each one's `tier.move` row, `how: shared_blob`, also says `forced: another_files_archive_date` and `why: neither_file_could_get_its_own_copy`. It names no other file. `omnifile.tier.forced_archive` counts each, and the rule `tier-forced-archive` and a Settings row fire. For a current version under a pin warmer than Archive, a `notify` message goes in the same transaction to the pin's setter (`set_by_identity_id`, a folder's pin included): one Teams card with no buttons, saying the pin wasn't kept, and an "Open in portal" link. Email is the fallback, as for a recall's card: when the app is blocked, the conversation is gone twice, or the card has failed for an hour. A setter who can't read the file now hears nothing. Each outcome is audited (`pin.notice.teams`, `.email`, `.skipped`). There's no `catalog.notification` row, since its `recall_id` is required and this has no recall, so a crash just after the send can send it twice. RT-44 checks it on a real tenant.

## Concurrency and crashes

All tested.

| What happens | What it does |
|---|---|
| Two workers on two references decide at once | One gets the blob's lock and starts. The other defers on the lock, then sees `own_copy` on the first's message, and waits. One copy; the second then has the blob to itself |
| Any other move of the blob during a split | Waits on the same check, since the copy has no lock open. Handed back after `max_reads`, not dead-lettered. A move to Archive takes its own copy there instead |
| Worker dies during the copy, either side of it | The message comes back. A copy that got there is adopted and read back like any other. One copy, the same row |
| Message lost at any phase (dead letters) | The next sweep's move finds the row left behind and finishes it. No second row. It doesn't reuse a copy that failed its read-back, or one other rows use |
| Replayed `commit` | Changes nothing |
| Dedupe during the copy | Attaches to the original, the only primary it can see. The later delete sees it and keeps the bytes (`shared`), and its row stays true |
| Dedupe during the swap | The swap's lock is exclusive and the dedupe's is a shared try: whichever comes second doesn't wait. A dedupe uploads its own copy; the swap comes back 30 s later |
| Dedupe after the swap | Finds the new blob: the same bytes |
| File overwritten during its copy | The old version finishes on its own blob |
| Version pruned during its copy | The copy goes. The swap looks again under its lock, so this holds right up to it |
| A copy dropped just before the swap | No swap: the same look |
| Stamping hangs | Bounded like the other calls (`MOVE_CALL_TIMEOUT`), then counted as a try |

The swap takes its rows before its file, lowest id first, as the change feed does.

## Cost visibility

- **Audit:** every split writes `tier.move`, `how: own_copy`, with `from`, `to` and `target_location_id`, in the file's own dataset. A join adds `joined: true`. No other file is named, and no key, because a key carries its first uploader's file id. Files that stay get no row, since nothing happened to them.
- **Metric:** `omnifile.tier.own_copy` with `dataset_id`, `file_id` and `outcome` (`copied`, `joined`, `failed`).
- **The bill:** `datasets[].stored` counts physical objects, so the extra blob appears there by itself.
- **Policy preview (`policy/cost.py`): no change.** It prices each file as a blob of its own, with no dedupe saving, so a split moves the bill towards its number, not past it. It models no pins. The docstring says so.
- **Pin preview: changed.** On a shared blob, `pin_early_deletion` was wrong and `monthly_cost_change` understated. It now gives `pin_own_copy` (info), with one read of the tier as its `fee`, and the whole new blob as the monthly change. It says "unless the other file wants this tier too", because a preview doesn't read the other file's plan. In that case the old numbers would be the true ones (L).
- **Portal's "move waiting":** `Entry.move_hold` is set only once the worker has reported a wait, which happens only when the copy failed. A file getting its copy isn't shown as waiting. It reads: "Its move to Cold waits until 7 Nov: it shares its storage with another file and couldn't get a copy of its own. It tries again then."
- **Not shown (L):** nothing in the portal says a copy is under way. The file shows its old tier and its pin until the swap, as an archive copy does today.

**The sweep (5).** One `{"op": "retire_left_behind"}` message on the `retention` queue does the work. It reads one page of 500 secondaries in `location_id` order, retires what it finds, and sends itself on at once with a cursor, so a backlog clears in one go: 10^8 rows is 200,000 short messages. The last page writes `retention.left_behind.swept` with how many it retired. The `replaced_secondaries` sweep, hourly, sends the first message only if none is queued and no pass finished in the last day, under a transaction's advisory lock, so a replica starting does nothing, and a dead-lettered pass starts again within the hour. Nothing waits in the queue between passes, because `omnifile.queue.oldest_age` counts from when a message was sent, and a message hidden for a day would fire the stuck-queue alert. The page, not what it finds, bounds a batch, because most secondaries can be retained for years. Migration `0049_secondary_index.sql` adds the partial index it reads, `CONCURRENTLY`, in no-transaction mode. It was 0048 until #70 merged with its own 0048.

**The stamp (6): the tension, and how it's resolved.** A stamp has to hold something across its provider calls, and no transaction id may be held across one, since that stops the edge feed. So each row's stamp takes a **session** advisory lock on the blob's key (`pg_try_advisory_lock`), which takes no id, and lets it go in a `finally`. It's the same key movers and dedupes use. It's a try lock: if the blob is busy the row is skipped with its flag up, and the next sweep gets it. A session lock is safe here because the stamp runs on an autocommit connection, outside the consumer's transaction, and #76's consumer lets go of any session lock left behind anyway. **What it doesn't close:** a hold set in the catalog just after the check isn't seen by that check. It raises its own row's flag, and that row's stamp follows under the same lock, so the provider ends with the hold set. `_another_hold` is now checked for every row with no hold, not only one clearing a hold.

**#71's guard, removed (the coordinator's second condition).** With only Archive forcing, `_held_until`'s warmer-only, tier-clock rule can't fire: no warmer move reaches it, since a differing move now waits first, and a move to Archive isn't warmer. So `_held_until`, `BLOB_CLOCK_SQL` and the clock conditions in the scheduler and `web/entries.py` are gone. What still works is kept as the waiting signal: the once-a-day report (`HELD_BACK`, `_report_hold`), the wake (`_hold_wake`), the scheduler's filter on a report, and `Entry.move_hold`. `SHARED_BLOB_WARMER_HOLD` is now `OWN_COPY_RETRY_AFTER`. The version sweep gained the same filter, since old versions now wait too and nothing else would stop it trying every sweep. Whichever way a copy fails, the move runs again without a copy and `_in_place` alone decides what that means: Archive moves the blob, anything else waits. So there is one place for the rule.
