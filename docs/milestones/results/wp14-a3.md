# WP14 A3: the return paths and recalled copies (plan)

Branch `claude/annex-a3`, from main at 2794aeb (#65 merged; #61, A2.2, merged before it). The design is `docs/design/annex.md` §3.6, §4.1, §4.4–4.6, §5, §7, §8.3–8.4 and §10.1–10.2. A recalled file can be put back on the filer where it came from, in a restore folder, or in an OmniFile share. The same rules system as the outbound side decides where, and the visual builder gets its Back half.

This is a plan only. A3 is the first phase that can **replace** something on a NAS, so no NAS write path gets built until the coordinator has read "What A3 writes to a NAS" and "Overwrites at the origin" below. The rules, the builder's Back half and the service pieces that write nothing to a NAS (A3.1, and A3.2's share placements) may start while it is reviewed.

## Phases (five PRs)

**A3.1: return rules, the builder's Back half, folder ACLs and placement requests. Nothing is written to a NAS.**
- **Rules (`annex/rules.py`, the edge's `rules.rs`):**
  - the triggers `recall_requested` and `recall_completed`;
  - the actions `place_at` (a `nas_folder` or `share_folder` location, with `conflict`: `same_content`, `restored_name` or `overwrite_keep_version`), `hold_days`, `notify` and `let_requester_choose` (a list of locations);
  - the condition `requester_in` (SIDs, return rules only);
  - the three return templates and the default per outbound mode (§4.4).
- **Save checks (§4.2):**
  - a `place_at` target covered by a `remove_from_source` rule with no hold is refused, and so is a Move-now drop folder;
  - `overwrite_keep_version` on a `nas_folder` is allowed only inside the annex's root.
  - A proposal that adds a `place_at` outside the annex's own folders needs an ArchiveAdmin (§4.3).
- **Folder ACLs:** the edge's scans capture each folder's ACL as they do files' ACLs, compared by hash. The service turns them into `read_sids` and `write_sids`, the latter from the right to add a file:
  - SMB `FILE_ADD_FILE`;
  - NFSv4 `ACE4_ADD_FILE`;
  - POSIX `w` and `x` on the folder.

  Deny wins, and an unmappable entry fails toward "can't place it here". This also captures what A2 noted would reopen previews to Owners; reopening them is left for A4.
- **Return preview (§4.5)** over the annex's removed files: per rule and target, the files, the names taken today (from the edge's listing) and the space needed against `statvfs` of the read-only mount.
- **Service:**
  - `GET /v1/files/{id}/return-targets`: the targets the running rule set allows this requester, default first, each with the write check's result and the edge's last free-space report;
  - `POST /v1/recalls` gains `place_at` and `on_conflict`, and creates an `annex_placement` in `requested`;
  - `GET /v1/placements/{id}`.

  Placements wait in `ready` until A3.2 or A3.3 builds their consumer. The origin is offered only for files whose `nas_state` is `removed` or `gone`; a file still hidden in its grace period is put back by cancelling its removal (A2's W3) instead.
  - An API client's placement must name the person it is for. That person's read access and write access are checked, as for proposals (decision 52). Otherwise `422 requester_required`.
  - A file that is online (not in Archive) needs no rehydration. Its placement skips that step, rather than being refused with `recall_not_needed` as today.
- **Portal:** the builder's Back half (§8.3), drawn from the same ordered, accessible rule list: "From" (tier and recall time), "If", "Place at", with the conflict and hold chips and today's conflicts and space. The recall dialog gets a target picker, from `return-targets`, and the optional "Why do you need it?" note.

**A3.2: recalls into an OmniFile share. This writes to OmniFile's own share, not to a NAS.**
- **The service copy:** the blob is copied server-side into the share's dataset as a new catalog file (`origin = 'annex_restore'`), linked to its placement. The copy is verified by the in-Azure CRC read before the placement says `placed`.
- **Its ACL:** the copy gets the annex file's own catalog ACL (`read_sids`, `deny_sids`, `deny_first`), never the share folder's default. So the people who can read it are the share's readers who could also read the original.
- **Name conflicts:**
  - `overwrite_keep_version` is decision 34's restore as overwrite, through the same edge instruction, refused as it is today when the edge holds unsynced writes to that path;
  - `restored_name` uses `routes_rewind.restored_name`.
- **Fill:** the edge fills the copy at once and keeps it online for the hold. The hold is a "Keep online" pin (decision 33) until `hold_until`.
- **Teams:** the recall card gains the placement steps and "placed at" with a path to copy. A failure offers the other allowed targets as signed `place_at` intents through the relay.

**A3.3: placing a file on a NAS (the write path below).** The placer, `annex/placer.rs`, with:
- tickets, the journal, the restore mount, the space check, the fill, the read-back and the ACL, owner and timestamps;
- the no-replace rename, and the `same_content` and `restored_name` conflict choices;
- pointer files;
- loops: `returned` events, the hold, no recopy and the circuit breaker.

**A3.4: `overwrite_keep_version` at the origin.** Its own PR, because it is the only A3 path that takes a name a user's file had. Detailed under "Overwrites at the origin".

**A3.5: recalled-copy cleanup (§8.4).** Nothing here touches a NAS or an original.
- **Open counts:** the edge counts opens of placed files from Ganesha's opens and Samba's audit of opens, and reports hourly totals (`placement_opens`).
- **The lists:** the Recalled copies tab on each share, and the Annex page's Recalls.
- **Filters:** the §8.4 filters, saved filters, and `GET /v1/recalled-copies`.
- **Bulk delete:** `POST /v1/recalled-copies:delete`, with `expected_count`, a dry run and per-file outcomes. It skips held, WORM, changed and legal-hold copies, and any copy whose original isn't verified and safe. It only ever takes files with `origin = 'annex_restore'` made by a placement: never a user's file a `same_content` placement linked to (`already_there`), nor one a placement overwrote with a new version (#68 review).

## What A3 writes to a NAS, and how each write is gated

Revised 2026-11-05 after the independent review of the plan's write paths. The review's points are numbered R1–R8 below, where each lands.

All of A3's NAS writes live in one module, `annex/placer.rs`, as A2's live in `remover.rs`, and only these two modules get a writable handle.
- Every write goes through a directory fd opened beneath the export's root with `openat2` (`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_XDEV`), and every file is created `O_NOFOLLOW`.
- A name the edge is given is one path component, never `.`, `..`, `.omnifile-*` or `*.omnifile.txt`, and at most 255 bytes.
- Nothing is ever written to or deleted by name alone. A file A3 replaces or deletes is one it created and journalled, checked again just before.

**Two accounts (R4):**
- **The read account** mounts the read-only mount. It is in `OmniFile-Annex-Read`; it scans and copies, and it reads placed files back.
- **The placement account** mounts the placement mount. It is in `OmniFile-Annex-Restore`, and it is the only account that writes a placed file.

By default both are the edge's machine account, each mount with its own Kerberos credential cache. With service accounts, they are `annex.keytab` and a new `annex-restore.keytab`, both sealed. A2's removal account (`annex-remove.keytab`) is a third, and a Copy annex never gets it.

**The staging folder (R1).** Temporary files are never created in the target folder. Each annex has one staging folder, `.omnifile-staging-<annex_id>-<token>/`, at the root of its export; the token is random and journalled before the `mkdir` (#70's second review). (Planned as one per filer. #70's review found that its journal is the annex's, so a second annex on the same export would meet a folder it didn't make and stick for good.)
- **It is locked down before it is ever used.** The edge makes it once, sets a protected DACL, and reads that DACL back, refusing to go on unless it matches. The DACL gives the placement account full control, the read account read and traverse (`FILE_TRAVERSE`; over NFSv4, `EXECUTE`), and nobody else anything. Over NFSv4 the ACL names only those two; over NFSv3, the folder is mode 0700, owned by the placement account.
- **It is never adopted.** The journal records the name (`staging_rel`), then a successful `mkdir` (`staging_made`), then the lock (`staging_ino`). If the `mkdir` wasn't recorded (a crash, a replayed `EEXIST`, a journal that failed), that folder is never used: it is removed if empty, and the next try has a new name, so nothing is held up. A folder under the recorded name with another inode stops placements on that annex with an owner problem. The edge never uses it and never changes it.
- **It is checked before every use, on the very dir fd the creates use** (one `openat2` per placement, then `fstat` and `fgetxattr` on that fd, then `openat` relative to it). The edge requires the journalled inode, the same DACL hash and the same owner. If either changed, every placement on that filer stops with a problem for an ArchiveAdmin. There is no fallback to the target folder.
- **Nothing is taken from what a new file inherited.** A file created there gets its own lock on its fd, read back before a byte is written; a file that won't take it fails `staging_file_not_locked`. Its name also carries a random 128-bit token, so nobody can guess it either.
- **It reaches the target folder only by `linkat` (P4).** That works only on the same volume. A target on another volume fails P4 with `EXDEV` (`cross_volume`), cleanly. Once that has happened, the target isn't offered.

| # | Write | How |
|---|---|---|
| P0 | Make the missing folders of a restore folder's relative path | `mkdirat` in the target, one component at a time, each journalled (name, then inode) before the next. **The new folders inherit the restore folder's ACL** (decided, question 4). The file in them carries its own protected ACL, while a protected copy of the original folder's ACL could widen access to the folder. It is never used for the origin target. An origin folder that no longer exists fails `target_missing`, and the other targets are offered. |
| P1 | Create the temporary file in the staging folder: `<token>-<placement>` | `create` is journalled with the name first. Then `openat(staging_fd, tmp, O_CREAT \| O_EXCL \| O_NOFOLLOW \| O_RDWR, 0600)` and `fstat`, and its inode and nlink are journalled (`created`). It is born with only the staging DACL. |
| P2 | Fill it | `pwrite` on that fd only, from the blob version's ranged, version-pinned GET, as the recall fill reads. The CRC64-NVME of the stream is compared with the catalog's. `filled_to` is journalled every 256 MiB, then `fsync`. **Resume (R5):** the file is reopened only when its inode matches, nlink is 1 and the hash of its ACL is the staging DACL's. Then it is truncated to `filled_to` and the fill goes on. Ctime isn't used here, because every write moves it. |
| P3 | Group and ACL, then timestamps | First the group, so that until P5 no group gets in that shouldn't. The placement account's primary group (often Domain Users) is never the file's group under its final name. A `GROUP@` ACE or mode group bits copied from the original would grant that group read between P4 and P5. The group is set with `fchown(fd, -1, gid)`, or over SMB the descriptor's group SID; `protected_hardlinks` checks only the uid, so P4's link still passes. Then the captured descriptor is set on the fd: the raw NT descriptor (`system.cifs_ntsd`, owner left alone), the NFSv4 XDR (`system.nfs4_acl`), or mode plus `system.posix_acl_access`. In any folder but its own, the descriptor's inherited entries become explicit and the DACL is protected (§4.6: its own descriptor, never its new folder's). The owner is set only after P4 (R3). Then come the read-back (gate 3) and `futimens` (atime, mtime), which goes last because the read-back moves atime on a NAS that keeps it. **Then ctime and the ACL hash are journalled (`secured`)** (R2). |
| P4 | Link it under its final name, never replacing anything | Only after `place_go` and a forced `statx` that matches `secured`: the same inode, size, ctime and ACL hash, with nlink 1. Then `linkat(staging_fd, tmp, target_dirfd, final, 0)`; the server refuses it with `EEXIST` if the name is taken, so the check and the write are one step. Then `unlinkat(staging_fd, tmp)`. **The link comes before the owner is set (R3):** the file is still the placement account's, so `protected_hardlinks` lets it through, on the edge and on a Samba server's host alike. A rename is never used to make a final name. NFS refuses `RENAME_NOREPLACE`, and cifs appears to check it on the client and then ask the server to replace. A3.3 tests, with a second client and a capture, that cifs's link sends `ReplaceIfExists = 0` (R3). |
| P4a | Only where the server refuses the link anyway (`EACCES`, `EPERM`, `EOPNOTSUPP`, `EMLINK`) | #61's placeholder. The final name is created `O_CREAT \| O_EXCL` in the target (atomic at the server: SMB `FILE_CREATE`, NFS exclusive create), holding `PLACEHOLDER_TEXT`, then `fsync` and `fstat`, and its inode and ctime are journalled. Just before `renameat(staging tmp → final)`, it is checked again: the same inode, an unchanged ctime, exactly that text and nlink 1. Otherwise the placement goes to `stuck` and nothing is renamed. The residual window, between that check and the rename, is #61's: a user would have to write into a file that says it is OmniFile's, within milliseconds. |
| P5 | Owner | After P4, on the same fd: `fchown`, or over SMB the descriptor's owner set with `system.cifs_ntsd_full`. If the owner can't be set (no restore right), the file stays the placement account's and the card says so. Until then, the file is under its name with its final DACL and the placement account as owner. That only ever narrows access (the real owner's `OWNER@` rights wait), and a resume finishes it (`linked → owned`). A forced `statx` and an ACL read then record the final state. |
| P6 | Pointer files | Only when the file is back under its own name in its original folder: `<name>.omnifile.txt` is unlinked when its inode and text hash match what W4 recorded, with nlink 1. **R6:** that needs an A2 change, in A3.3's PR: W4 records the pointer's inode and the SHA-256 of its text in `removal`. Pointers written before that have no inode recorded, and are matched by their exact text (the text `pointer_text` produces for this file, with the date it states) and nlink 1. A note a user edited is left alone. Placed anywhere else, the pointer is left as it is (decided, question 3). |
| P7 | Clean up after a failure or a crash | The staging file is unlinked only when its journalled inode matches and nlink is 1. After a crash between `create` and `created` (R7), the file at the journalled name is accepted only if it is empty, owned by the placement account, nlink 1 and holding exactly the staging DACL. Then it is unlinked or used; anything else is reported, never touched. Folders P0 made are removed with `unlinkat(AT_REMOVEDIR)`, which the server refuses for a folder that isn't empty, and only when their inode matches. A staging file the journal doesn't name is never deleted; it is reported as a problem. |

**Gates. All of them hold before P0 or P1. Gates 1 and 2 are checked again by the service at `place_go`, before P4, and gates 3 and 4 by the edge.**

1. **The mounts.** The placement mount exists only while the service has a live placement ticket for that filer and the placement switches are on. The unit unmounts it when the last ticket ends.
   - It has the same `nosharesock`/`nosharecache` and `rw,nosuid,nodev,noexec,nosymfollow` checks as A2's, with an `st_dev` apart from the read-only mount.
   - **Backup intent (R8):** over SMB, setting another owner needs `SeRestorePrivilege` used with backup intent. That is `backupuid`/`backupgid` on **the placement mount only**. The read-only mount and the removal mount never get them.
   - With backup intent, the placement account's opens bypass the NAS's ACLs, so the placement mount is the most powerful handle the edge holds. `docs/design/threat-model.md` records this, under T7/T10, in A3.3's PR. The mitigations are that it is mounted only while a ticket is live, that only `placer.rs` gets it, and that every write is ticketed and journalled.
   - It is proven against the test Samba server before anything relies on it.
   - Targets are folders on filers that already have an annex on this edge; a filer folder with no annex isn't offered in v1.
2. **A ticket from the service for each placement.** The edge never places a file by itself. The service issues `place` (minutes; renewed while a long fill reports progress), and later a separate `place_go` for P4, only when all of these hold:
   - the placement switches (per annex, global) are on;
   - the requester can still read the version, through the catalog's read set, deny-first (`access-control.md` §5);
   - the target is one the running, approved rule set allows this requester, or a folder under a location it allows;
   - **the requester can write the target folder:** `acl_can_write` over the folder's snapshot. At `place_go`, the snapshot's hash must equal the target folder's ACL as the edge reads it then, so an ACL that changed during a 15-hour rehydration is checked again;
   - the version is committed, its CRC is known, and its bytes are online.
   - **Recalls never widen access (decision 51).** At `place_go`, the edge sends the ACL it reads back from the staging file after P3. The service computes that ACL's effective read set **as it will be after P5**, with the final owner and group put in place of the placement account (an `OWNER@` or `GROUP@` entry, or mode bits). The placement is refused (`acl_mismatch`; P7 cleans up) unless it is within the catalog's read set for the file. In a share, the copy's read set is the file's own (A3.2).
3. **The edge's own checks.**
   - **Space**, before P0 and P1: `statvfs` of the target. The file's size plus 5% must fit; this reflects the quotas on the placement account. `ENOSPC` or `EDQUOT` at any write fails the placement and runs P7.
   - **The read-back, after the ACL is set in P3 (R2, R4):** the file is read back through **the read-only mount** after `posix_fadvise(DONTNEED)`. That is a separate superblock and connection, so the bytes come from the server and not from the placement mount's page cache.
     - The read account can open it, because the descriptor is the one the read account read the original under: the same entries, made explicit in another folder.
     - Over NFSv3 with `sec=sys` as root, the read-back proves the bytes, not access: root reads whatever the mode says.
     - If it can't (`EACCES`, for example because its groups changed), the placement fails `readback_denied` and P7 cleans up: fail closed.
     - Its CRC64-NVME must equal the catalog's. A mismatch runs P7 and retries once, then fails `crc_mismatch`.
   - **Before P4:** the forced `statx` against `secured`, as in P4's row.
4. **The final name (P4).** The edge tries the names the ticket allows, in order, each with no-replace:
   - `<name>`;
   - on `EEXIST` with `same_content`, an existing file of the same size whose CRC equals the version's is left alone, P7 removes the staging file, and the outcome is `already_there`;
   - with `restored_name`, `<stem>-restored<ext>`, then `<stem>-restored-<YYYY-MM-DD-HHMMSS>Z<ext>`;
   - a taken timestamped name fails `name_taken`, never overwritten.
5. **The journal.** `annex.db.placement` records each step before it is taken, in this order: `ticketed → space_checked → [mkdir(name) → made(ino)]* → create(name) → created(ino) → filling(filled_to) → filled → acl_set → read_back(crc) → secured(ctime, acl_hash) → go → linking(name) → [placeholder(ino, ctime)] → linked(ino) → owned → pointer → done`, or `cleaning → failed(why)`, or `stuck` (an owner problem, an ALERT line, retried hourly).
   - The journal write is fatal before every write. A restart resumes from the journal, and first checks whether the file is under its final name already (#61's lesson).
   - Every step is acknowledged to the service and audited with the file, version, CRC, rule, target and requester. A repeated report of the same outcome is recorded once.
   - Debug builds take crash points under `OMNIFILE_ANNEX_CRASH_AT` at every step, and thread-local faults (`JOURNAL_FAILS`, `ENOSPC_AT`, `LINK_EACCES`, `CRC_FLIP`, `NAME_TAKEN_AT`, `READBACK_EACCES`), as `remover.rs` has.
6. **Loops (§4.6).**
   - A placement records its target path, file id and CRC. A scan that meets that file sends `returned`, not `arrived`, so `arrived` rules don't fire for it.
   - Outbound rules skip it until `hold_until`, and its age counts from the placement.
   - Unchanged content reuses the verified version, so a later removal needs no upload.
   - A file placed and removed more than three times in 30 days raises `loop_breaker` and is pinned until an Owner looks.
   - A removal ticket is never issued for a file in its hold.
   - The scanner skips staging folders only at the top of the export. A user's own folder of that name anywhere else is scanned like any other.

## Overwrites at the origin (A3.4)

**The default never overwrites.** "Back where it came from" uses `restored_name`, and every NAS conflict choice except `overwrite_keep_version` only ever creates names (P4 is no-replace everywhere). `overwrite_keep_version` on a NAS is a rule a person must choose. The save checks allow it only inside the annex's root, and an approver sees it as a replacing rule.

**Never over a user's newer file.** The file at the name is replaced only when it is exactly the annex's current version of that file, already verified in Azure. So whatever it holds is kept as a version before it goes. The service issues an `overwrite` ticket only when all of the removal ticket's gates hold for that existing file:
- the `annex_file` row's current version is the one copied;
- that version had an in-Azure read within 24 hours;
- no legal hold stands on it or a folder above it;
- the file is inside the annex root;
- **no removal of it is open** (an `annex_removal` that isn't `done` or `cancelled`; decided with question 1).

The edge then checks, as for W1 and W2:
- a forced `statx` matching that version's inode, size, mtime and ctime;
- nlink 1;
- no alternate data streams;
- over SMB, the CRC read again once before the replace step.

Anything changed since the copy, including a write a minute ago that no scan has seen, fails the `statx` match. The placement then falls back to `restored_name` and records `overwrite_refused(<why>)`. It never fails silently, and it never replaces.

**How it replaces, so a user's write is never lost in the gap:**
1. Hide the existing file with A2's W1, renamed to `.omnifile-replacing-<placement>-<name>` with no-replace. Over SMB, this is refused while someone has it open without `FILE_SHARE_DELETE` (decision 59): in use, and it falls back to `restored_name`.
2. Wait the annex's grace period (15 minutes by default). Then check the hidden file again with the W2 gates: the ctime W1 left, journalled; the size; nlink 1; and over SMB the CRC re-read and then `statx` once more.
3. Put the placed file at the now-free name with P4 (no-replace). If a user created that name during the grace period, the placed file takes `restored_name` instead, and step 4 still runs.
4. Delete the hidden old file with W2, only now that its gates hold again. If any gate fails at step 2 or 4, nothing is deleted: the hidden file is put back with W3 (no-replace). If its name is taken, it stays hidden and the placement goes to `stuck`, with a problem for the Owners, as in A2.

Every step is journalled as `replacing → hidden → … → old_deleted`. The service acknowledges each one and audits it with the replaced version's id and CRC, so the portal can show "replaced; the old content is version N". A3.4's exit test kills the daemon at each step, and checks that a write made in each window to the old file survives.

## Tests

**Unit tests (edge, Linux; each one fails without its gate):**
- a name created by a user between `secured` and P4 is never replaced, through each of P4's paths: the link, and the placeholder;
- a staging folder whose DACL or owner changed stops every placement on that filer;
- a staging folder the journal didn't make, or with another inode, is never adopted;
- **the group:** a file whose group differs from the placement account's primary group is never readable by that group at any step, P1 to P5, on NFSv4, NFSv3 and SMB; and `place_go`'s read set is computed with the final owner and group;
- the read-back comes after P3, and a file changed after `secured` (size, ctime, ACL hash, nlink) is never linked;
- a crash between `create` and `created` accepts only an empty, placement-owned, nlink-1 file with the staging DACL;
- a P2 resume refuses a file whose inode, nlink or ACL hash changed;
- that cifs's `linkat` sends `ReplaceIfExists = 0`, by a second client creating the name at the server and a capture on the VM;
- a placeholder that was edited, replaced or linked goes to `stuck`;
- a flipped byte on the server is caught by the read-back through the read-only mount;
- a journal write that fails stops before the write it guards;
- P7 never deletes a name the journal doesn't own, and never removes a folder that isn't empty;
- P6 deletes a pointer only on its recorded inode and text hash, or an older pointer's exact text;
- a crash at every step resumes or cleans up, and never leaves a partial file under a real name.

**Service tests:**
- `place` and `place_go` are refused when the requester has lost read or write access, when the folder ACL hash moved, when the placement switches are off, when a rule changed, or when the read set placed is wider than the catalog's;
- `requester_required` for an API client;
- the save checks (a return target emptied again; overwrite outside the root);
- A3.4's overwrite ticket refused for an unverified, held or changed file;
- A3.5's bulk delete skipping held, WORM, changed, legal-hold and not-safe copies, with a count that changes between preview and confirm refused.

**Exit test** (stage 7 of `tests/e2e/annex_a1_test.sh`, P0–P14 on both test NAS on omnifile-acl, with §10.2's placement list):
- each conflict choice against a free name, a name with the same content, different content and a recreated file;
- a target the requester can't write to is not offered, and is refused when requested anyway;
