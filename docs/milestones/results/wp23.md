## 1. Dead letters

### What was checked

| Claim | Result |
|---|---|
| A `restores` message that fails five times dead-letters, and the recall stays `requested` | True. Run: `test_a_dead_lettered_recall_is_stuck_until_the_sweep_sends_it_again`. |
| `api/recalls.py` joins it without sending | True, by reading. So do `web/recalls.py` and `api/teams.py`. |
| No sweep re-sends restores, retention or upload verify | True. |
| None for migrate, seed and exports | True. See "Other queues". |

### What I picked for recalls: both, in order

A sweep alone never ends, and failing at once fails a recall for a provider's bad minute. So `worker/redrive.py` (`dead_letter_redrive`, every minute) sends it again after 5, 10, 20 and 40 minutes, then each hour, six times, then once more when the provider answers. An hour after that it fails with a reason, about 5 h 25 min after it first failed (the table under "How long"). It reuses `_set_recall`, so an annex placement waiting on the recall fails too.

- **What the user sees:** the portal shows `recall.failure`: "The storage service kept failing, so this recall was stopped. Recall the file again to retry." Teams shows its general reason and how to retry (`cards.failure_text`). Neither carries the provider's text, which goes in the audit row, `recall.gave_up`. The recall card's Recall button, the portal, and opening the file each start a new recall, not a join.
- **Anti-pattern 5:** the first re-send clears `eta` and updates the card ("No time is promised yet"). No new time is made up. The note text said "Files over 10 GB have no promised recall time" for every recall with no ETA, which a cleared one would now read as false, so it says "No recall time is promised."
- **An outage doesn't fail the fleet.** At the bound, the sweep asks for the recall's own object with `head`, with no transaction open. An answer, or "not found", means the provider is up and this recall has the problem. No answer means an outage, and the recall keeps waiting at the longest interval. A backend that gave no answer isn't asked again that sweep.
- **The bound on that:** `outage_limit`, 3 days, so nothing waits for ever. And at most 100 dead letters per queue per sweep, so a mass failure reaches Teams at that rate.
- **Not covered:** a provider that answers HEAD but refuses every restore, such as a role that lost a permission. Those recalls fail after about 5 h 25 min. I think that is right, since someone has to act, but it is many cards at once.

Three smaller changes to `handle_restore`, since these were what dead-lettered in the first place:

- `Throttled` now retries and never counts. S3's 1,000 restores a second is shared, so a busy afternoon could dead-letter a recall.
- `ObjectNotFound` fails the recall at once.
- An answer from the provider clears the re-send count, so a day-long restore isn't failed for the morning's errors.

A recall that is active with no message and no dead letter (one purged by hand, say) is sent again too, after a two-minute grace.

### After the review of a43e3e4

**Throttling had no bound (S1). The review was right.** Azure maps any 503 to `Throttled`, and each `Retry` is a fresh message. So a gateway returning 503 for days left a recall `requested`: no dead letter, no outage limit, and a quiet queue-age alert. On main it dead-lettered, so my change made this one worse. `verify` already had the loop on main.

- **Now:** `queue.throttled` retries with no attempt used up for **one hour**, then raises the error, which counts as a failure, dead-letters and reaches `redrive.py`.
- **Why an hour:** real throttling lasts seconds or minutes, and S3's budget is per second, so no burst gets near it. An hour is also short enough that an operator hears about a dead gateway in the same hour.
- **After that:** a recall still has its 3 days under the outage rule. A HEAD that gets the same 503 counts as no answer. The sweep's own re-send keeps the start time, so the message comes straight back on the sweep's schedule rather than looping unseen for another hour.
- **Left, the same on main:** `tiering.py:507,644,729`, `portal_jobs.py:135,293,308` and `share_placements.py:369,390` also retry `Throttled` with no bound. `queue.throttled` is a one-line change at each. Not done here: you named recalls and verify.

**`drop` could strand work (S2). True.** It now refuses, changing nothing and saying what would be stranded, without `--force`. That covers an upload's `verify`, a `delete_blob` still `deleting`, an `annex_purge` still wanted, and `migrate`, `migrate_verify`, `seed`, `snapshot_export`, `portal`, `cloud_task` and `settings_test`, which have nothing to send them again. A letter whose work has ended drops freely. `--all` needs `--yes`, on `resend` too. `--force` names what it stranded in its output and in the audit row.

### How long

Worked out from the code, and corrected after the re-check of b903850. The text had said 3 hours, then 4, and 7 tries. There are **8 rounds**, so the reason shown to the user no longer gives a count.

A round is what the consumer does before a message dead-letters: `max_failures` 5 and `backoff_base` 5, so 5 + 10 + 20 + 40 = 75 s. `_due` in `redrive.py` then waits `least(1 h, 5 min x 2^redrives)` from the moment the letter died.

| Step | Wait before it | Total waits |
|---|---|---|
| 1st re-send (redrives 0) | 5 min | 5 min |
| 2nd (1) | 10 min | 15 min |
| 3rd (2) | 20 min | 35 min |
| 4th (3) | 40 min | 75 min |
| 5th (4) | 60 min | 135 min |
| 6th (5) | 60 min | 195 min |
| The last try (6), which needs the provider to answer | 60 min | 255 min |
| It ends (6) | 60 min | 315 min |

| | Rounds | Ends about |
|---|---|---|
| Recall or read-back | 8: the first delivery, 6 re-sends, the last try. 10 min, plus 5 h 15 | **5 h 25 min** |
| A recall throttled for its first hour | The same, after that hour | **6.5 h** |
| A read-back after read errors | The same, after about a day of `BackendError` backoff | about a day more |
| Delete or annex purge: no last try, since no HEAD decides anything | 7: 8.75 min, plus 3 h 15 and the final hour | **4 h 25 min** |
| A provider that answers nothing | Held and asked again each hour, up to `outage_limit`, 3 days from the first dead letter; then the last try and its hour | about 3 days |

The waits are checked by `test_a_recall_ends_on_the_waits_the_docs_give`, on the default config with each letter aged to 30 s either side. The 75 s round is by reading: the tests drain with no backoff.

### Upload verify

- **What a dead letter loses:** the read-back. The location stays `verified = false`, so nothing can be treated as verified: stubs, the policy engine and `api/stubs.py` all require it. The harm is the file stuck, with the edge keeping its bytes.
- **Fix:** it is sent again on the same schedule. Then a `location.verify` deny is recorded and the dead letter stays, so the alert does. An archive move's `_verifying` already acts on a deny: the copy is dropped, the original kept. It no longer sends another read-back while one lies dead, which on main made a loop of a new dead letter every two minutes, for ever.
- **A silent loop on main, found here:** a `BackendError` on the read was `Retry(30)` for ever, with a fresh message each time, so even the queue-age alert stayed quiet. It now backs off to 15 minutes and, after about a day, dead-letters.
- **Left:** an upload denied this way stays on the edge until someone runs `resend`. Nothing re-uploads it. `verify.py`'s docstring calls that the reconciler's job, and I found no code that does it.

## 2. No transaction id across a provider call

### How I looked

A pytest plugin, not committed, wrapped every storage, mover, Graph and bot client and asked Postgres at each call who held an id or a lock. Over the whole suite at `685e2a6` it listed 72 call sites. I then read the rest. `service/tests/watched.py` is the committed form: a provider wrapper for one test, counting only its own database's sessions, as #71's feed test does.

Worse than either review said: **`reconcile_container` held an id for the whole read of a bucket**, because its temporary table is created and loaded inside one transaction. On 10^8 objects that is hours with every edge's feed stopped. And `share_placements` held one across a whole-file CRC read.

### The fix: `queue.outside`

Most handlers keep their locks and re-checks as they are. `await outside(msg, "tag", call)` raises a signal the consumer catches: it commits what the handler has done, makes the call with **no transaction open**, and runs the handler again from the top with the result. So:

- no id, and no read lock either, so item 3 is closed for those paths too;
- the handler re-reads and re-locks everything, and any row moved during the call is seen, as after a `Retry`;
- `hide_for` keeps the message hidden through a long call. A row lock used to make a second holder wait.

A message no consumer read calls in place, so a test or CLI with its own transaction works as before. `Outside` is a `BaseException`, because a handler's `except Exception` swallowed it in the first version (`cloud_jobs.py`, caught by its test).

| Path | Was | Now |
|---|---|---|
| `changefeed_sync._sync_page` | `FOR UPDATE SKIP LOCKED` across `read_changes` | Advisory try-lock; read; then lock the cursor and drop the page if it moved |
| `sources/follow.py` HEAD | Inside the page's writes | `heads_to_follow` asks first; a failed HEAD still fails its own record. The same in `journal_sync` |
| `recalls.handle_restore` | `FOR UPDATE` across head, restore, status | Read, `outside`, lock, look again. A restore started for a recall cancelled meanwhile is still recorded, and a later recall joins it |
| `retention.delete_blob` | `FOR UPDATE` across tags and delete | The blob's advisory lock (`Defer` if busy), and no row lock until after. This also closes a race: a dedupe in flight holds that lock shared |
| `expire_recall_copies` | Marked and deleted in one transaction | Marks and queues; the consumer deletes |
| `sync_share_policy` | `FOR UPDATE` across ARM | Advisory lock; afterwards, looks again and records only what it did |
| `verify.handle_verify`, `tiering._copy`, `_archive_copy`, `stubs` | Read locks across the call | `outside` |
| `portal_jobs` restore and download | `FOR UPDATE` across Copy Blob | `outside`, then back through every check |
| `share_placements` | `FOR UPDATE` across the copy and a whole-file read | The same |
| `exports.step`, `expire` | `FOR UPDATE` across the upload and deletes | Advisory lock; the row after |
| `sources/run.seed_step` | `FOR UPDATE` across the inventory or listing | `outside` |
| `reconcile/run` | One transaction around the whole load | Batches of 10,000, each on its own; compare in one transaction, with nothing read from the backend in it |
| `migrate.verify_copy` | Id across `set_metadata` | `outside` |
| `settings/cloud_jobs` | `FOR UPDATE` across ARM and a listing | `outside` |

The restores consumer's visibility is now 300 s, with every call bounded at 240 s.

### Still holding an id, and why

- **The migration engine's step.** `migrate/engine.py:194` takes `FOR UPDATE OF m`, and `_advance` mixes writes with provider calls, all in one transaction: `engine.py:230,241,269,402,421`, `staging.py:112,154,188,199,275`, `waves.py:123,168`, `checksums.py:95,138,143`. **This is the largest stall left. The reviewer's estimate is minutes to hours of stall for every edge at `staging.py:112`, delaying ACL revocations too.** Left alone in this PR, as asked, and routed separately. A step's atomicity is its design (a provider error rolls back the step, `worker/migrate_jobs.py`), and `outside` would commit half a step. It needs each provider call to become its own phase, as `_plan` and `_copy` do.
- **`engine.py:683`:** deleting a bad copy under its row lock. Only on a checksum mismatch, one short call.
- **`notify/delivery.py:189,323,328,465-469,533,604,619`:** Graph and Bot Framework calls inside the handler, with writes between recipients. Not a storage call, but the same stall. Recording a card with its send is what stops a double send, so changing it needs its own care.
- **`settings/worker_jobs.py:119`:** a Settings test send, under its row's lock. An admin's click, one call.
- **`worker/crl_jobs.py:274,287`:** an AWS call under the anchor's advisory lock, with a possible state write first. Deliberate (review on #32).

### The guard, so new code is caught

`tests/provider_guard.py` wraps the backend, mover and Teams clients for the whole suite. It finds every connection in the calling frames and asks each for its transaction id. A provider call with one held fails the test, so another session's id can't fail a test or pass it, and a read lock doesn't count. A call under `outside` in place is skipped: that is a test or CLI driving a handler in its own transaction.

- **The allow-list, `KNOWN`, has 18 sites:** 12 in the migration engine, 6 in `notify/delivery.py`. Each says why it is there. All 18 were hit in the whole-suite run.
- **It shrinks:** a whole-suite run also fails on an entry nothing hit.
- **It found three things, all fixed:**
  - `sources/run.register_source` (the CLI) read the manifest with its new row uncommitted;
  - two test helpers took an id in their own transaction, by running `pgmq.read` or a non-autocommit `SELECT` there.
- **Not wrapped:** the AWS Roles Anywhere client and the Settings test senders. Those sites are named above by reading. ARM and Azure's `get_range` are wrapped since the re-check.

**What it can't see,** so don't read a pass as more than this:

- **A call on another task or thread.** Those frames don't hold the caller's connection, so the guard finds none and says nothing. What the service has today, by `grep` for `create_task`, `gather` and `to_thread`:
  - `worker/runner.py:151` gathers whole consumers, and each one's stack is whole inside its task, so it is seen;
  - `sources/metadata_s3.py` calls boto3 through `to_thread`. It is on no wrapped client, so the guard wouldn't see it either way;
  - `reconcile/blob_inventory.py` uses `to_thread` for a parquet read of what it already fetched;
  - the rest are the web, enrol and catalog sign-in paths and the sim, which are outside handlers.
- **`outside(None, ...)`.** The guard skips a call under `outside` in place, so product code passing `None` there would hide one. `test_no_call_outside_passes_none_in_product_code` fails on that literal. A variable that happens to hold `None` still gets past.

## 3. Migrations

`catalog/migrate.py` now gives each statement `lock_timeout` 5 s, gives up its transaction, lets the queue drain, and tries again: six tries, with pauses from 5 s to 60 s, about three minutes. Then it stops with a message naming the file and the sessions holding table locks. Nothing is recorded, and no superuser is needed. The sessions come from `pg_locks`, since `pg_stat_activity` hides other roles' details from a non-superuser. A plain statement in a no-transaction file does the same. A concurrent build keeps its 5 minutes, since it blocks no reader. A migration can still be held by one long session, but it now fails instead of stopping the catalog.

Test: `test_a_migration_blocked_by_an_open_reader_gives_up_and_lets_readers_past`, run as a non-superuser like every test's `migrate`, with its waits bounded and the reader closed in `finally`.

**Worker paths that still hold read locks on those tables across a provider call:**

| Path | Call | Why it stays |
|---|---|---|
| `tiering._in_place` (`tiering.py:495`) | Set Blob Tier, moments; an S3 class change, up to 6 h | The blob's lock must last through the record of the move |
| An admitted High recall (`recalls._start`) | head, restore, status, moments | The budget's lock must last until its restore is recorded |
| `retention.delete_blob` (`worm_sync.py:374,377,459`) | head, tags, delete, moments | The blob's lock, as above |
| `tiering._verifying` (`tiering.py:682`) | head, moments | Could be closed; only reached on a denied copy |

| `exports.step` (`exports.py:203`) | the upload, about a minute a part | It reads the rows as it uploads |

In the API, `api/feed.py:140` mints credentials inside a read transaction. It takes no id. A `user delegation key` call can happen there, and it holds read locks while it does.

A long S3 class change is the one that matters here: a migration during one fails and has to be run again. Closing it means a session advisory lock in `_in_place`, which I didn't do on top of #71's tests.
