# WP24: each share's quiet period (decision 67)

**Decision 67 (the owner, 2026-11-06):** the NFSv3 quiet period is set per share, by an Owner or an ArchiveAdmin, defaulting to 60 s on WORM shares and to today's period elsewhere.

Branch `claude/quiet-period-per-share`. Migration **0050**: #79 took 0047, #70 0048, and #77 holds 0049. `catalog/migrate.py` refuses a gap, so **this PR merges after #77**, or its migration is renumbered to the next free number then.

## Where the quiet period was, and what it is now

Before, one period served the whole edge: `[commit] quiet_s`, **10 s** by default (`edge/crates/omnifile-edge/src/config.rs`; the dev stack sets 3 s). It was used in four places:

- **The detector** (`omnifile-detect`): a file is reported once nobody has written it for the period (`QuietTracker`).
- **The commit's further wait** (`commit.rs`, `still_being_written`): with no NFSv4 open, a reported file must keep its size and mtime for another period. #54 added this.
- **A swept file's check** (`commit.rs`, `swept_unready`): not written within the period.
- **The namespace sweep** (`nsync.rs`, `hand_unseen`): a file no close was seen for is handed over once it has been quiet for the period plus 2 s.

Shares reach the edge as `share.upsert` feed rows (`api/rows.py`, `share_row`), kept whole in the replica. The share loop renders Samba and Ganesha config from them (`docs/design/share-provisioning.md`).

Now each share has a period:

- **Catalog:** `catalog.share.quiet_s` (migration 0050), integer seconds or null, `CHECK (quiet_s IS NULL OR quiet_s BETWEEN 10 AND 600)`. The migration writes no rows.
- **Service:** `PATCH /v1/shares/{share_id}/settings` takes `quiet_s` (10 to 600, or null for the default). It is an Owners-or-ArchiveAdmin field like `on_open`, and preview takes it too. Each change is audited in `share.settings` with `details.quiet_s = {old, new}`, where null means the default. The share's JSON carries `quiet_s` and `quiet_default_s` (60 on a WORM share, 10 on any other). `share.upsert` carries `quiet_s`.
- **Edge:** `quiet.rs` holds a table of share roots and their periods. It is rebuilt from the replica at start, before anything looks at a file, and every 5 s after (`daemon::quiet_loop`). A null period takes `[commit] worm_quiet_s` (new, 60 s) on a WORM share, and `[commit] quiet_s` on any other. A file takes the nearest share above it, as `Replica::share_of` does, and a file outside every share takes `quiet_s`. All four places above ask the table. The detector gets the table through a new `QuietSource` trait in `omnifile-detect`, and each waiting file keeps its own period.
- **Portal:** a card titled "When a file counts as finished", described below.
- **Docs:** `edge-metadata.md` (the NFSv3 limit, and a new section on each share's period), `fsal-namespace.md` (it said a WORM share may set 0), `tiers-versioning-worm.md`, `share-provisioning.md`, `ARCHITECTURE.md` (a "quiet minutes" policy knob that never existed is removed), `control-api.md` and `portal-api.md` §5.6, both OpenAPI files, the generated client, and the customer guide (§15, plus the wait in §15.3, which said "a few seconds" and is about 20).

## Behaviour

- **The defaults.** An existing share has no value, so it takes its default: a WORM share moves to 60 s when its edge is upgraded, and every other share keeps 10 s. Before the service is upgraded, a new edge already reads WORM from the row and applies 60 s. A share's default follows WORM: it moves to 60 s when WORM goes on, and back to 10 s if WORM is cancelled in its test window. An explicit value stands either way.
- **A change takes effect without a restart:** it reaches the replica through the feed, and the table within 5 s.
- **A file already waiting** takes the new period at once, measured from its last write. A shorter period lets it finish as soon as it has been quiet that long, so possibly at the next tick. A longer one makes it wait on. The commit's further wait does the same at its next look. A file already committed is not affected.
- **A file moved while it waits** into a share with a longer period waits that period again, counted from when the move is noticed. One moved to a shorter period finishes on its old one.
- **Uploads start later.** A file starts uploading about twice the period after its last write, and a little more, because the further wait is looked at with a backoff (2, 4, 8 … s). On a WORM share with the default that is about 2 minutes, where it was about 20 s.

## The range, and why

**10 to 600 s.** The service, the catalog and the edge all hold it. A stray value in a row is brought into the range by the edge, never used as it is.

- **10 s, the floor,** is today's period. A partial version needs a pause longer than twice the period, and below 10 s that is a pause under 20 s, which an ordinary NFS writeback stall can reach. Allowing less would make partial versions routine.
- **600 s, the ceiling,** has two reasons:
  - The commit's further wait is retried with `Retries::deferred`, which gives up after 10 looks, about 1,110 s in all. A longer period would leave a file to its next write. `carry.rs` has a test that the looks outlast the ceiling.
  - The detector holds one open file for each file it waits on. At 2,000 new files a second, 600 s is 1.2 million descriptors, over the unit's `LimitNOFILE` of 1,048,576. 60 s is about 120,000.

## What it does for each protocol (checked in the code)

The edge can't tell which protocol wrote a file, because Ganesha and smbd write the same xfs tree. So **the period applies to every write on the share.** What it protects differs:

- **NFSv3** has no open or close, so the period is how a file counts as finished. A pause longer than twice it keeps a partial version, then the finished file as the next version. That is the limit `tests/e2e/large_copy_test.sh` shows. On a WORM share, the partial version stays until retention ends.
- **NFSv4:** a file a client holds open for write is never committed, through `OPEN_STATE_QUERY`, however long it sits. After the CLOSE it still waits the period.
- **SMB is like NFSv3 for a writer that pauses with the file open.** `still_being_written` asks only the FSALs, so it sees only NFSv4 opens, and the daemon doesn't look for smbd's open fd on a file the detector reported. This is now written down in `edge-metadata.md`, the portal and the customer guide. It is one reason every WORM share defaults to 60 s, whatever its protocols. See the open question below.

## The portal

The card sits on the share's settings page, between Rewind and NFS security, and uses the page's existing parts: the radio options, an inline number, field hints and the `details.more` disclosure. The question up front is "How long a file must sit untouched before OmniFile treats it as finished". It offers the default, with its value and why a WORM share's is longer, or a time of the share's own, 10 to 600 seconds. One line gives the trade-off: "Longer means fewer partial versions, but uploads start later: about twice this long after the last write." Below it is one line per protocol the share serves, as in the section above.

- **On a share that serves NFSv3,** the card is up front.
- **On a share that doesn't,** it is one click down. The summary reads "Files wait N seconds after their last write. This matters most on NFSv3, which this share doesn't serve."
- **Who can change it:** Owners and ArchiveAdmins. Everyone else who can see the page sees it read-only, with the page's usual note. An out-of-range value holds back the whole save.

I checked it in the browser against the mock, on the NFSv3 share and on the WORM SMB share.

## The review's fixes (2026-11-07)

**1. A failed read of the replica dropped WORM shares to 10 s (must fix).**
- **What went wrong:** `refresh_quiet` read the shares with `unwrap_or_default()`, and each root's path with `.ok().flatten()`. An error, such as one SQLite busy error, left the table empty or a share out. The generation then moved, and every waiting file took the 10 s default. A WORM file quiet for 15 s mid-copy became due at once, so a 25 s pause would commit a partial version that can never be removed.
- **Now:** the daemon only calls `QuietPeriods::refresh`. A failed read keeps the table and its generation. So does a row that doesn't parse, or a root whose path can't be read: the table would be incomplete. A root not on disk yet is no error, because that share has no files.
- **Before the first good read, and for any path no share resolves,** the period is the longer of `quiet_s` and `worm_quiet_s`.
- **Tests:** four new `quiet::tests`, and `quiet_world` in `daemon_linux` now waits for the plain share's own 1 s, since every path starts at the longer value.

**2. The portal's default could differ from the edge's.**
- **The edge reports its defaults:** the heartbeat carries `quiet_default_s` and `quiet_worm_default_s`, kept with the other gauges in `catalog.edge.health`.
- **What the share shows:** `quiet_default_s` as the edge reported it, `quiet_applied` (false while the edge hasn't reported), and `edge_name`.
- **The portal's note:** where `quiet_applied` is false, it says "Not yet applied on its edge". The edge may be an older version, which uses its own period for every share. This was the full fix, not the plain note.

**3. Lowering a WORM share below 60 s asks first.**
- **The portal** opens a dialog titled "Wait only N seconds on <share>?". It says that a copy pausing for longer than 2N seconds keeps the half-written file as a version, which can't be deleted until retention ends.
- **The API** needs `quiet_s_confirmed: true` for it, else `400` with `quiet_s_confirmed` as the field. The audit row adds `confirmed_below_worm_default: true`.
- It is a warning, not a refusal.

## Open question for the owner

**A WORM share that serves no NFSv3 still waits 60 s.** The decision says 60 s on WORM shares, and that is what is built. The code shows an SMB client pausing with the file open is exposed just like NFSv3, so the longer default protects SMB-only WORM shares too. An NFSv4-only WORM share gains little, because its opens already hold commits, and its uploads start about 2 minutes after the last write instead of 20 s. **Recommendation: keep it as built.** An Owner can lower it to 10 s on such a share.
