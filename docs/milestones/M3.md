`docs/BUILD-PLAN.md` M3 says *what*. M3 is committed on `claude/m3-tiering`, stacked on M2.

**Exit (from the build plan, against sim; real Azure is in `real-azure-checks.md`):**
- A file goes hot → archive on schedule.
- Its stub reads trigger a rehydrate; the reader waits or fails per policy; the bytes come back verified.

## Open items found during M3

- **The M1 stub sweep overrides M3 policies.** `worker/stubs.py` `SWEEP_SQL` stubbed every file after `stub_after_minutes` unless `stub_at = never`. **Resolved (M3 integration):** the sweep now skips datasets whose active policy has an `archive_day`; the scheduler stubs those per `stub_at` (`tests/worker/test_stubs.py`).
- **The API's recall answer duplicated policy logic.** **Resolved (M3 integration):** `api/recalls.py` takes the ETA from `policy.recall.plan_recall` over the backend's `capabilities()` (`worker.backends.capabilities_for`, restore options narrowed to the object's class), with no time above the no-promise size, and decides with `decide_on_open` (`waitquick` on the ETA).
- **Decision (coordinator, M3 review): an archive copy is verified by an in-Azure CRC64 read-back before it becomes the record.** Two-account archive moves run in phases (`worker/tiering.py` `handle_move`), and no catalog lock is held across a provider call:
  1. **plan**: a transaction records a `pending` secondary location in the archive account;
  2. **copy**: Copy Blob into the archive account, landing in **Hot**. Hot has no minimum duration, so there is no early-deletion fee; Cool and Cold are never used. The location becomes `committed`, unverified, and `{"location_id"}` goes on the existing `verify` job, which reads the pinned version back and compares CRC64-NVME and length with the catalog;
  3. **verifying**: once verified, the move goes on. On a failed read-back the copy is dropped (`deleting`, then `retention` deletes it), the source is kept, the refusal is audited, and the file is tried again a day later;
  4. **archive**: Set Blob Tier → Archive in place on the copy. The archive account is LRS/GRS, so Archive is allowed there;
  5. **commit**: a transaction makes the copy the primary (`verified_by = azure_read_crc`), marks the source `deleting`, and only then queues its delete on `retention`.

  A retry adopts a copy of the right length left by a crash; it is still read back. If the source has vanished and the copy is already in Archive, the copy is kept unverified, so the edge keeps its bytes. A copy that fails its read-back is never dropped when the source is gone. WORM layouts are unchanged: in-place Set Blob Tier, nothing deleted. The flow uses only contract calls (`copy_object`, `get_range`, `set_class`), so it is the same on sim and Azure. The backends' own `set_class` archive move (copy straight to Archive) also checks length and Content-MD5 before deleting, but the worker no longer uses it.
  - **Cost:** one in-region read of every archived file's bytes, and a short Hot stay (minutes to hours, depending on the `verify` backlog and the file's size) before Archive.
- **Decision (coordinator, M3 review): in `smart` mode the archive day counts from the commit (`written`), whatever `clock` says,** so reads never postpone it (the archive date is always respected). `clock = last_read` applies to scheduled mode only (`policy/engine.py` `anchor`, `tests/policy/test_review_fixes.py`).
- **Superseded versions are tiered (M3 review).** Superseded content versions, and a deleted file's last one, follow the schedule from their commit, colder only, with no pins or stubs (`policy/scheduler.py` `sweep_versions`). On two-account layouts, retained or held versions wait, because archive there is copy-and-delete. On WORM they tier in place.
- **Decision (coordinator, 2026-10-05): when a share's WORM policy locks, its existing live versions get `retention_until = lock time + retention_days`,** not commit time + retention. This never protects less than the owner would expect from switching WORM on. Azure's container policies count from blob creation instead. Revisit if the owner prefers that.
  - This includes versions committed during the validation window: at lock they get `greatest(retention_until, lock time + retention_days)`. Retention never shrinks.
- **Decision (coordinator, M3 review): a WORM extension applies to existing versions.** Extending a share's retention to N days sets `retention_until = greatest(retention_until, committed_at + N days)` for every retained version in the share's scope; triggers re-stamp the backend copies (`retention/worm.py`, `tests/retention/test_worm.py`).
- **Reconcile matches exact versions (M3 review).** Each committed location is compared with the stored version it names (`backend_version_id`, or the current version when it has none), from a listing of every version: `VersionListing.list_all_versions` (sim, Azure `include=versions`, sim_http RPC), else `list` plus `list_versions` per key and a probe of unlisted keys. Overwritten versions and the retained versions of a deleted WORM blob are no longer drift; a lost version is. Configure Azure Blob Inventory with `includeBlobVersions` when its reader is built.
- **Change-feed sync touches only the version a record names (M3 review),** and ignores a record older than the location's last applied record or last tier move (`tier_changed_at`, which the tiering worker already sets). A record that keeps failing is retried; on the third consecutive failure it is skipped and recorded as `feed_record_failed` drift (migration 0009). `lag_report` adds `last_record_age_seconds`, so a stalled feed is visible. Reconcile also resolves change-feed drift once the location is retired or its version is back. Re-enabling WORM within 30 days of cancelling it audits `share.worm.cycling` and logs a warning.
- **Register the `verify` job in M3's runner.** **Resolved (M3 integration):** `runner.Worker` registers `verify` with its built-in consumers (restores, edge_instructions), so every worker reads uploads back, whatever starts it.
- **The worker on sim_http drives the same sim the edge uses.** `worker.backends.SimHttpBackend` (was the HEAD-only `SimHttpHeadBackend`) reads through the Blob data plane and makes every control call (tier moves, restores, change feed, retention, holds, tags, deletes, container policy) through the facade's `POST /_sim/backend` (`backends/sim_http/rpc.py`).
- **Virtual time across processes (dev and e2e only).** `backends.sim.clock.OffsetClock`: the wall clock plus an offset in a file (libfaketime's `+<seconds>` form). sim_http (`--clock offset --clock-file`), the api and the worker (`OMNIFILE_DEV_CLOCK_FILE`, dev mode only) share it, and the M3 test runs Postgres under libfaketime on the same file, so `now()` in the catalog's guards moves too. `POST /_sim/advance` moves everyone; a user delegation key that lapses is reissued and republished to the key file, and the api re-reads it.
- **WORM before the container exists.** Enabling WORM on a share whose container doesn't exist yet fails the container-policy sync (retried by the `worm_policy` sweep) until the container is created. On Azure the setup guide creates it; M4's share setup should create the container (with version-level immutability) before WORM can be enabled.
