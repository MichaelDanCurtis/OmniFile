# M5: S3 backend and the migration namespace, progress

`docs/BUILD-PLAN.md` M5 says *what*. This file records what has landed and what is next. M5 work branches from `main` (M0–M4).

**M5 is done (2026-10-21).** Its exit test passes on the dev VM, NFS half 139/139 with PR #10's checks ported (below, "Exit test, NFS half"), and service side (`test_m5_exit.py`). What only real AWS can confirm is in `real-aws-checks.md`.

## Landed

**The S3 backend, part 1** (`service/src/omnifile_service/backends/s3/`):
- `StorageBackend` over AWS's SDK (aiobotocore, Apache-2.0):
  - **put:** PutObject up to `part_size`, otherwise multipart. Either way a full-object CRC64NVME is computed here and checked by S3. An upload whose bytes don't match the expected CRC is aborted, never committed.
  - **reads:** ranged reads.
  - **listing:** listings with RestoreStatus, versions, and `list_all_versions` for reconcile.
  - **classes:** a class change is CopyObject onto the same key; copies above 5 GiB use UploadPartCopy.
  - **tags and metadata:** tags; a metadata replace keeps the storage class.
- **Tiers:** the logical-tier map and `capabilities()` are the verified S3 column, shared with sim so the two can't drift.
- **Restores:**
  - RestoreObject with `Days`; Intelligent-Tiering archive tiers take none.
  - Speed rules: no Expedited from Deep Archive or for objects of 250 MB or more.
  - A per-process token bucket keeps this process under the account's 1,000 restore requests/s.
  - A restore already running is tracked, not failed.
  - Expiry follows the backend clock, so a restored copy past its expiry is not read even while S3 still serves it.
- **Events:** EventBridge S3 events pulled from SQS through the interface endpoint (`read_changes`). Delivery is at least once: a page's messages are deleted when its cursor comes back. Another bucket's events are released, and junk is dropped.
- **Credentials and network:**
  - IAM Roles Anywhere through AWS's `aws_signing_helper` as botocore's `credential_process`, with the key in a file. It is the only provider, so a stray environment key is never used. *Superseded by decision 43: the service uses web identity from its Azure managed identity, with no key file.*
  - The edge gets a pointer, never a secret.
  - TLS 1.2 is allowed and certificates are verified.
  - With private networking, only the configured interface endpoints are used (decision 22).
- **Wiring:** `catalog.backend.kind = "s3"` builds it (`worker/backends.py`).
- **Tests** (`service/tests/s3/`):
  - the shared backend contract suite over an in-memory S3/SQS fake, directly and through one shared event loop;
  - S3-specific tests;
  - unit tests for config, error mapping, events, the restore header, TLS and the credential process.
- **What only real AWS can confirm:** `real-aws-checks.md`.

**Catalog seeding, part 1** (`service/src/omnifile_service/sources/`; design: `docs/design/catalog-seeding.md`):
- **Sources:** `catalog.source` (migration 0013) binds a bucket prefix to a folder of a dataset. Registering one sets the dataset `migrating`, starts its change feed at the inventory's snapshot (`S3Backend.change_cursor_at`), and queues the seed.
- **Readers:**
  - S3 Inventory in CSV: the manifest is checked against `manifest.checksum`, the gzip CSV is streamed, and the columns come from `fileSchema`;
  - or a listing of the prefix.
- **Rows:** one remote file per current object, with a committed content version and a committed primary location. Folders are created on demand. Everything gets the source's AD groups as its ACL, never world-readable. Keys that can't be POSIX paths, and file/folder clashes, are drift, not dropped.
- **Running it:** the worker's `seed` queue processes one idempotent, resumable batch per message. A CLI registers a source and shows its progress: `python -m omnifile_service.sources`.
- **Throughput:** about 1,500 objects/s locally.
- **Tests:** `service/tests/sources/`, over the S3 fake and Postgres.

**Seeded sources kept current** (`sources/follow.py`; design note section 8): after seeding, each S3 Created or Deleted event for a key under a source HEADs the current object and makes the catalog match: a new remote file, a new content version for an overwrite, or a tombstone. Unversioned overwrites and permanent deletes retire the old location. A folder at the path, a file whose bytes no longer come from S3, or one busy on the edge is drift `path_conflict`, never overwritten.

**Reconcile per source prefix** (design note section 9): a bucket with sources is reconciled over its source prefixes only, so the rest of the bucket isn't `unexpected`; a bucket still seeding is skipped.

**Partner API: sources** (`portal-api.md` §5.10): `POST /v1/sources` (`Archive.Adopt`, or an ArchiveAdmin session) registers a source; `GET /v1/sources[/{id}]` follows its seeding; `POST /v1/sources/{id}/retry` resumes a failed one. `POST /v1/adopt` catalogs data Prizmanyx already moved into the dataset's own backend, at its original paths, with no migration (`source.kind = 'adopt'`, migration 0015). `web` writes only the catalog; the worker's first seed step reads the snapshot and starts the feed.

**Partner API: reads** (`portal-api.md` §5.11, `Archive.Read`): `GET /v1/files?dataset_id&path` (catalog rows by path: tier, where the bytes are, archive date, hashes, duplicates, holds); `GET /v1/restores`; `GET /v1/events?after=` (the catalog's ordered pull feed, long-lived cursors); `GET /v1/usage` (bytes and monthly storage cost by tier, share and dataset, from a daily snapshot, migration 0014).

**Migration engine, part 1** (`docs/design/migration-engine.md`; `migrate/`): `POST /v1/locations` asks for a prefix of a migrating dataset to move to its own backend. The worker's `migrate` queue runs a Storage Mover job through the `Mover` port (a sim mover in tests and e2e; `copy: external` when Prizmanyx copies), finds the copies under `migrated/<bucket>/`, and checks each one on `migrate_verify`: a full CRC64-NVME read in Azure against the S3 object's own checksum (decision 24). A bad copy is drift `checksum_mismatch`, removed, and copied again by the next Additive run. POSIX metadata is stamped on a good copy. When every live file has a verified copy of its current content and the bucket's events are applied past the run's start, the prefix cuts over: copies become primary, S3 objects secondary, and the dataset is `cut_over` once nothing comes from S3. Migration 0016.

**Migration engine, part 2:** the Azure Storage Mover client behind the `Mover` port (`migrate/storage_mover.py`), over ARM's REST API with the worker's managed identity: Additive job definitions on the customer's endpoints, runs and their counters. The worker takes it from `OMNIFILE_STORAGE_MOVER`; the Bicep passes `storageMoverConfig` and grants the custom "OmniFile Mover Operator" role.

**Migration engine, restore waves** (design note section 8; `migrate/waves.py`, migration 0017): a verifying prefix with archived objects that have no copy gets an S3 Batch Operations restore job (Bulk, 14 days), with a `catalog.restore` row per object that Restore Completed events update. Any restore under the prefix completing, a wave's or a user's recall (decision 15), makes the next Storage Mover run start within the hour. The S3 backend's `batch` config names the account, role and manifest bucket.

**Migration engine, checksum jobs** (design note section 5; `migrate/checksums.py`): S3 objects written before S3 kept a CRC64NVME get one from an S3 Batch Operations Compute checksum job, read from its completion report, so their copies can be verified (decision 24). Objects it can't checksum (SSE-C) are counted in the prefix's `last_error` and are not cut over.

**Migration engine, staging copies** (design note section 4; `migrate/staging.py`, migration 0018): a user's recall of an object under a migrating prefix is copied inside S3 into the backend's `staging_bucket`, and a small Storage Mover run moves it onto the real target path, so it is copied, verified and served from Azure without waiting for the prefix's next run. The staging object is deleted once the copy is verified. The recall worker marks a restore of an object under a migrating prefix `migrate_on_complete` (decision 15), and a staged recall doesn't also start a rerun of the whole prefix.

**Edge reads of S3-resident files** (R1's read path; `fsal-namespace.md` §5.3, `control-api.md` §3): the service mints a presigned GetObject URL for one object version, signed for the edge's own interface endpoint (`edge_credentials = presigned`, credential mode `s3_presigned_url`), and the edge fills the placeholder with ranged GETs (`BlobClient::get_s3_range`: length and `x-amz-version-id` checked, TLS 1.2 allowed). S3 ranges carry no checksum, so a fill from S3 widens the marker only once, after the whole-file CRC-64/NVME matches: no S3 byte is readable before the whole file is verified. Edge errors redact `X-Amz-Signature` and `X-Amz-Security-Token`. *Decision 43 makes Roles Anywhere the edge's default; presigned URLs are the fallback.*

**Point-in-time listings for rewind trees** (`control-api.md` §4.5; decision 30): `GET /v0/edges/{id}/asof?dir_id&t` returns a directory's entries as they were at `t`. Each entry has the content version valid then and that version's own location, and is read with `POST …/credentials` for that version. Requests are refused beyond the share's rewind depth. This is the service half of `.snapshots/` and Previous Versions. On the edge, the daemon creates label directories from each share's rewind settings and answers `POPULATE_DIR` from `asof`. It creates read-only placeholders of the versions valid at the label and unpopulated subdirectories, erring towards fewer rights on ACLs (`fsal-namespace.md` §7). Reading a rewind placeholder fetches or recalls that version into it, and never into the live file. The FSAL's `.snapshots` routing and Samba's Previous Versions are next.

**The portal's Migrations page** (ArchiveAdmin): the prefixes being moved, with state in plain words and files verified out of total, and the sources with their cataloguing state and last problem. It reads `GET /v1/locations` and `GET /v1/sources` and refreshes every 30 s.

## Exit test, service side

`service/tests/api/test_m5_exit.py` runs the M5 gate (`BUILD-PLAN.md` M5) against the S3 fake and sim, through the real `api` app, the real S3 backend and the worker's handlers:

1. A bucket with Standard, Glacier and Deep Archive objects is seeded into a dataset. The edge's feed carries all three at their paths, with their S3 locations. The Standard one reads at once through a presigned S3 URL.
2. A user's read of the Glacier object starts an S3 restore (`migrate_on_complete`), and the recall's states go to the notify queue (the Teams card). When the restore completes, the recall is `downloading` with a presigned URL for that version. The restore is staged and copied by a Storage Mover run, without rerunning the prefix.
3. The Deep Archive object comes back the same way. Every copy is verified by an in-Azure CRC read, and the prefix and the dataset cut over. No staging object is left, and nothing is deleted in S3.
4. **No client-visible change:** the feed after cutover shows the same files, parents, names, sizes, content versions, owners, modes, times and CRCs. Only the location changes, and an online read now gets an Azure SAS.

Removing the staging step, or the flip, fails it.

## Exit test, NFS half

`tests/e2e/m5_exit_test.sh` runs on the M1 stack (`dev/scripts/install-*.sh`): Ganesha V15.6 with `FSAL_OMNI` under its real unit, the daemon with its smb-guard on xfs, and the service units. The sim facade hosts the S3 sim (`--s3`). Reads go through libnfs (`fsal/tests/nfsc.py`). It never retries, so each JUKEBOX or DELAY is seen, and it needs no kernel NFS client. The test proves:

1. A bucket with a Standard and an archived object is registered as a source of a share's dataset (`python -m omnifile_service.sources register`). The worker seeds it from a listing. Both files are in the catalog with one copy each, the S3 object; nothing is in Azure.
2. The edge materialises both as placeholders, full size, with no data on disk. NFSv3 and NFSv4 list them.
3. The Standard object reads over NFSv3 on the first try, byte-identical with no zero blocks, and over NFSv4 too. It needs no restore. The local copy has the object's CRC-64/NVME, and the catalog still has one copy, on S3, now with the CRC S3 stores for it.
4. The archived object answers JUKEBOX (NFSv3) and DELAY (NFSv4), never ENOENT, and starts an S3 restore. Once the sim's clock passes the restore time, the same reads return its bytes.
5. **SMB Previous Versions:** a standalone smbd with the stanza `render_smb` emits lists a folder of today's unfilled label. The daemon's smb-guard holds the open while the folder fills from the as-of listing. The listing shows both files, and a file read from that version has its bytes.
6. **Previous Versions → Open** (decision 36): Ubuntu's smbd opens `deep/d.txt` directly in yesterday's unfilled label.
   - Through `shadow_copy2` alone it is `NOT_FOUND`.
   - With `vfs_omnifile_prevver` (`samba-vfs/`) installed and named by `omniacl render`, the file has that version's bytes, and the label and `deep` were filled by the guard.
7. **Shares from the catalog** (the script's step 9; M6, `docs/design/share-provisioning.md`). The daemon renders the exports Ganesha serves (`[shares] render`), and `ganesha.conf` includes them:
   - the seeded share is served from the daemon's rendering;
   - a share added in the catalog (the rows `POST /v1/datasets` and `POST /v1/shares` make) is rendered with its export id, and Ganesha is reloaded and serves it over NFSv3 and v4, while the other share keeps serving;
   - a removed share is no longer rendered or served, and its folder stays;
   - Ganesha stays up through both reloads.
8. **Renames and deletes reach the catalog** (the script's step 10; `docs/design/namespace-sync.md`). Over NFS and from a shell, against the real service:
   - a file renamed, moved to another folder, and moved with its renamed folder keeps its catalog id each time;
   - a local `chown` gives it its new owner in the catalog;
   - an unlinked file, a removed folder, and a folder removed whole from a shell are tombstoned, and nothing deleted comes back on the edge;
   - every rename, unlink and owner op in the edge's outbox is acknowledged.
9. **A service outage** (the script's step 11; M7 chaos). A file whose bytes are only in S3 (a second bucket, seeded as its own source) is read with the control API stopped, for 20 s, over NFSv3 and v4:
   - every answer is "not yet" (JUKEBOX, DELAY) or an error, never bytes and never ENOENT, and the placeholder stays empty;
   - once the API is back, the same read returns the object's bytes, with no zero blocks, over both versions;
   - the daemon stays up throughout.
10. **Network loss** (step 12; M7 chaos): every packet from the daemon to the backends and the control API dropped. NFS calls still answer within the FSAL's park time, S3-only reads fail closed, a file written meanwhile is kept; the link then comes back as through a stateful firewall that forgot the flows open during the outage, and the read and the upload complete with the daemon never restarted.
11. **The daemon killed mid-fill** (step 13; M7 chaos): SIGKILL during the whole-file fill of a restored Glacier object from S3, with an NFSv3 and an NFSv4 reader waiting. No reader gets bytes before the whole-file CRC matched; systemd restarts the daemon, Ganesha stays up, and the fill resumes where it recorded its progress. Online objects take the chunk path since decision 44, so the object is archived.
12. **Range reads** (step 14; decision 44): ten ranges at random offsets of a 160 MiB S3-resident object over NFSv4 are byte-identical and fetch only the chunks they touch (44 MiB from S3: 11 chunks and the header prefix). The file stays a placeholder with a chunk map, never filled whole. NFSv3 reads the same ranges with no S3 bytes, and so does NFSv4 after a SIGKILL of the daemon.
13. **A migration** (step 15; ported from #10, `migration-engine.md`): a prefix of a third bucket moves to Azure (`request_location`, the worker's sim Storage Mover):
   - a user deletes an S3-resident file over NFSv4; an NFSv4 reader holds another open;
   - a user reads a Glacier object that no copy has reached: "not yet", a restore with `migrate_on_complete`, its bytes once restored; the restore is staged (an S3 copy into OmniFile's staging bucket), copied into Azure by a staging run and verified;
   - the prefix cuts over using that copy, with no rerun of the whole prefix, and the staging object is deleted;
   - the held fd reads the whole file across the cutover, byte-identical, same inode; an object first read after the cutover comes from Azure;
   - the cutover report lists the deleted file and who deleted it: the NFS user's identity, `claimed`.
14. **No write to a source bucket** (step 16; decision 40): the sim's per-bucket counters show no PUT, COPY, DELETE, tagging, retention or policy request by OmniFile on any source bucket in the whole run. Its only S3 writes were the staged copy into its staging bucket and that copy's delete.

**On the dev VM** main's test first passed 89 of 92. What each failure was, and what the new steps found:

- **VM setup.** Previous Versions -> Open (step 8): `vfs_omnifile_prevver` was never built there. `dev/scripts/install-e2e-tools.sh` now builds it for the VM's smbd and stages it where the test finds it; `samba-vfs/build.sh` refused the arm64 build, whose module also needs glibc's dynamic loader (`__stack_chk_guard` lives there on arm64). The outage's held flows (step 12): Ubuntu's kernel has no `/proc/net/nf_conntrack` and the VM had no `conntrack` tool. The FSAL module installed on the VM predated #25, so NFS changes had no actor (`unknown`); the results now name the daemon and module that ran.
- **The test, after the product moved.** Step 13 assumed an online object is filled whole; since #23 the chunk cache serves it and never records fill progress, so the step now kills the daemon during a restored object's whole-file fill. `e2e.py backdate` set every version to one time; since migration 0030 a file's create and content are two versions, so an as-of listing held both and the daemon found no rewind placeholder (step 8); it now moves the history back as one block. The virtual clock now restarts at real time each run.
- **A product bug** (found by step 15): an edge op on a file whose version is dated ahead of the catalog's clock (a seeded S3 object commits at its LastModified, S3's clock) was refused with a 500, so a user's delete of a freshly seeded file ended as a conflict in the edge's outbox, never in the catalog or the cutover report. Migration 0031 commits such a version at its predecessor's time (`tests/api/test_commit_floor.py`).

One check is intermittent: step 10's local chown failed to reach the catalog in 2 of 12 full runs on the VM, both while the host was heavily loaded, and never in isolation (6 tries) or in the 5 runs since. It is not root-caused (the namespace sync's owner change racing the ACL scan, or a lost pass, are the suspects).

On the dev VM, run it with `tests/e2e/run.sh --m5` (or `--m5-test`). M4's exit test passes on the same VM too (15/15 service-side checks, 10/10 Playwright; `tests/e2e/results/m4-latest.md`), once the M4 stack's dev certificates carried key identifiers, which the VM's Python requires.

The first runs found four bugs. Each is fixed, with a test that fails without its fix:

- **Seeded S3 files could not be read at all.** A listing or an inventory gives no CRC, and every fill is checked against the file's CRC, so the edge refused to fill them. The service now learns the CRC S3 stores (HEAD with checksum mode), records it on the location and the file, and puts it in the S3 read credential. The edge uses it when its replica has none yet (`control-api.md` §3). The migration engine also sets the file's CRC when a copy verifies or a Compute checksum job reports. Before, a seeded file that was never read had no CRC, so it could not be filled from Azure after cut-over either. Tests: `test_m5_exit.py`, `test_engine.py`, the daemon test `an_s3_fill_is_verified_against_the_credentials_crc_when_the_replica_has_none`.
- **The guard reported new placeholders as user writes.** The daemon sizes a placeholder before setting its marker, and the notification watcher took that `FS_MODIFY` for a write into a `PARTIAL` file's local prefix. The daemon then filled the file whole and committed it as a new version. A file with nothing resident has no local prefix, so the watcher now ignores it (A-suite x01).
- **Seeding from a listing failed on Azure-style ETags.** The listing reader treated any ETag as the MD5 whenever the backend knew one. It now does so only when the ETag is that MD5 (`test_seed.py`).
- **A backend added after the worker started was unknown to it**, and the source's seed messages were dead-lettered. Backend rows are read at start, with the dev-clock and sim checks, so the error now says to restart the worker.

Objects S3 stores no CRC for (written before S3 added them) still can't be read through the share. They become readable once the migration's Compute checksum job records their CRC, or once they are copied to Azure.
