# Checks that need a real Azure subscription

Everything below was built and tested against the simulated backend, Floci or mocked SDK transports, but can only be confirmed on real Azure. Run them in the scheduled real-Azure lane (test strategy, layer 3) or during pilot 4. Each line names where the assumption lives.

Each line has an id (`RA-nn`). The real-cloud harness maps every id to an automated check, a step of the M6 exit, or a recorded manual step (`tests/real/harness/checks/azure.py`; a test fails if a line has no mapping). `tests/real/run.sh all --cloud azure` runs them on a subscription the owner has put on `tests/real/allow-list.local`, then tears everything down. `tests/real/collect.py` ticks a line only from a real run, with the run id and its evidence under `tests/real/results/<run id>/`. A manual step is recorded with `collect.py --record RA-nn=pass`. How to run it: `tests/real/run.sh`'s header, and `docs/milestones/results/wp5.md`.

## Storage behaviour

- [ ] RA-01 **CRC64 mismatch error code.** `sim_http` and the Azure backend return or expect `Crc64Mismatch` for a bad `x-ms-content-crc64`. Microsoft documents only a 400. (`backends/sim_http`, `backends/azure`)
- [ ] RA-02 **Change-feed event mapping**, from Azure's event types and schema v4 fields to our `ChangeKind`. (`backends/azure/changefeed.py`)
- [ ] RA-03 **Rehydrate-copy target.** Can a Copy Blob rehydrate from an LRS archive account target the ZRS live account? Until confirmed, the recall copy stays in the archived blob's own account; sim uses `live/recall`. (`backends/azure`, `worker/restores`)
- [ ] RA-04 **Smart tier with versioning and immutability.** It's undocumented, so Smart isn't offered for WORM shares. (decision 31, `tiers-versioning-worm.md`)
- [ ] RA-05 **Set Blob Tier on locked version-level WORM blobs:** to Archive and back, plus early-deletion billing within 180 days. (decision 31)
- [ ] RA-06 **Real recall times** for files of 8 GB, 184 GB and 1.2 TB at Standard and High priority. (pilot 4; sets the portal's ETA table)
- [ ] RA-07 **Change-feed lag** under load. (M3 exit)
- [ ] RA-08 **Listing with `include=versions`** returns every version with its version id, tier and length, for reconcile's (key, version) join. (`backends/azure` `list_all_versions`, `reconcile/`)
- [ ] RA-09 **Deleting the current version by version id.** The archive move calls `delete_blob(version_id=…)` on the source's current version, and Azure may refuse to delete the current version that way. (`backends/azure` `_archive_move`)
- [ ] RA-10 **Archive-copy read-back, then Set Blob Tier Hot → Archive on the copy** (two-account archive; coordinator decision). Copy Blob from the live ZRS account into the LRS archive account lands Hot. A CRC64-NVME read-back through the private endpoint matches the catalog. Set Blob Tier → Archive in place then works on that copy, with no early-deletion fee for the short Hot stay. Measure the read time per TB. (`worker/tiering`, `worker/verify`)
- [ ] RA-11 **Get Block List for a version.** `versionid` selects that version's committed block list, which `complete` checks. Azure returns no per-block CRC; it validates each block's `x-ms-content-crc64` at Put Block. (`backends/azure` `committed_blocks`)
- [ ] RA-12 **Forwarded-certificate trust.** `OMNIFILE_API_TRUSTED_PROXIES` / `ingressSourceCidrs` match the Container Apps ingress source addresses, and a client can't reach `api` except through ingress. (`api/clientauth.py`, `deploy/azure`)
- [ ] RA-13 **Floci's coverage.** It checks neither SAS signatures nor CRC64, so its lane proves request shapes only. (`.github/workflows/floci.yml`)

## Storage Mover (migration engine, `docs/design/migration-engine.md`)

- [ ] RA-14 **Additive (merge) and a changed source.** A rerun overwrites a target whose S3 object changed since the last run. If it skips existing names instead, the engine must delete stale copies before a rerun. And `GET` on a job definition names a running run in `latestJobRunName` and `latestJobRunStatus`, which is how a run a crashed step started is found and not started twice (`AzureStorageMover.running_run`). The engine asks before it changes the job, so a `PUT` refused during a run can't lead to a second run; check whether ARM does refuse that `PUT`, and that a job definition that doesn't exist answers 404. (`migrate/mover.py`, `migrate/engine.py`)
- [ ] RA-15 **Unrestored Glacier objects** in a prefix come back as failed or unsupported, and the run still succeeds. (`migrate/engine.py` copying → verifying)
- [ ] RA-16 **A private-only target account** (public network access disabled) can be written by Storage Mover. (decision 22, pilot)
- [ ] RA-17 **Run status** from `azure-mgmt-storagemover`: states and counter names, as `MoverRun` maps them. (part 2, the Azure client)
- [ ] RA-18 **Verifier read rate** in Azure per worker replica, to size verification of a large prefix. (`worker/verify.read_crc`)

- [ ] RA-27 **The custom storage roles are enough and no more** (M7 review): with only **OmniFile SAS Minter**, `api` mints a read SAS and a `cw` SAS an edge uploads with (Put Block, Put Block List with metadata), and a delete through either SAS is refused; with **OmniFile Blob Worker**, the worker gets a user-delegation key and a portal download link works. - [ ] RA-28 **Per-app database privileges on Azure Database for PostgreSQL** (M7, `catalog/privileges.py`): run `migrate` as the Entra administrator with `OMNIFILE_DB_MEMBERS` naming each app's `pgaadauth` principal. Check that the group roles are created, that each principal inherits its role's privileges, that the owner-run functions (owned by the Entra administrator, not a superuser on Azure) create and drop partitions and ANALYZE when the worker calls them, and that every app works with only its grants.
- [ ] RA-29 **Each app signs in to PostgreSQL with Entra as its own role** (`catalog/connect.py`; `deploy/azure/README.md`, "The catalog connection"): `api`, `enrol`, `web`, `worker` and the verifier job each connect with their managed identity's token over `verify-full` (the container's CA bundle accepts the server's certificate), `SELECT session_user, current_user` shows `id-<prefix>-<app>` and `omnifile_<app>` (the verifier: `omnifile_worker`), and a connection opened more than an hour after start still signs in (the token is renewed). A wrong `AZURE_CLIENT_ID` or a missing membership stops the app at start with the error, and no token appears in the logs.
- [ ] RA-30 **Direct replica access inside the internal environment** (M7 review; T5, with `apiIngress = tcp`, the default): `api` terminates mutual TLS itself on 8443 behind a TCP ingress. From a container in the internal subnet (the harness uses `api`'s own, since `web` can scale to zero at `deploymentSize=small`), check two things: a connection to `api` without an edge CA client certificate is refused at the handshake, and a request carrying a forged `X-Forwarded-Client-Cert` authenticates nobody (direct TLS refuses the header). Also check that the TCP ingress and its NSG rule reach `api` from the edge networks and the relay's environment, and that the ingress IP restrictions apply to TCP. The local proof is `service/tests/api/test_t5.py` and `deploy/images/smoke.sh`'s `api` step. (`api/clientauth.py` `DirectTls`, `deploy/azure` `apiIngress`; `docs/design/threat-model.md`, T5)

## Tiering a shared blob (WP21)

- [ ] RA-53 **A repeated Copy Blob while one is pending.** How Azure answers when the destination has a copy still running: 409 `PendingCopyOperation` is assumed, not seen. It matters when a worker dies, or a call passes its bound, in the middle of an archive copy: the retry starts the copy again. `_copy`'s `existing()` looks only at length and tier and ignores the copy's status, so it can take a copy still pending for a finished one, and the read-back then decides. Check that a pending copy reports its final length, and that the retry reaches the end rather than dead-lettering. (`worker/tiering.py` `_copy`, `backends/azure/backend.py` `copy_object`.)

## A file's own copy of a shared blob (WP26, decision 66)

- [ ] RA-54 **Copy Blob within one account, out of Cool and Cold, into Hot.** The source stays where it is, with its tier and clock unchanged. Sim assumes this, and that the copy is online at once or within `_wait_copy`'s bound. (`worker/tiering.py` `_copy`)
- [ ] RA-55 **Copy Blob out of a version under locked version-level WORM, into the same container, with a default policy on it.** Microsoft says immutable blobs "can be created and read". No page we have read shows this exact case, so it isn't proven. A refusal ends in the fallback. (`_copy`, `tiers-versioning-worm.md`)
- [ ] RA-56 **A file's copy into Archive within one account under version-level WORM:** landing in Hot, read back in full, then Set Blob Tier to Archive, with the original untouched and another copy of it running. It is how a file's archive date is kept while another file's split runs. (`_in_place`, `_archive_copy`)
- [ ] RA-57 **Retention and a legal hold on the copy's version,** set after it landed, in a container with a default policy: that Set Immutability Policy takes a date on a version the default already covers, and that `head` shows both. (`retention/worm_sync.py` `stamp_worm`)
- [ ] RA-58 **Does Azure accept a past retention date?** OmniFile no longer sends one (`stamp_worm` clears the flag when retention has ended), so the answer only tells us what the older code risked. Sim accepts it, and refuses to shorten a locked one. Record the answer for both an unlocked and a locked blob.
- [ ] RA-59 **What a split bills:** on a real bill, a retrieval for the read out of Cool or Cold, Copy Blob's operations, and no early deletion on the blob that stayed. Then the second blob's storage from that day. The prices are the repo's, marked `verify: true`. (`docs/milestones/results/wp26.md`)
- [ ] RA-60 **Retiring a replaced row:** after retention ends, delete the old version by id under a container policy that still covers newer versions. The worker's daily sweep does this, through `delete_blob`. (`retire_replaced_secondaries`)
