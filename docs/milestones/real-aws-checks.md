# Checks that need a real AWS account

The S3 backend (`service/src/omnifile_service/backends/s3/`, M5) was built and tested against an in-memory S3 and SQS (`service/tests/s3/s3_fakes.py`). The fake answers botocore at `before-call`, so requests go through the SDK's parameter validation and serialization, but S3's behaviour is the fake's. The shared backend contract suite passes over it. Everything below can only be confirmed on a real account. Run the checks in a real-AWS lane (to be added like the real-Azure one) or during the client-site pilots. Each line names where the assumption lives.

Each line has an id (`RW-nn`). The real-cloud harness maps every id to an automated check or a recorded manual step (`tests/real/harness/checks/aws.py`; a test fails if a line has no mapping). `tests/real/run.sh all --cloud aws` makes tagged buckets, a queue, Batch Operations jobs, a Roles Anywhere trust anchor and an EC2 probe behind interface endpoints in an account on `tests/real/allow-list.local`, runs the checks, and tears it all down. `tests/real/collect.py` ticks a line only from a real run, with the run id and its evidence under `tests/real/results/<run id>/`.

## Storage behaviour

- [x] RW-01 **Full-object CRC64NVME on multipart uploads.** `CreateMultipartUpload` with `ChecksumAlgorithm=CRC64NVME, ChecksumType=FULL_OBJECT`, per-part `ChecksumCRC64NVME`, and the whole object's CRC on `CompleteMultipartUpload`. HeadObject with `ChecksumMode=ENABLED` then returns the full-object CRC that the catalog keeps. (`backend.put`) (passed in run rr-202611150718-62e9: tests/real/results/rr-202611150718-62e9/RW-01.json)
- [ ] RW-02 **UploadPartCopy and the full-object CRC.** For copies above 5 GiB, whether S3 computes a full-object CRC64NVME when the parts carry none, or whether `CompleteMultipartUpload` must be given one. (`backend._copy`)
- [x] RW-03 **CopyObject with `ChecksumAlgorithm=CRC64NVME`** keeps the same CRC as the source; the verifier (decision 24) relies on it. (`backend._copy`) (passed in run rr-202611150718-62e9: tests/real/results/rr-202611150718-62e9/RW-03.json)
- [ ] RW-04 **The x-amz-restore header after expiry.** The backend reports EXPIRED from the expiry date on its own clock while the header is still there. S3 removes the restored copy, and the header, asynchronously; after that, HeadObject reads as plain ARCHIVED. Measure the gap, and confirm that GetObject in that gap still serves bytes (the backend refuses to). The catalog's expiry tracking (later M5) is the authority. (`backend._restore_state`)
- [x] RW-05 **ListObjectsV2 `OptionalObjectAttributes=RestoreStatus`** on a bucket reached through an interface endpoint. (`backend.list`) (passed in run rr-202611150718-62e9: tests/real/results/rr-202611150718-62e9/RW-05.json)
- [ ] RW-06 **RestoreObject on an already-restored copy** extends the expiry (200) and on an ongoing restore answers 409 `RestoreAlreadyInProgress`. (`backend.restore`)
- [ ] RW-07 **Intelligent-Tiering archive tiers:** `ArchiveStatus` on HeadObject, RestoreObject without `Days`, and the object back in the frequent tier with no x-amz-restore expiry afterwards. (`backend._restore_state`, `backend.restore`)
- [x] RW-08 **ETag as MD5** for single-part uploads under SSE-S3, and not under SSE-KMS. Buckets with default SSE-KMS give no MD5 from HeadObject; the verifier then needs S3 Batch Compute checksum. (`backend._head_from`) (passed in run rr-202611150718-62e9: tests/real/results/rr-202611150718-62e9/RW-08.json)
- [ ] RW-09 **Real restore times** for Flexible Retrieval and Deep Archive at Standard and Bulk, for 8 GB, 184 GB and 1.2 TB objects. These set the ETA table. (`capabilities`, pilot)

- [x] RW-17 **HEAD with checksum mode on an archived object** returns its full-object CRC64NVME without a restore, and which older objects have none (the verifier then needs a Batch Compute checksum job). - [ ] RW-18 **Batch Operations restore waves:** CreateJob with `S3InitiateRestoreObject` from a CSV manifest (URL-encoded keys, with and without version ids), through the S3 Control interface endpoint with private networking; each object's Restore Completed event reaches the queue as for a single restore; DescribeJob's status and counts. - [x] RW-19 **Batch Operations Compute checksum:** CreateJob with `S3ComputeObjectChecksum` (`ChecksumAlgorithm=CRC64NVME`, `ChecksumType=FULL_OBJECT`) and a completion report with `ReportScope=AllTasks`; the report's layout (`<prefix>/job-<id>/manifest.json` listing results CSVs), its key encoding (URL-encoded as in the manifest?), the `ResultMessage` JSON's field names (`checksum_hex` or `checksum_base64`), the error rows for SSE-C objects, and whether reading the report needs `ExpectedBucketOwner`. - [ ] RW-20 **Presigned GETs for edges (fallback since decision 43):** a URL signed by the service from its **web-identity** session (`AssumeRoleWithWebIdentity` from the managed identity; the pre-decision-43 Roles Anywhere signer is retired) for the edge's interface endpoint host works from the edge over PrivateLink with TLS 1.2; its lifetime is capped by that web-identity session's (check the real cap and what happens to an outstanding URL when the session is renewed); ranged GETs of a named version return `x-amz-version-id`; an archived object answers 403 `InvalidObjectState`. (`S3Backend.edge_credential`, `omnifile-blob` `get_s3_range`)
- [x] RW-21 **Edge Roles Anywhere (the default since decision 43):** the edge's TPM-held key gets temporary credentials through `aws_signing_helper`; the role's policy and profile give read-only access to the source prefixes only, `aws:SourceVpce` restricts it to the interface endpoint, the session lifetime is at most 1 h, and revoking the edge's certificate at the trust anchor stops new sessions. - [ ] RW-22 **A trust anchor from OmniFile's edge CA (decision 50):** `CreateTrustAnchor` with source type `CERTIFICATE_BUNDLE` takes the edge CA's certificate (ECDSA P-384, self-signed by the Key Vault key, `init-kv-ca`), and a certificate `enrol` issued (`POST …/aws-certificate`, ECDSA P-384/SHA-384 signature over a P-256 key, `OU=omnifile-roles-anywhere`, `CN=omnifile-edge-<id>`, clientAuth, 30 days) gets a session through `aws_signing_helper` from the edge. (`enrol/ca.py`, `deploy/aws/README.md` step 2)
- [x] RW-23 **The profile's and role's certificate conditions (decision 50):** the trust policy's `aws:PrincipalTag/x509Subject/OU = omnifile-roles-anywhere` and `x509Subject/CN = omnifile-edge-<id>` (or the `sts:SourceIdentity` `CN=omnifile-edge-<id>`), and `aws:SourceArn` = the trust anchor, let in that edge's Roles Anywhere certificate and refuse: its mTLS certificate (same CA, no OU), another edge's certificate, and a certificate from another trust anchor. The session's name is the certificate's serial (hex), which the audit row `edge.roles_anywhere.sign` records. (`deploy/aws/iam/edge-role-trust.json`) (passed in run rr-202611150718-62e9: tests/real/results/rr-202611150718-62e9/RW-23.json)
- [ ] RW-24 **CRL import and update (decision 50):** the worker's `ImportCrl` (PEM, `enabled: true`, tagged `omnifile-trust-anchor=<id>`) and later `UpdateCrl`, with the service role's web-identity session through the Roles Anywhere interface endpoint; that the tag-on-create needs `rolesanywhere:TagResource` or not; that the policy's `aws:RequestTag` / `aws:ResourceTag` conditions (`deploy/aws/iam/service-crl-policy.json`) allow exactly that; that a revoked edge's next `CreateSession` is refused within a minute of the upload (how long Roles Anywhere takes to apply an updated CRL), and live sessions run out within the hour; what Roles Anywhere does when the CRL's nextUpdate (30 days; refreshed weekly) passes; that `ListCrls` finds the CRL after a lost `ImportCrl` answer. (`worker/crl_jobs.py`) Seen with the harness's own identity in run rr-202611150718-62e9 (tests/real/results/rr-202611150718-62e9/RW-24.json): a CRL that revokes nothing is refused on `ImportCrl` and on `UpdateCrl`; one whose only entry is a stale serial is accepted; the revoked certificate's `CreateSession` is refused within a second; `ListCrls` finds the CRL. Left: the service's web-identity session and its tag conditions, and nextUpdate passing.
- [ ] RW-25 **Restore budget under a wave:** while an S3 Batch Operations restore job runs, single `RestoreObject` calls (user recalls) still succeed, or get `SlowDown` that a retry clears; that the job's own pace stays within the account's 1,000/s. - [ ] RW-32 **S3 Metadata tables** (built behind a per-source choice until this passes; `docs/design/s3-metadata.md` §5, `sources/metadata_s3.py`, `worker/journal_sync.py`). The local tests use a PyIceberg SQL catalog with the published schemas, so on a test bucket of about 10^5 objects with a metadata configuration (journal and live inventory), check:
  - **Endpoint and signing:** PyIceberg's REST catalog at `https://<s3tables_endpoint_url>/iceberg`, `warehouse` = the `aws-s3` table bucket ARN, SigV4 signing name `s3tables`, from a VPC with only the `s3tables` and S3 interface endpoints (no internet), TLS 1.2. Credentials from the service's web-identity session (decision 43) once it is built, Roles Anywhere until then (`credentials.botocore_session_for`).
  - **Data files:** the table bucket's Parquet and metadata files read by pyarrow through the S3 interface endpoint (`s3.endpoint` = `endpoint_url`; virtual-hosted or path-style addressing against `bucket.vpce-…`), and that a read of a known file never needs a LIST.
  - **Names:** the namespace for a bucket with `-` or `.` in its name (`b_<bucket>` as written, or mangled), and the table names `inventory` and `journal`.
  - **Schemas:** the column names and types the reader takes (`key`, `sequence_number`, `version_id`, `is_delete_marker`, `size`, `last_modified_date` as timestamp without zone, `e_tag` with or without quotes, `storage_class`, `is_multipart`, `encryption_status`, `record_type`, `record_timestamp`), and `version_id` for an unversioned object (null, or `"null"`).
  - **Versions in the inventory table:** that it lists noncurrent versions and delete markers (the reader assumes so and picks the newest `sequence_number`); if it lists only current rows, the reader's index pass can go. Its memory on 10^5 objects.
  - **Backfill and lag:** the backfill time and cost; how stale the inventory table's current snapshot is against its `timestamp_ms` (the reader assumes at most an hour, `INVENTORY_LAG`); the journal's lag from a PUT to its row.
  - **Snapshots:** how long the inventory table keeps a snapshot (a seed that outlives its pinned one starts again); journal compaction shows as `replace` snapshots, and incremental append scans skip them; a journal cursor behind an expired snapshot reads by `record_timestamp`.
  - **Journal rows:** a delete marker is `DELETE` with `is_delete_marker = true` (and its `version_id`), a permanent version delete is `DELETE` with that version, a lifecycle transition is `UPDATE_METADATA` with the new `storage_class`, and keys are not URL-encoded.
  - File Gateway's `x-amz-meta-file-*` in `user_metadata` (not used yet; `catalog-seeding.md` §11).
  - **Zero LIST:** CloudTrail data events on the source bucket during a seed and a day of journal follow show HEADs only, and no write (decision 40).
