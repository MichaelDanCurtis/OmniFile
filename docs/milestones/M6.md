## Built so far

**Recall and upload dashboards** (`docs/design/observability.md` §3):
- `GET /v1/activity` (`portal-api.md` §5.13) sums the catalog per UTC day over 7, 30 or 90 days, optionally for one dataset:
  - uploads committed by edges;
  - copies waiting for their read-back;
  - files still landing;
  - recalls started, available and failed, the median and 90th-percentile time to available, bytes recalled, and recalls open now.
- The portal's **Activity** page (ArchiveAdmin) shows it as summary cards, a per-day chart, and a table with the same numbers.
- Tests: `service/tests/web/test_activity.py`, `portal/src/features/activity/activity.test.tsx`, and the browser test `portal/e2e/ops.e2e.mjs` (part of the M4 exit run). It checks the page against `/v1/activity`, the Migrations page against `/v1/sources` and `/v1/locations`, and that a Reader gets neither.

**Observability** (decision 37; `docs/design/observability.md` §1 and §2):
- **Service metrics:** OpenTelemetry instruments (`service/src/omnifile_service/metrics.py`) for queues and handlers, API requests, recalls and uploads, migration prefixes, restores, change-feed lag, provider throttling and edge health. They are exported to Application Insights with the apps' managed identities.
- **Bicep** (`deploy/azure/modules/app-metrics.bicep`):

- **Edge logs:** a data collection rule, and the Azure Monitor Agent on Arc-connected edges (`edge-monitoring*.bicep`).
- **The edge heartbeat now runs**, with certificate renewal. It never did before: an edge's 30-day certificate would have expired. It reports new gauges (fills, recalls waiting, data-volume space, FSAL connections), which the service keeps (migration 0021).
- **The portal's Edges page** (`GET /v1/edges`, `portal-api.md` §5.14) shows each edge's health, with a status judged by the alert thresholds.
- **Tests:**
  - service: `tests/worker/test_metrics.py`, `tests/web/test_edges.py`, and `tests/api/test_feed_and_changes.py::test_heartbeat_keeps_the_edges_health`;

**The appliance image** (decision 38; `appliance/README.md`, spike results in `docs/design/appliance-image.md`):
- mkosi builds Ubuntu 26.04 minimized as a GPT disk image. `/usr` is read-only erofs with dm-verity, there are A/B `/usr` slots, and root holds `/etc` and `/var`. It carries Ganesha with `FSAL_OMNI`, Samba with `vfs_omnifile_prevver`, and our binaries and units.
- **Updates:** `systemd-sysupdate` takes a signed feed: the UKI, `/usr` and its verity hash.
- **Boot counting:** a new version is blessed only once `boot-complete.target` is reached, and the smb-guard kernel check (`smbguard-tool kernel-check`) is required by that target. A kernel without working pre-content events falls back to the previous version.
- **Formats:** `appliance/convert.sh` writes qcow2, VHDX and an OVA.
- **Releases are gated (R3):** `appliance/release.sh` is the only thing that signs a feed. It boots the image being released, runs the kernel canary and the smb-guard A-suite on its kernel, and signs only when every check passes (`appliance/README.md`, "Releasing: the R3 gate"). `build.sh` no longer signs.
- **The maintenance window:** a downloaded update restarts the box only in the admin's window (`systemd-sysupdate-reboot.timer`, from the wizard's restart window).
- **Tests** (all in qemu; the CI lane is `.github/workflows/appliance.yml`): `appliance/tests/smoke.sh`, `appliance/tests/update-round.sh` (0.1.0 → 0.2.0 in its window → a bad 0.3.0 → back to 0.2.0) and the gate's own test. The latest results are under "Appliance gaps closed" below.
- **Source offer:** every build writes mkosi's package manifest (`ManifestFormat=json`), from which `appliance/source-offer/` collects the GPL and LGPL sources for the release (`LICENSES.md`, "The appliance image").

**The setup wizard** (`docs/design/setup-wizard.md`):
- `omnifile-setup` (`edge/crates/omnifile-setup`) asks, on the console, in plain language:
  - the filer's name and network;
  - the data disk (formatted only after `ERASE` if it holds anything);
  - the AD domain, join account and admin group;
  - private endpoints;
  - the enrolment code;
  - the update feed and restart window.
- It applies the answers in twelve idempotent steps (the twelfth, `aws`, below). They are the same unattended from the systemd credential `omnifile.setup`.
- The appliance runs it at first boot: on tty1 until setup is done, or unattended when the credential is there.
- **The break-glass account** (`access-control.md` §8):
  - `omnifile-recovery`, console only;
  - sealed with a password shown once (or a hash, unattended);
  - every session logged at `auth.alert` and marked, so the heartbeat's `recovery_used` makes the Edges page show attention and the `edge-recovery-used` alert fire until it is sealed again.
- **Private networking is enforced on the edge** (decision 22, `omnifile_blob::net`): with it on, a storage name resolves only to private addresses, and a public IP is refused.
- **The portal adds edges:** `POST /v1/edges` and `POST /v1/edges/{id}/bundle` (`portal-api.md` §5.15) issue one-time enrolment codes. The Edges page has Add edge and New code. Bicep passes the enrol URL to `web`, and the pinned CA is a parameter (`deploy/azure/README.md`, step 11).
- **Tests:**
  - unit tests: 39;
  - a real domain join against a Samba AD DC, with the break-glass account: 31/31;
  - unattended setup on the appliance in qemu, with a vTPM: 36/36 (with the Roles Anywhere step, below);
  - the service and portal tests for Add edge.

**TPM-held keys** (`docs/design/setup-wizard.md`, "Keys"; `omnifile_control::seal`):
- The edge's mTLS key, and the key of a certificate request in flight, are sealed with `systemd-creds`. They are bound to the TPM 2.0 and the host key, and never on disk in the clear. The wizard writes `[service] key_protection = "auto"`. An edge enrolled before M6 has its key file sealed in place.
- `omnifile-edge --check` seals and opens a probe, so a box that can't seal fails at start.
- **Tests:**
  - `edge/crates/omnifile-control/tests/sealed.rs`: enrolment and renewal against the mock with sealed keys. No plaintext key is left on disk, the name is bound in, an old key file is sealed in place, and `tpm2` without a TPM refuses before sending anything;
  - the appliance setup test: on a VM with a vTPM (swtpm), the daemon's own unit, sandbox included, seals to the TPM.

**Adding datasets and shares** (`docs/design/share-provisioning.md`):
- **Portal:** Add share on the Shares page (ArchiveAdmin). It asks the plain questions first, with every knob under More settings, and shows the Kerberos throughput note whenever Kerberos is chosen.
- **Service:** `GET /v1/backends`, `POST /v1/datasets` and `POST /v1/shares` (`portal-api.md` §5.16). Every rule the edge checks again is checked first, and both creations are audited.
- **Catalog:** migration 0022 adds each share's NFS export id (fixed for its life, unique per edge) and SMB encryption. `share.upsert` carries them.
- **Edge:** the daemon renders each share's Samba stanza and Ganesha `EXPORT` block from its `share.upsert` and reloads both servers when the files change. It gives the share root its groups' ACL, and moves the ACL when the groups change.
- **Wizard:** the appliance includes the rendered files.
- **Shares of folders and removal** (migration 0023): a folder of a dataset whose root is shared can have its own share; `DELETE /v1/shares/{id}` stops serving a share and keeps its data (never a WORM share). The edge drops a removed share on `share.delete`.
- **Tests:**

  - end to end, step 9 of `tests/e2e/m5_exit_test.sh`: a share added in the catalog is rendered by the real daemon and served by Ganesha under its real unit over NFSv3 and v4; a removed one stops being served and keeps its folder (56/56 with the rest of the M5 test, 2026-10-16).

## Appliance gaps closed (2026-10-21)

**IAM Roles Anywhere works on the appliance** (decision 43):
- **The helper ships in the image.** Before, its unit wanted `/usr/local/bin/aws_signing_helper`, which nothing put on the read-only `/usr`, so it could never start. AWS's 1.8.5 release is now pinned by version and SHA-256 (`appliance/third-party/aws_signing_helper/PIN`, AWS's published checksum). `build.sh` refuses any other file and stages it at `/usr/libexec/omnifile/aws_signing_helper` with its LICENSE and NOTICE. The unit runs it from there and waits for the certificate too.
- **The wizard's `aws` step** (`docs/design/setup-wizard.md`, "Keys"):
  - it makes the key in memory and seals it with `systemd-creds` on stdin, to the TPM and the host key, with no plaintext anywhere;
  - it writes a CSR naming the edge, for the trust anchor's CA, which is the operator's (AWS Private CA or their own; see "Needs the owner");
  - `omnifile-setup aws-cert FILE` installs the certificate, but only if it is for this key and valid;
  - it writes the helper's env file from checked ARNs;
  - the console asks for the ARNs.
- **Found on the way:** with a vTPM and Secure Boot off, `systemd-pcrlock-secureboot-policy` failed at every boot. The preset now disables pcrlock, since our keys are bound to no PCRs.

**The maintenance window is exercised.** `update-round.sh` now has 0.1.0 download 0.2.0 at once. The restart then waits for the window the wizard renders (one time, 5 minutes ahead) on `systemd-sysupdate-reboot.timer`: the box stays up until the window and restarts with it.

**The R3 gate is automatic.** `appliance/release.sh` boots the new image with the suites on a second disk and runs `ci/kernel-canary/run.sh` and the A-suite on its kernel. It signs `SHA256SUMS` only when:
- the guest is that version;
- both suites exit 0;
- every expected check reports PASS.

Otherwise it exits 1 and removes any signature. A subset never signs without `--allow-partial`, which is for test feeds. A signed feed carries `R3-GATE`, under the signature. For the suites to run on the appliance, the canary now finds the kernel config beside the modules, and x03 uses the image's own prevver module (`/usr` is read-only).

**Results.** These ran on 2026-10-21, on Apple silicon: qemu TCG (multi-threaded, `VM_TCG_MULTI=1`) with an x86-64 guest, a swtpm vTPM, the images built by `build.sh` with mkosi in an arm64 container (`Architecture=x86-64`), and binaries cross-compiled. Nothing reached AWS: the Roles Anywhere endpoint was `appliance/tests/ra-stub.py`.
- `smoke.sh`: **18/18** (before #30 added its module-load check). This adds the pinned helper on `/usr`, its key sealed to the vTPM with no plain copy, and the helper serving credentials on 127.0.0.1:9911 (IMDSv2 token, role, keys; 401 without a token). The stub saw CreateSession signed `AWS4-X509-ECDSA-SHA256` with the sealed key's certificate, for the env file's ARNs.
- `setup.sh`: **36/36.** This adds the `aws` step:
  - it seals the key with no plain copy, and writes a CSR that verifies and names `omnifile-edge-<host>`;
  - a certificate for another key is refused and nothing is installed;
  - the CA's certificate is installed with its chain;
  - the helper serves credentials signed with the wizard's key;
  - a rerun changes nothing.
- `update-round.sh`: **12/12** (the 9 A/B checks plus the window's 3). 0.1.0 downloaded 0.2.0, armed `systemd-sysupdate-reboot.timer` 177 s before the window the wizard rendered (`RandomizedDelaySec=0`), and stayed up until the window: its last heartbeat was 0 s after the window opened, and the timer's `systemd-sysupdate reboot` restarted it then. 0.2.0 was blessed, the bad 0.3.0 spent its three tries, and the box fell back to 0.2.0.     - a full release without its source offer refused;
    - an offer whose `MANIFEST.json` isn't complete refused;
    - a build without its manifest refused;

**A deployable service** (#34, `wp1.md`):
