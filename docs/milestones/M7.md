## Threat model and security review

`docs/design/threat-model.md` (T1 to T11). Three independent reviews (the public relay; the service and its Azure deployment; the edge's privileged paths) found one blocking issue and eleven should-fix issues, all fixed. Since then:

- **Users' renames, moves, deletes and chowns reach the catalog** (`docs/design/namespace-sync.md`; threat model T8). An independent review of it found three blocking and five should-fix issues, and a re-review of the fixes one more blocking issue and two should-fix; all are fixed, each with a test that fails without it.
- **Per-app database privileges** (`service/src/omnifile_service/catalog/privileges.py`; T6), applied by every migration run. Every service test runs each app's connections under its own role. The review found that an app could attach an owner-run trigger function to a temporary table of its own; EXECUTE on them and TEMP (the worker aside) are now revoked.
- **Ingress restrictions** on `web` and `enrol` that leave the relay's subnet out (`webAllowedCidrs`, `enrolAllowedCidrs`; T1), and on the relay (`relayAllowedCidrs`, the Bot Service ranges). - **The feed's and audit log's time partitions** are kept by a daily worker sweep (nothing ran it before), with an alert on rows in a DEFAULT partition.

- **Restricted folders (T7, decision 39, the owner's choice of a warning):** a folder an Owner restricts after its `sec=sys` share was made now shows on the share and in the list of shares ("Needs attention"), and the `share-host-trusted-restricted` alert fires, until an ArchiveAdmin switches the share to Kerberos or records an override. A recorded override now silences the check. Tested end to end through the web API and the metrics collector (`test_a_folder_restricted_after_a_sec_sys_share_was_made_needs_an_answer`), failing without the fix.

- **T5 is closed by default** (#34, `results/wp1.md`): `api` sits behind a TCP ingress and terminates mutual TLS itself, with a server certificate from the edge CA that each edge pins from its enrolment answer. - **API clients and keys** (#43, `results/wp11.md`; T3 and T6 in the threat model): only registered clients' tokens are accepted, approval refuses self-approval through a minted key and re-checks the client and owner, refused keys are throttled per address, and `web` can no longer write a backend row directly.
- **The Annex** (#51, `results/wp14.md`): reviews of the edge and the service found 4 blocking, 4 should-fix and 8 minor issues, among them an unreadable folder reported as deleted, ACL capture falling back to the mount's mode bits, and annex copies pruned by rewind depth a day after a NAS delete; a re-review found that an app-proposed annex could be approved by the owner the app named. - **Cloud connect** (#64, #65; threat model T11, from `docs/design/cloud-connect.md` section 5): the delegated ARM sign-in keeps no token and makes only the calls of its stored plan; the two custom roles hold no data action, key, delete or authorization write; the AWS connect template trusts only this tenant's web identity and denies every S3 write outside the ops bucket. - **Annex rules and removals** (#57, #61; `results/wp14-a2.md`): the edge and service reviews of each, and re-reviews of #61, found among others that W2 could delete bytes never verified (a same-size rewrite with its mtime put back; W2 now checks the ctime W1 left, and over SMB the CRC again) and that reusing a removed file's name purged its only copy. ## Windows clients

The client matrix needs Windows clients joined to the client's AD, so it runs in pilot 1's on-site part: `docs/pilots/windows-client-matrix.md` (14 rows, three client versions). Built ahead of it, for risk R4 (Explorer starting recalls):
- **Stubs are offline to SMB clients.** The edge sets `FILE_ATTRIBUTE_OFFLINE` in Samba's `user.DOSATTRIB` whenever a marker says some bytes are not local, and clears it once the file is filled (`omnifile_marker::dosattr`, `[shares] smb_offline`, on by default). Only that bit changes; Samba's creation time and other attributes stay, and the write is conditional on what was read (a race with smbd is retried once; the bit is advisory).
  - **Stubs from before the upgrade, and the switch turned off:** a background pass at start (`offline_sweep`) brings every file's bit in line with its marker, once per edge and again whenever `smb_offline` changes; off, it only ever clears.
  - **Cost:** about 36 bytes of xattr per placeholder. Measured on xfs with 512-byte inodes, a placeholder's attributes stay in the inode with up to 8 named entries in its access ACL (11 without the bit), with or without a resident header; beyond that they take a 4 KiB block. Shares use three groups. Step 7 of the M5 test checks it through a real smbd: a placeholder lists as `Ao`, a filled file as `A`. Unit and xfs tests cover Samba's own layout, a fresh value, directories, and the switch off; each fails without the hook.
- **Offline Files is off** on every rendered share (`csc policy = disable`), so "Always available offline" can't recall a folder.
- **The client kit** (#33, `results/wp7.md`): `tests/windows/` runs the matrix's rows on a Windows client and records pass or fail per row, with a recall counter read from the edge's journal. Its own tests (`tests/windows/run-tests.sh`, Pester 5.7.1) passed 64/64 at their last run; `pwsh` has since gone from the Mac, so they need it back to run again. The rows themselves still run on site.

## Chaos

- **Daemon kill during a fill, and backend outages:** the M1 exit test (steps 6, 8, 11, 12).
- **Daemon kill during a fill from S3:** step 13 of `tests/e2e/m5_exit_test.sh`, which runs where the M1 lane can't (no kernel NFS client). The daemon is killed with SIGKILL while it fills a 132 MiB object from S3, each 4 MiB range slowed to 400 ms, with an NFSv3 and an NFSv4 reader waiting. Before the kill, 64 MiB are on disk and the marker still says 0 bytes resident: an S3 range isn't verified on arrival, so nothing is readable before the whole-file CRC matches. Every answer before the bytes is "not yet"; systemd restarts the daemon and Ganesha keeps its pid; both readers then get the object's bytes, byte-identical. The fill resumes where it recorded its progress (`trusted.omnifile.fetched`, every 64 MiB): 144 MiB were fetched for the 132 MiB object, where starting over would fetch at least 196 MiB. An edge that never resumes fails that check.
- **A control-API outage:** step 11 of `tests/e2e/m5_exit_test.sh`. With the API stopped for 20 s, every read of a file whose bytes are only in S3 answers "not yet" (JUKEBOX, DELAY), never bytes or ENOENT, and the placeholder stays empty; once the API is back, the same read returns the object's bytes. The daemon stays up.
- **Network loss:** step 12 of the same test. Every packet from the edge daemon (an nftables rule on its cgroup, so the service and the sim are untouched) to the backends and the control API is dropped for 45 s, so requests hang rather than fail. Each NFS call still answers within the FSAL's park time (5.1 s, `Park_Ms`), "not yet" over v3 and v4, never bytes or ENOENT; the placeholder stays empty, and a file written over NFS meanwhile is kept. The link then comes back as through a stateful firewall that forgot the open flows: packets of every flow from the outage (22 in the last run, marked through conntrack) keep vanishing, and only new connections pass. The read returns the object's bytes 29 s later, the file written meanwhile is committed 33 s later, a share added in the catalog afterwards reaches the edge (the feed resumed), and the daemon never restarts.
  - **What it doesn't prove:** an edge built with hour-long HTTP timeouts passes this step too, even with the outage's flows kept dead: every new request opens a new connection. (A review found the first version's "forgotten flows" were never held, because packets dropped in OUTPUT never get a confirmed conntrack entry; flows are now marked in OUTPUT and dropped in INPUT, and the step checks some were held. Every answer during the outage must now be "not yet", not merely not bytes or ENOENT; step 11 too.) What the timeouts guard against, a request left waiting for ever on a server that accepts and never answers, is checked at unit level, each test failing without its timeout: `omnifile-control` `a_hung_service_times_out_and_is_retryable` (feed, heartbeat, read credential) and `omnifile-blob` `tests/timeouts.rs` (range reads from Azure and S3 and property reads, before the headers and with a body that stalls halfway).

### The chaos soak, NFS grace and their fixes (2026-11-03 and 11-04, PST)

**NFS grace reclaim** (#48, `tests/e2e/nfs_grace_test.sh`, `results/wp3.md`): three kernel NFS clients in their own namespaces. A holds 8 NFSv4.1 opens with write locks, 4 read-only opens and 4 NFSv3 locks, and is cut off for 20 s after the restart; B asks for the same locks before, during and after grace; C rides the restart with writers.

| run | checks | opens reclaimed | v4.1 locks reclaimed | grace |
|---|---|---|---|---|
| `systemctl restart nfs-ganesha-omni` | 23/23 | 12/12 | 8/8 | 90 s |
| SIGKILL, restarted by systemd | 23/23 | 12/12 | 8/8 | 90 s |
| NLM off, for comparison | 19/19 | 12/12 | 8/8 | 30 s |

B was never granted a lock A held, and the riders saw no error and no wrong byte. NFSv3 locks are reclaimed through SM_NOTIFY, which needs sm-notify at every Ganesha start (Ganesha's first act is `SM_UNMON_ALL`). With NLM on, Ganesha can't end grace early (decision 54). There were no delegations to reclaim: FSAL_VFS, which FSAL_OMNI is stacked on, doesn't support leases.

**The chaos soak** (#48, `tests/chaos/soak.sh` and `soak.py`): eight fault types on a schedule drawn from a seed (SIGKILL of the daemon, Ganesha, smbd or the worker; a Postgres crash; a full data volume; the edge's network dropped; a restart in the middle of a 96 MiB fill), with writes and reads over NFSv3, 4.1, 4.2 and SMB. It checks continuously for zeros, wrong bytes and ENOENT, and at the end that every successful write is committed with its CRC, every recall is `available`, and every unit came back.
- **30 minutes and 55 minutes on the old daemon:** 0 zeros, 0 wrong bytes, 0 ENOENT, and 1 and then 3 lost commits: files closed 0.9 to 2.5 s before a daemon kill or clean restart were never committed.
- **6.75 hours on #42's fix** (seed 3125631393, each fault 12 times; `tests/e2e/results/chaos-6h-wp9.md`): 24,930 good reads, 2,367 of them across unfilled regions and 7,190 of archived files, with 0 zeros, 0 wrong bytes and 0 ENOENT; 1,817 writes and **0 lost commits**. It was red: 4 of 613 recalls stayed `downloading`, and `restart_mid_fill` ran 8 of 12 times. With no fault active, 31 NFS reads got EIO and 6 SMB reads an I/O error.
- **The harness's own gap** (found in review): a read that saw zeros and then failed reported only its error, so "0 zeros" is unproven for the 73 failed reads of that run. `soak_io.py` now counts as it reads, and a failed SMB download has its partial file checked. `tests/chaos/test_soak.py` covers each harness fix with no VM.

**What the soak found, fixed:**
- **Lost commits** (#42, `results/wp9.md`): the detector's wait for the quiet period died with the daemon, and the sweep at start left files the replica didn't know to the detector. Now every sweep hands such files to the commit pipeline, the detector's fanotify group is kept in the systemd fd store, and a durable log of pending closes is replayed at start. All 8 `lost_commit_linux` tests fail on the old main; `cargo test -p omnifile-edge --all-targets` 125 passed in the omnifile-acl VM.
- **Stuck recalls and the EIO reads** (#52): a fill that failed with ENOSPC during a full disk was never reported, and a later read joining the `downloading` recall waited for a feed event that had already come. A failed fill now fails the recall, an interrupted one resumes with a backoff (about 15 minutes) before it is reported, and a joining read starts the fill. M1 83/83, M2 111/111 and M5 139/139 on the dev VM at #52's head (436a678), on the branch before merge.
- **smbd never restarted after a crash** (#50): smbd, nmbd and winbind now restart on failure, bound to the guard.
- **M2 step 10** (#49, `results/wp15.md`, found by the regression lanes, not the soak): a restarted daemon fenced a held SMB fill before Ganesha's FSAL reconnected, and the readers got EIO. The fence now waits, bounded by `fsal.reconnect_wait_ms`, for every running Ganesha's FSAL. M2 111/111 (was 107/111).

## The Annex: rules and removals (2026-11-05)

### Before the bulk seed path (2026-10-16)

`service/tests/api/test_scale.py`, skipped unless `OMNIFILE_SCALE_FILES` is set: a dataset seeded from an S3 Inventory through the real seeder, then the edge's calls through the api app under its own database role. The target is 10^8 files per dataset; this checks that the cost per row stays flat as the catalog grows, so 10^8 costs 500 times what 2×10^5 does.

**Results (2026-10-16, 200,000 files, Postgres 16 on the dev container, one worker):**

| What | Measured | At 10^8, by the same rate |
|---|---|---|
| Seeding | 1,378 files/s; a batch of 5,000 takes 3.3 s in the first tenth and 3.6 s in the last | about 20 hours on one worker; sources on different prefixes seed in parallel |
| Paged snapshot (`GET …/snapshot`, 10,000 a page) | 0.33 s a page at the start, 0.30 s at the end (24 ms of it SQL) | about 50 minutes; very large datasets load from the bulk export instead |
| Digest (`GET …/digest`, daily) | 0.14 s | about 70 s (a full pass by design) |
| As-of listing of a 1,000-entry folder | 6 ms | flat (by folder) |
| One create (`POST …/changes`) | 0.21 s through the test client | flat |
| Catalog size | 384 MB | about 190 GB |

- **Where seeding's time goes:** about nine tenths is in Postgres, in per-row triggers: the commit's `file_version_after_commit` (about 0.4 ms a file), `file_resync_location`, and three file updates, each with its feed event. `catalog-seeding.md` §6 had measured 1,500 files/s.
- **Owner-run triggers cost about 3–5%:** the same 20,000-file insert and commit took 19.0–19.3 s with the trigger functions owner-run (`SECURITY DEFINER` with a fixed `search_path`) and 18.4–18.6 s without.
- **Found by the first runs:** a snapshot page looked like 4.5 s, but that was the test harness validating each 6 MB page against the OpenAPI schema; the scale test now skips that check.

Not done here: 10^8 itself (the catalog alone would be about 190 GB, more than this machine's disk), thousands of concurrent waiters on real hardware (the smb-guard A-suite runs 4,000 here), and 200 GB SEG-Y at line rate (pilot 2).
